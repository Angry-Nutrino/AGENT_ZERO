**3. The exact runtime fix and why `find_spec` returns the wrong answer.**

That swap is done before the warmup synthesis, so the warmup itself runs on CUDA and the JIT cost is absorbed on the GPU session. If CUDA isn't available, it logs and stays CPU. ### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification is the ratio between what the application actually writes and the physical bytes the storage device ends up receiving. Amplification of 10 means for every 1 MB you intend to write, the disk absorbs 10 MB. In LSM engines it's structural, not incidental.

**Where it comes from**

1. **WAL.** Every write hits the write-ahead log before anything else. That's write #1 before the data even reaches the memtable. (Group commit amortizes this, but it's never zero.)

2. **Memtable flush.** When the in-memory table fills, it's written to disk as an SSTable. That's the baseline physical write — 1x for the data itself.

3. **Compaction — the dominant cost.** The LSM maintains levels (L0, L1, L2...). Overlapping SSTables get merged and rewritten into the next level. A key that survives through N levels is physically written N+1 times: once at flush, once per level transition. That's the core mechanism: the same logical data gets rewritten repeatedly over its lifetime, even though the application wrote it exactly once.

4. **Leveled vs size-tiered trade-off.** Leveled compaction (RocksDB default-ish, Cassandra's LCS) keeps levels small and sorted, giving excellent reads and low space usage — but every byte passes through each level, so write amplification typically lands in the 10–30x range. Size-tiered compaction (Cassandra's STCS) merges only when a tier fills, so amplification drops to roughly 2–5x — but at the cost of worse reads and transient space spikes. There is no free lunch; the amplification is just being moved between write, read, and space budgets.

**What it costs in practice**

- **SSD endurance.** This is the one that bites people. Flash has finite program/erase cycles. A consumer SSD rated for a few hundred TBW can be consumed in months, not years, under a write-heavy workload with high amplification — and once it dies, it dies outright, no warning. Datacenter SSDs and careful tuning exist precisely because of this.
- **Sustained throughput.** Effective write bandwidth is device bandwidth divided by amplification. A disk that absorbs 500 MB/s with 10x amplification delivers ~50 MB/s of real ingestion. This caps how much write load the system can take, which is exactly the workload LSM engines are chosen for.
- **Tail latency.** Compactions are background, but they compete for the same I/O queue and CPU. When L0 file counts exceed thresholds, the engine *stalls foreground writes* to let compaction catch up — those stalls show up as sharp p99 spikes. On production systems, write stalls are the classic LSM latency cliff.
- **CPU.** Merging, checksumming, compression during compaction consumes cores that could be serving reads. On write-heavy systems this is often the first bottleneck you hit, not disk.
- **Space amplification, the cousin.** During compaction old and new files coexist, and deleted/overwritten keys sit as garbage until a merge cleans them. Disk usage can run 2–3x logical size at peaks — which is why LSM deployments need headroom, not just "enough for the dataset."

**The mitigations that actually matter**

- Compression first — it cuts physical bytes written even if the logical amplification ratio stays the same.
- Bigger memtables to reduce flush frequency and small-file churn.
- **KV separation** (RocksDB's BlobDB, or value-log designs like WiscKey) — only small keys ride the LSM; large values live in append-only blob files and never get rewritten by compaction. This collapses amplification for value-heavy workloads, which is most real ones.
- Tuning compaction parallelism, L0 thresholds, and level sizes to trade a bit of read performance for fewer rewrites.

This is exactly the LSM-vs-B-tree trade-off Kleppmann walks through in Chapter 3 of DDIA — B-trees write each page once but pay read-modify-write in place; LSM-trees batch sequentially but pay the rewrite tax at compaction. He frames it as choosing which scar you prefer; the number you quoted in practice comes down to how long your keys live, how many levels they traverse, and whether you've separated values out of the tree.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works on a simple premise: **writers never modify existing data in place — they create a new version of it.**

Here's the mechanism, then the mess.

**The mechanism.** Each row/object carries version metadata — typically a creation transaction ID and a deletion transaction ID. A writer that wants to UPDATE a row inserts a brand-new version; the old one stays untouched on disk. A DELETE doesn't remove anything either; it just stamps the row as deleted by the current transaction. When a transaction begins, it takes a snapshot of which transactions are in-flight at that moment. From then on, every read consults that snapshot and asks: "Which version of this row was created by a transaction that committed *before* my snapshot, and has not been deleted by one?" That version is what the reader sees — period.

**Why readers don't block writers.** Because a reader never needs to lock what it's reading. It has its own private view of history. A concurrent writer is busy appending a new version somewhere else; the reader simply never looks at it. The two never contend over the same byte. Writers don't block readers for the same reason — a writer may overwrite or delete a row, but the old version still exists for any reader whose snapshot predates that change. So you get non-blocking reads *and* non-blocking writes in both directions. (Note: writers can still block *each other* — the version chain doesn't resolve two concurrent writers to the same row; that needs a lock or an abort.)

**The garbage.** Every version that is no longer visible to *any* active transaction is dead weight:

- **Obsolete row versions / dead tuples** — the old state of an updated row is garbage as soon as every snapshot that could still see it has closed.
- **Version chains** — each new version points to its predecessor; long chains slow down reads because the reader must walk the chain to find the visible version. That traversal is *spending* the garbage.
- **Index entries pointing at dead versions** — indexes don't get separate versions (in most designs); they accumulate pointers to rows that no longer exist, bloating the index.
- **Transaction bookkeeping** — snapshots and commit records of old transactions also linger until they're provably unneeded.

**The cleanup.** That's the vacuum (PostgreSQL), the purge thread (MySQL InnoDB), or the garbage collector of whatever implementation you're looking at. It scans for versions whose transaction IDs are older than the **oldest still-active transaction's snapshot**, and reclaims them. That watermark is the delicacy: if one long-running transaction stays open, cleanup can't advance past it, and dead versions pile up behind it — the classic "vacuum can't keep up because of one idle transaction" failure mode. Cleanup also has to resurrect the just-deleted row if a transaction that started before the delete is still alive, so it can't be naive about it.

**The tradeoff worth remembering:** MVCC trades space for concurrency. You accept the storage cost of keeping multiple versions alive and the background machinery to reap them — and in return you get read/write concurrency without locks on the read path. That's the deal that makes it the default in basically every serious database.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of taking a single deployable unit — one codebase, one runtime, one database — and splitting it into multiple independently deployed services, each owning its own slice of domain logic and its own data. The *point* is not smaller codebases; it's independent deployability, independent scaling, and fault isolation. If the split doesn't buy you at least one of those, it's just a distributed monolith with extra latency.

The main risks, in order of how badly they actually hurt:

**1. The data boundary.** This is where migrations die. A monolith's schema is one connected graph — foreign keys, shared tables, transactions that touch six tables across three features. You cannot split the code without splitting the database, and the database does not want to be split. You end up with sagas, outbox patterns, idempotency keys, and eventual consistency replacing things that used to be one ACID transaction. Every migration plan that hand-waves "we'll figure out the data later" fails exactly there.

**2. Distributed transaction complexity.** In-process calls become network calls. Guarantees you used to get from the runtime — atomicity, ordering, exactly-once-ish behavior — now have to be *built*. Compensating transactions, rollback logic, handling partial failure mid-workflow. This is a permanent increase in cognitive load, not a one-time migration cost.

**3. Latency and partial failure.** A call that was microseconds is now milliseconds plus serialization, network, and another process's scheduling. Worse: every call can now fail *independently*. You need timeouts, retries, circuit breakers, bulkheads, and a real answer to "what happens when this dependency is down but the rest of the system is fine?" Monoliths crash; distributed systems degrade in messy, partial ways.

**4. Consistency model shift.** Strong consistency to eventual consistency. A JOIN becomes N service calls or a denormalized read model. Stale reads, write skew, divergent data. You pay for this in application code forever after.

**5. Operational explosion.** One deployable becomes ten. Monitoring, logging, distributed tracing, config, secrets, versioning, CI/CD — every axis multiplies. You cannot operate this without real observability, and retrofitting it after the split is miserable.

**6. Wrong boundaries.** If you cut along the wrong seams, every feature touches three services, and you've taken the worst of both worlds: network overhead plus tight coupling. Boundaries have to follow the domain and the org — Conway's law is not optional.

**7. Premature migration.** If you don't have a concrete driver — team size that can't ship from one codebase, a scale limit you're actually hitting, a deploy-frequency bottleneck — you're paying the tax and buying nothing. Small teams and small systems are usually better served by a well-structured monolith.

The safe path is the strangler pattern: carve one bounded context at a time, extract it behind its data boundary, keep the monolith as host. Incremental, reversible, each step independently valuable. Big-bang rewrites are how microservices migrations become career-ending events.

```python
class RateWindow:
    """Sliding-window rate tracker. Record timestamps, query how many fall within
    the last `window_s` seconds (strict left-exclusive, inclusive right)."""

    def __init__(self, window_s: float) -> None:
        self.window_s = window_s
        self._hits: list[float] = []
        # Append-only history: count() prunes self._hits in place, but peak()
        # must evaluate over every recorded timestamp to honor the spec
        # (max over all recorded ts of count(ts)).
        self._all_hits: list[float] = []

    def hit(self, ts: float) -> None:
        """Record an event at the given timestamp (seconds)."""
        self._hits.append(ts)
        self._all_hits.append(ts)

    def count(self, now: float) -> int:
        """Return how many recorded timestamps satisfy:
        now - window_s < ts <= now"""
        cutoff = now - self.window_s
        # Prune expired entries from the front (in-order insertion means
        # once ts <= cutoff is past, everything after is still valid).
        i = 0
        while i < len(self._hits) and self._hits[i] <= cutoff:
            i += 1
        if i > 0:
            self._hits = self._hits[i:]
        # Count remaining hits within the window.
        return sum(1 for ts in self._hits if cutoff < ts <= now)

    def peak(self) -> int:
        """Return the maximum number of hits ever simultaneously inside the
        window, evaluated at each recorded hit timestamp as time advances —
        i.e. max over all recorded ts of count(ts)."""
        if not self._all_hits:
            return 0
        sorted_hits = sorted(self._all_hits)
        max_count = 0
        left = 0
        for i, ts in enumerate(sorted_hits):
            cutoff = ts - self.window_s
            # Strictly left-exclusive window: advance past hits <= cutoff.
            while left <= i and sorted_hits[left] <= cutoff:
                left += 1
            max_count = max(max_count, i - left + 1)
        return max_count

    def first_exceeding(self, k: int) -> float | None:
        """Return the earliest recorded hit timestamp at which the in-window
        count reached or exceeded k — i.e. the first recorded ts (evaluated
        in timestamp order) where count(ts) >= k — or None if it never does."""
        if not self._all_hits:
            return None
        sorted_hits = sorted(self._all_hits)
        left = 0
        for i, ts in enumerate(sorted_hits):
            cutoff = ts - self.window_s
            # Strictly left-exclusive window: advance past hits <= cutoff.
            while left <= i and sorted_hits[left] <= cutoff:
                left += 1
            if i - left + 1 >= k:
                return ts
        return None
```

How the new method satisfies the spec:

- **Earliest ts where count reached k**: iterates `sorted(self._all_hits)` in ascending timestamp order and returns the first ts for which the in-window count `>= k` — the earliest satisfying timestamp by construction. Returns `None` if the threshold is never reached (or no hits recorded).
- **Same window semantics**: uses the identical two-pointer pattern as `peak()` — advancing past hits `<= ts - window_s` honors the strict left-exclusive, right-inclusive boundary, including simultaneous hits at the same ts (duplicates preserved by `sorted`, each counted).
- **No behavior change**: a pure read over the append-only `_all_hits`; it never mutates `_hits`, so `__init__`/`hit`/`count`/`peak` behave exactly as they did at L2. O(n log n) due to the sort, consistent with `peak()`'s existing posture.
