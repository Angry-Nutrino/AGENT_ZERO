### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic concurrency control assumes conflicts are rare — you read, do your work, then check on write whether the underlying data changed (usually via a version number or timestamp). If it did, you abort and retry. Pessimistic concurrency control assumes conflicts are likely — you lock the resource on read so no one else can touch it until you're done.

**Pessimistic** is the right choice when contention is high (many writers fighting over the same row/file), when retries are expensive (long-running transactions that do real work), or when the cost of a conflict is higher than the cost of holding a lock. Classic example: inventory systems where two users might buy the last item simultaneously, or your own vault code where silent corruption on concurrent writes was unacceptable.

**Optimistic** wins when contention is low (most reads won't conflict), when your transactions are short and cheap to retry, or when you can't afford the latency and throughput hit of holding locks. Git's model is an example — multiple people edit the same file, conflicts surface at merge time. Also common in read-heavy web apps with versioned documents.

The trap is applying either one universally. Pessimistic under low contention burns throughput on lock overhead for no benefit. Optimistic under high contention degenerates into constant retry thrash. Your EventQueue is a good hybrid — the `drain_blocking` gets the batch, processes it, and the write guard on vault ensures the optimistic path has a fallback when it collides.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Threads share the same memory space within a process — they see the same heap, global variables, and file descriptors. Processes are isolated: each gets its own virtual address space, file descriptor table, and signal handlers, which means context-switching between threads is cheaper, but one thread crashing in C extension land can take the whole process down.

In Python, the GIL adds a practical constraint: for CPU-bound work, threading gives you false parallelism at best and contention overhead at worst. Multiprocessing side-steps the GIL entirely — each process gets its own interpreter, so you can actually saturate all cores. Threading still wins for I/O-bound workloads — network calls, disk reads, database queries — where most of the time is spent waiting on the kernel, not executing Python bytecode, so the GIL is released and you get real concurrency without the serialization cost of passing data between process boundaries.

Pick multiprocessing when you need to parallelise computation on multiple cores. Pick threading when you need to overlap I/O waits. Pick neither if the task is trivially sequential — the setup overhead isn't free.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Average latency lies about user experience because it's dominated by the bulk of fast requests — the slow tail (p99/p999) is what actual users in a multi-request flow hit.

In distributed services, a single page load fans out across dozens of microservices or shards. If a user makes 40 backend calls per request, and each has a 99th percentile latency of 100ms, the **probability that at least one call exceeds 100ms** is 1 - (0.99)^40 ≈ 33%. For 100 calls, it's ~63%. So tail latency *compounds* non-linearly — the user's overall experience is determined almost entirely by the worst-performing branch, not the median one. Average latency here is a distraction because it hides the outlier that actually hurts the user.

One architectural technique to tame it: **hedged requests** (also called speculative retries). Issue the same request to two replicas, accept whichever returns first, cancel the other. This converts a 100ms p99 into a sub-50ms p99 trivially because the joint distribution of two independent samples is much tighter — unless failures are correlated (same shared resource). The trade-off is 2x load on backend replicas, so you apply it selectively: only on request paths where tail latency is the highest metric cost (e.g., your internal RPC fan-out, not the cache hit path with 1μs baseline). By the numbers, p99 of `min(X, Y)` for two independent samples from a distribution E with p99 latency τ is typically < 0.5τ, which is often worth the resource multiplier for user-facing latency SLOs.
