### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic concurrency control assumes conflicts are rare: read the data, perform the work, then check before committing — if the version hasn't changed, write; if it has, abort and retry. Pessimistic concurrency control assumes conflicts are likely: lock the resource before you touch it, so nobody else can modify it until you're done.

Optimistic wins when contention is low and retries are cheap — think read-heavy workloads, short transactions, or CRDT-based systems where conflicts merge automatically. Pessimistic wins when contention is high, retries are expensive, or you need strict ordering guarantees — think inventory systems (two people can't buy the same last seat), financial ledgers, or any operation where a retry means rolling back a costly side effect.

The wrong choice in either direction hurts differently: optimistic under high contention gives you throughput collapse from abort storms; pessimistic under low contention gives you unnecessary lock overhead and reduced concurrency. Know your workload's conflict profile before you decide.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Two levels.

**Process vs Thread:** A process has its own isolated virtual address space — heap, code, data, file descriptors, everything. A thread shares the address space with sibling threads in the same process. What threads share: heap, code/data segments, open files, signal handlers. What they don't share: stack, registers, program counter, errno. Context switching between threads is cheaper because the TLB doesn't need flushing. Context switching between processes is heavier — the kernel flushes the virtual memory mapping and reloads page tables.

**Multiprocessing vs Threading in Python specifically:**
- Threading is **not parallelism** under CPython — the GIL ensures only one thread executes Python bytecode at a time. Threading is for **concurrency with I/O.** Your thread yields the GIL during I/O waits (network, disk, sleep), so other threads run. CPU-bound work on threads is serialized at the bytecode level — no speedup.
- Multiprocessing gives you true parallelism via separate processes, each with its own GIL. The cost: data can't be shared implicitly — you must pickle/serialize across a `multiprocessing.Queue`, `Pipe`, or shared memory (`multiprocessing.Value`/`Array`). Overhead is higher per-spawn.

**Decision rule:**
- **Threading** when your workload is I/O-bound: HTTP requests, file reads, database queries, waiting on APIs. Each thread yields the GIL while blocked, and you get concurrent throughput on a single core.
- **Multiprocessing** when your workload is CPU-bound: matrix multiplication, image processing, tokenization, model inference, parsing large blobs. You need a process per core to bypass the GIL.
- **Hybrid pattern** when both exist: use `concurrent.futures.ThreadPoolExecutor` for the I/O layer, `concurrent.futures.ProcessPoolExecutor` for the compute layer, and dispatch accordingly. Your orchestrator today already does this via `_run_fast` vs `run_task` — the call patterns map to the same distinction.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the long tail of request durations — the slowest 1% (p99) or 0.1% (p999). It dominates user experience because a single user request fans out across dozens or hundreds of backend servers in a distributed system; the user waits for the *slowest* of those sub-requests. If a service calls 100 backends in parallel, even with a 1% tail probability per backend, there's a ~63% chance *someone* experiences the p99 — and that user is *you*. The average hides this entirely.

The architectural technique with the highest return: **hedged requests**. Issue the same request to two replicas, take whichever responds first, cancel the other. This collapses p99 tail by squaring the probability — a request enters the tail only if *both* replicas hit it simultaneously. Cuts effective latency from p99 to roughly p50-p75 for typical distributions, trading marginal capacity overhead for dramatic user-facing consistency.
