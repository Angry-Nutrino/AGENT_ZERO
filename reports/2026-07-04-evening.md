### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write-ahead logging (WAL) is how databases guarantee durability without flushing every data page on every write.

**How it works:**
- Before modifying any in-memory data page, the database appends a sequential log record describing the change to a write-ahead log on disk.
- This log append is *cheap* — sequential I/O, typically just a few microseconds.
- The actual in-memory page is updated immediately. The data page on disk is *not* touched yet — it remains stale.
- If the database crashes, on restart it replays the WAL from the last checkpoint, reapplying any committed transactions that hadn't yet been flushed to the data files.

**Why this matters for performance:**
- A transaction is "durable" the moment its WAL record hits disk — no need to scatter random data page writes across the transaction's critical path.
- Data pages get flushed to disk lazily, batched by the background checkpoint process, amortizing expensive random writes over many transactions.
- The WAL itself is consumed sequentially — the read head barely moves, so throughput stays high even on spinning disks.

**Correctness guarantee:**
- The WAL and data pages follow a strict ordering: a page is never written to disk *before* its corresponding WAL record. This is called the WAL protocol — it's the invariant that makes crash recovery safe.
- If a data page on disk is old and the WAL has a newer version, the replay fixes it. If the data page is already up to date, the WAL record is just skipped. Either way, the database reaches a consistent state.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC lets readers and writers coexist by storing multiple versions of a row. A writer creates a new version of the row without overwriting the old one. A reader that began its transaction before that write happened continues to see the old version — it never waits for a lock held by the writer. The writer doesn't block on the reader either, because it's not modifying the data the reader is looking at; it's creating a separate snapshot.

The garbage it creates is **dead row versions** — tuples that are no longer visible to any active transaction. Over time, these accumulate in the table's heap pages (Postgres calls them "dead tuples", InnoDB calls them "old versions in the rollback segment"). If left uncollected, they bloat the table, degrade cache efficiency, and make sequential scans slower because the engine has to skip invisible rows.

The cleanup mechanism is **VACUUM** in PostgreSQL (autovacuum triggers it), **purge** on a dedicated background thread in MySQL/InnoDB. The collector identifies which versions are below the oldest active transaction's snapshot horizon and reclaims that space for reuse. If the cleanup falls behind — because of long-running transactions pinning old snapshots or autovacuum being too conservative — the table grows unbounded, and index-only scans stop working because visibility info isn't in the index, forcing heap lookups on dead rows.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services that communicate over a network, each owning its own data and bounded context.

The main risks are:

1. **Network as the new primitive** — In a monolith, a function call is reliable, low-latency, and free. In a distributed system, every call is a network hop with potential for latency, timeout, and partial failure. Teams that don't internalize this end up with chatty service-to-service calls that are slower and less reliable than the original monolith.

2. **Distributed transactions break** — The moment you split a database, ACID transactions across services become distributed transactions (2PC, Saga patterns, or eventual consistency). Most teams underestimate how much business logic relied on "just wrap it in a transaction." The result: data inconsistencies that were previously impossible.

3. **Operational complexity multiplies** — One monolith means one deployment pipeline, one set of logs, one monitoring dashboard. N services means N of everything. If you haven't invested in observability (distributed tracing, centralized logging, metrics aggregation) and CI/CD automation before the split, you're not ready.

4. **Service boundaries are wrong the first time** — You discover the real bounded context by operating the system, not by drawing boxes on a whiteboard. The first decomposition is almost always wrong. If your architecture can't tolerate re-merging or re-splitting services without a rewrite, you've locked yourself into bad boundaries.

5. **The distributed monolith trap** — The most common failure mode. Teams create services that share a database, share code libraries, or make synchronous calls in chains so deep that deploying one service requires deploying five. You get all the complexity of microservices with none of the independence.
