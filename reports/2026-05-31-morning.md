### Q01 [CHAT] — Explain the difference between a process and a thread. What do they share and what do they not share? Answer from your training knowledge.

A process is an independent execution unit with its own virtual address space, file descriptors, and process ID. A thread is a lightweight execution unit within a process — multiple threads share the same address space, open files, and signal handlers of their parent process.

**What they share (threads within a process):** Heap memory, code/data segments, open file descriptors, current working directory, user/group IDs, and signal dispositions. Each thread gets its own stack, register set, program counter, thread ID, and errno value.

**What they don't share (distinct per process):** Virtual address space (complete isolation — one process cannot access another's memory without IPC), file descriptor table, process ID, parent process linkage, resource limits, and global scheduling context. A crash in one process cannot corrupt another's memory; a crash in one thread can bring down the entire process because the address space is common.

**Key cost difference:** Context switching between threads is cheaper than between processes because the MMU doesn't need to flush the TLB (the virtual memory mapping stays the same). On Linux, `clone()` with appropriate flags controls what gets shared at creation time — threads and processes are actually a continuum, not a binary distinction.

### Q04 [CHAT] — What is the difference between synchronous and asynchronous I/O? When does async help and when does it not? Answer from your training knowledge.

Synchronous I/O blocks the calling thread until the operation completes — every read, write, or connect waits its turn. Asynchronous I/O returns immediately, allowing the thread to continue execution while the OS or an event loop handles the I/O in the background, completing and notifying via callbacks, futures, or awaitables.

Async helps when I/O-bound work is the bottleneck and you're managing many concurrent operations: hundreds of network connections, file reads with interleaved processing, database queries where latency dominates. A single thread multiplexed across many I/O operations can match or exceed the throughput of a thread-per-connection model with a fraction of the memory and context-switch overhead.

It does not help when the work is CPU-bound — computation, data transformation, number crunching. Handing off a busy loop to an async scheduler doesn't make the CPU finish faster; it just adds scheduling overhead. It also doesn't help for a single sequential I/O operation where the next step depends on the result — the await pattern reads identically to synchronous code and performs marginally worse due to event-loop overhead. Most importantly, async does not make individual I/O faster; it reduces *waste* by enabling overlap. If there's nothing to overlap, there's no gain.

### Q10 [CHAT] — What is a B-tree and why do databases use B-trees for indexes instead of plain binary search trees? Answer from your training knowledge.

A B-tree is a self-balancing tree data structure that maintains sorted data and allows searches, sequential access, insertions, and deletions in logarithmic time. Unlike binary search trees, B-trees are optimized for systems that read and write large blocks of data — specifically, disk storage.

Databases use B-trees instead of BSTs for two reasons. First, **height**. A B-tree's branching factor is configurable and typically large (hundreds of children per node), so its height stays very shallow — often 3–4 levels even for millions of records. A BST's height grows linearly with the number of records in the worst case (O(n)) unless explicitly balanced. Second, **block locality**. B-trees group many keys into each node, matching the size of a disk page or filesystem block. A single node read fetches dozens or hundreds of keys in one I/O operation. A BST stores one key per node, so every comparison potentially costs a separate disk seek. On spinning disk or even SSD, those seeks dominate latency.

The result: B-trees turn what would be dozens of random I/O operations into a small handful of sequential block reads. That's the entire reason they dominate database indexing — they're designed around the physical reality of storage, not just algorithmic complexity on paper.
