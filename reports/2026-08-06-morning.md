### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

## Optimistic vs Pessimistic Concurrency Control

**Pessimistic** assumes the other guy *will* show up. You acquire a lock before touching the resource, hold it for the duration of the operation, and force anyone else who wants it to wait. If the lock is exclusive, the second party blocks until the first finishes. Examples: `SELECT ... FOR UPDATE`, `threading.Lock()`, file locks, mutexes, two-phase locking in relational databases.

**Optimistic** assumes the other guy *probably won't* show up. You do the work without locking, then validate at the commit point — typically via a version number, timestamp, or compare-and-swap — that the data hasn't changed underneath you. If it has, you abort and retry. Examples: MVCC in PostgreSQL (writers don't block readers), HTTP ETags, CAS in Redis, Git's merge-then-resolve model.

### Decision criteria

Four variables decide it:

1. **Conflict probability** — how often two operations actually collide on the same data
2. **Cost of retry** — what does wasted work cost? Recomputing 10 minutes of a model run is expensive; re-inserting a row is cheap
3. **Cost of waiting** — what does blocking cost? A held lock on a hot path can stall everything behind it
4. **Predictability** — do you need bounded, guaranteed latency, or can you accept "sometimes it fails and retries"?

**Choose pessimistic when:**
- Conflicts are frequent (high contention on the same resource)
- Retries are expensive — the work done before the conflict is heavy and can't be cheaply redone
- Operations are short, so lock hold time is brief
- You need deterministic behavior — no surprise aborts at the end of a long transaction

Classic case: a bank transfer. Two updates to the same account in close succession are likely; a retry after abort is acceptable but a lock is simpler and the hold time is milliseconds.

**Choose optimistic when:**
- Conflicts are rare (low contention)
- Retries are cheap — a failed CAS is just a re-read and re-try
- Your workload is read-heavy, and you don't want readers blocked by writers
- Operations are long — holding a lock for minutes of computation is a serialization disaster

Classic case: a web service updating profile data. Hundreds of reads per second, rare write collisions; an ETag check costs nothing, and the occasional 409 → re-fetch → retry is harmless.

### How you actually choose

Compare the *expected* costs:

- **P(conflict) × cost_of_retry** = expected cost of optimistic
- **cost_of_waiting under lock contention** = expected cost of pessimistic

Optimistic wins when the expected abort cost is lower than the expected blocking cost. That's the whole game.

### The practical hybrid

Most real systems don't pick one. PostgreSQL gives you MVCC for reads (optimistic visibility) plus `SELECT FOR UPDATE` when you explicitly need the pessimistic guarantee on writes. The pattern that applies to your orchestration layer: **optimistic for reads and low-collision task dispatch, pessimistic for writes to shared mutable state** — and for anything backed by CUDA, pessimistic without negotiation, because the failure mode isn't a clean abort, it's silent corruption that neither strategy's retry handles.

The race condition you already fixed in the vault was exactly this decision being made for you: `threading.Lock()` is the pessimistic choice because the retry cost — corrupted memory — is effectively infinite. When you get to the arbitration engine, the correct default is: pessimistic when the resource is shared and the cost of collision is corruption or an inconsistent write; optimistic when the collision is merely wasted compute and the retry is bounded.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

A process is an isolated execution environment: its own virtual address space, file descriptors, signal handlers, and system resources. A thread is a single execution sequence within a process; threads in the same process share the process's memory, heap, code, and open files, but each has its own stack, registers, program counter, and thread-local state. Context switching between threads is cheap because they share an address space; switching between processes is more expensive because the kernel must swap memory mappings and flush caches. Processes are also safer — one crashing doesn't take down the others, whereas a segfault in one thread kills the whole process.

In Python specifically, the GIL complicates the choice:

- **Multiprocessing** — use when the work is CPU-bound (heavy computation, number crunching, image/video processing). Each process gets its own Python interpreter and GIL, so you get true parallelism across cores. The cost: higher memory overhead (each process has its own interpreter and state), slower startup, and you pay for inter-process communication via `Queue`, `Pipe`, or shared memory.
- **Threading** — use when the work is I/O-bound (network requests, file reads/writes, database calls, waiting on APIs). Threads are lightweight and share memory, so passing data between them is trivial. The GIL is released during most blocking I/O waits, so multiple threads can genuinely overlap their waiting time — you get concurrency without parallelism.

There's also the third option worth knowing: `asyncio` for very high-concurrency I/O with minimal overhead, and the hybrid pattern — use multiprocessing for the CPU-heavy cores and threads or async within each process for the I/O portions.

The rule of thumb: CPU-bound → `multiprocessing`; I/O-bound → `threading` (or `asyncio`); both → hybrid.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency dominates because user-facing requests in a distributed system are rarely one network call — they're a fan-out. Load a page, and you're waiting on dozens of services sequentially or in parallel. That changes the math completely.

**The amplification arithmetic.** If a single user request touches 100 independent services, and each service has a p99 latency of 100ms, the chance that *all* 100 finish within 100ms is 0.99^100 ≈ 0.366. Meaning ~63% of user requests take longer than 100ms — even though every individual service looks healthy at p99. The user's tail is the convolution of every component's tail. The average of that distribution tells you nothing about the outliers that actually ruin the experience, because averages are dragged by the common case. An outlier that takes 4 seconds could move the p999 by an order of magnitude while barely budging the mean.

**What the tail actually signals.** The mean hides where the system is fragile. Tail events are where the real failure modes live: GC pauses, lock contention, network retransmits, noisy neighbors stealing CPU, scheduler preemption, a hot shard. And users don't experience "average" — they experience individual requests. A 3-second stall feels broken even if the mean is 200ms. That's also why SLOs are written as percentiles, not averages: a service meeting its mean while violating its p99 contract is failing its users.

**One technique: hedged requests.** From Dean & Barroso's "The Tail at Scale." When a sub-request is in flight, you don't just wait for it — after a small delay (say, the p95-ish mark), you issue the *same* request to a second replica and accept whichever responds first, canceling the loser. The math is the point: if each replica independently has a p99.9 of 1s, the chance that *both* replicas are simultaneously slow is (0.001)² = 10⁻⁶. The tail gets squared — p99.9 of one replica becomes roughly p9999 of the hedged pair. Cost is moderate extra load; benefit is an exponential cut in the straggler probability. It's the most direct attack on the problem because it doesn't tune a distribution — it changes the distribution's shape.

The supporting practice that makes hedging safe is aggressive *client-side* timeouts: fail fast at the sub-request level rather than letting one straggler hold the whole fan-out hostage. Every un-bounded wait is a tail amplifier — bound it, then let hedging do the rest.

### Q20 [DELIBERATE] — core_logic/mcp_client.py multi-hop. (1) _ensure_alive restarts a dead server via connect(); what exception class does call() raise on a tool error? (2) Why must MCP calls use a direct await and never asyncio.to_thread — what concretely breaks if call() is run in a worker thread?

**1) What `call()` raises on a tool error**

`MCPError` — the module-level class at `mcp_client.py:19`. `call()` raises it at the tool-error site, `mcp_client.py:132-133`: when the response has `isError: true`, it raises `MCPError(f"Tool '{tool_name}' returned error: {result}")`. - `:107` — server not connected
- `:173` — server closed stdout mid-request (this is what `_ensure_alive` is meant to prevent from bricking)
- `:182-185` — JSON-RPC error frame (`[code] message`)

And `connect()` itself raises `MCPError` on handshake failure (`:88`), which propagates out of `_ensure_alive` — the comment at `:99` marks it: "raises MCPError on failure — caller surfaces it." So `call()` → `MCPError` in every branch, transport or tool-level. One type, no surprises.

**2) Why direct `await`, never `asyncio.to_thread`**

`mcp_client.call()` is an `async def`. That's the whole of it, mechanically:

- **`asyncio.to_thread` does `loop.run_in_executor(None, func, *args)`.** It calls `func` in a worker thread and treats the return value as the result. Calling an `async def` doesn't run it — it constructs a coroutine. So the thread returns a live coroutine object, the body of `call()` never executes, and you get a silent no-op (the tool result becomes `<coroutine object MCPClient.call at 0x…>`, or at best a "was never awaited" warning). The tool call didn't happen and nothing tells you why.

- **If you "fix" it with `asyncio.run(call(...))` inside the thread, it breaks worse.** `asyncio.run` spins up a *second* event loop in the worker thread. Everything inside `call()`'s chain is bound to the *main* loop: the per-server `asyncio.Lock` (`:152`), the subprocess `StreamReader/StreamWriter` (`:164-170`), and the `asyncio.wait_for` timeout (`:169`). Awaiting any of those on a foreign loop raises `RuntimeError: <…> is bound to a different event loop`. The MCP response never gets read.

- **The concurrency guarantee dies too.** The lock at `:152` is loop-bound at first acquisition. Concurrent `to_thread` calls for the same server create threads each with their own loop → each holds the "same" lock on a different loop → two threads write to stdin at once → interleaved JSON-RPC frames on the pipe. The `:192` C-13 comment exists because that corruption is real; the lock only works if every `call` runs on the one loop that owns the lock.

- The pipeline around it is in the same coroutine: `tool_executor.py` routes MCP tools through `_execute_mcp` (`:429`, `:553`), which owns write-ledger protection, read-hash recording, and `task_id` threading inside the same `await` chain (docstring `:260-264`). Off-threading `call` doesn't just break the transport — it splits the bookkeeping from the dispatch.

The contract is documented in both places: `tool_executor.py:15-16` — "mcp_client.call() is async — call it directly with await. Never wrap async MCP calls in asyncio.to_thread or asyncio.run." — and `CLAUDE.md:892`. The distinction is clean by design: native *blocking* tools (`web_search`, `python_repl`, `vision_tool`…) go through `asyncio.to_thread` in `execute_fast`/`execute_deliberate` because they're sync functions; MCP calls are async transport I/O and take the direct-await branch. That split in the dispatch code is the enforcement of the rule.
