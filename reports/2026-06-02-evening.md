### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

Two ways to handle increased load.

**Horizontal scaling (scaling out):** Add more machines. You go from one server to ten. Each handles a fraction of traffic, and the system keeps working if one dies.

**Vertical scaling (scaling up):** Add more resources to the existing machine. More RAM, faster CPU, bigger disk. One machine, just stronger.

---

**Tradeoffs:**

| Axis | Horizontal | Vertical |
|---|---|---|
| Upfront cost | Higher — you need load balancers, networking, distributed state management | Lower — just a bigger instance |
| Operational complexity | Significantly higher — distributed systems problems (data consistency, network latency, partial failures) | Low — same OS, same config, no coordination protocol needed |
| Fault tolerance | Inherent — losing one node degrades capacity but doesn't crash the service | Single point of failure — if the box goes down, everything goes down |
| Scaling ceiling | Theoretically unbounded — you can keep adding nodes | Finite — there's a maximum instance size the hardware supports |
| Stateful workloads | Painful — sessions, databases, caches need to coordinate across nodes | Natural — everything runs on one machine, no consistency problem |
| Cost curve | Linear or sublinear if you can use commodity hardware | Superlinear at the top end — high-RAM or high-core instances have premium pricing |
| Performance | Depends on network — inter-node latency is a bottleneck for tightly coupled operations | Best for compute-bound workloads that fit in one address space |
| Maintenance | Rolling updates, zero-downtime deploys possible | Downtime required for upgrades — you have to take the machine down |

---

**The practical decision rule:**

- **Vertical first.** Always. You start with one box, scale it up. It's cheaper, simpler, and keeps your architecture manageable. Most systems never outgrow a single beefy server.
- **Horizontal when you hit the vertical ceiling**, or when fault tolerance requirements exceed what a single machine can guarantee. At that point you accept the complexity because the alternative is impossible.

Premature horizontal scaling adds years of distributed-systems debt you didn't need to pay.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

A **primary key** uniquely identifies each row in a table — it must be unique and non-null. A **foreign key** is a column (or set of columns) in one table that references the primary key of another table.

The foreign key enforces **referential integrity**: it prevents inserting a value in the child table that doesn't exist in the parent's primary key, and it blocks deleting a parent row while child rows still reference it (unless `ON DELETE CASCADE` is set).

**Example:**

```sql
-- Parent table
CREATE TABLE Customers (
    customer_id INT PRIMARY KEY,
    name VARCHAR(100)
);

-- Child table
CREATE TABLE Orders (
    order_id INT PRIMARY KEY,
    customer_id INT,
    FOREIGN KEY (customer_id) REFERENCES Customers(customer_id)
);
```

`Orders.customer_id` must match an existing `Customers.customer_id`. You cannot create an orphan order, and you cannot delete a customer who still has orders (without cascade).

### Q08 [CHAT] — Explain how a write-ahead log (WAL) gives a database both durability and crash recovery, and what cost it imposes on writes. Answer from your training knowledge.

A write-ahead log gives durability by enforcing a strict protocol: every modification is first appended as a sequential log record to persistent storage (the WAL) *before* any dirty page is written back to the database's main data files. The log record contains enough information to redo or undo the change. The database only acknowledges a transaction as committed once its commit record reaches the WAL on disk.

Crash recovery follows directly: on restart, the database replays the WAL forward from the last checkpoint (the *redo* phase) to restore any committed changes that had not yet been flushed to the data files. Then it rolls back any uncommitted transactions that were in-flight at the time of the crash (the *undo* phase), using the before-images stored in the log. Because the WAL is ordered and append-only, recovery is always deterministic — you never lose a committed transaction and you never apply an uncommitted one.

The cost on writes is threefold:

1. **Every commit forces a synchronous `fsync`** — the storage device must confirm the log record is on stable media before the transaction is acknowledged. This is the single largest write latency bottleneck.
2. **Log bandwidth is additive** — every byte written to the data page is also written to the WAL, so total write IO is at least doubled for most workloads (more if the database uses full-page images for the first modification to a page after a checkpoint).
3. **Checkpoint overhead** — periodically, the background checkpoint process must flush all dirty pages to the data files and truncate the WAL, which spikes write IO and can compete with foreground writes. The interval and cost of these checkpoints are tunable, but you cannot eliminate them entirely.

The call is `os.replace`.

On Windows, `os.replace` raises `PermissionError` when another process (such as a reader from `/soul` or a harness `python_repl`) has the temp file open. The code wraps `os.replace` in a retry loop with backoff — it catches `PermissionError` and retries until the lock is released. If the replace consistently fails across retries, the in-RAM dict is preserved and the write is effectively dropped until the next save cycle, at which point it retries with a fresh temp file. The full-in-RAM design means a dropped replace self-heals because the next save writes the complete state again.
