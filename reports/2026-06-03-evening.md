### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

Two strategies for handling increased load.

**Horizontal scaling** (scaling out): add more machines to a pool behind a load balancer. Tradeoffs — no upper bound on capacity, fault-tolerant by design (one node dies, the rest keep serving), but introduces network overhead, data consistency challenges (distributed state is hard), and operational complexity (orchestration, monitoring, rebalancing).

**Vertical scaling** (scaling up): give the existing machine more CPU, RAM, faster disks. Tradeoffs — simpler to implement (no distributed system problems), lower latency within the node, but has a hard physical ceiling (the biggest machine money can buy), creates a single point of failure, and cost superlinear at the high end (the jump from 64GB to 128GB costs more than just double).

**Decision rule**: start vertical for simplicity until you hit diminishing returns on cost or hit the ceiling — then go horizontal, but only after you've designed your data layer to handle distribution. You don't start with Kubernetes for a PostgreSQL instance serving 500 users.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

**Primary key** — a column or set of columns that uniquely identifies every row in a table. No duplicates, no nulls. One per table. The table's identity.

**Foreign key** — a column or set of columns in one table that references the primary key of another table. Enforces referential integrity: you cannot insert a value in the child table unless it exists in the parent table's primary key. Multiple foreign keys per table, and they can be null.

**Practical distinction**: The primary key says "this is who I am." The foreign key says "this is who I'm related to." A foreign key can reference its own table's primary key (self-referencing), which is how you model hierarchies like employee-manager in a single employees table.

### Q08 [CHAT] — Explain how a write-ahead log (WAL) gives a database both durability and crash recovery, and what cost it imposes on writes. Answer from your training knowledge.

Two-phase protocol: before any data page is modified, the change is appended to an append-only log on stable storage. The log record contains enough information to either redo or undo the change (physical or logical logging).

**Durability** comes from the commit record. When a transaction commits, the database fsyncs its log records to disk — including the commit marker. Even if the database crashes immediately after, the committed transaction is logged. On restart, the recovery process replays committed transactions from the log that were not yet applied to data pages.

**Crash recovery** handles both committed and uncommitted work. The recovery process scans the log from the last checkpoint and builds two sets in one pass: (1) all pages modified by committed transactions since the last checkpoint need to be redone (REDO phase — reapply changes to data pages), and (2) all pages modified by uncommitted, in-flight transactions need to be undone (UNDO phase — roll back by restoring from log's before-images, or by writing compensating log records). Checkpoints bound how far back the recovery scan must go — without them, recovery would re-scan the entire log since database creation.

**Three costs on writes:**

1. **Synchronous fsync on commit** — Every commit must flush the log to disk before the commit is acknowledged. This is the dominant cost. The transaction is at the mercy of disk latency per commit, not per batch of writes.

2. **Doubled write IO** — Every data page modification is written twice: once as a log record, once when the page is eventually flushed to its data file location. The log write is sequential and small (the record), the data write is random and full-page. The log absorbs the sequential write cost, but the total bytes written to stable storage is at least double what a no-WAL system would write.

3. **Checkpoint overhead —** To bound recovery time, the database must periodically write dirty pages to their data file locations and record a checkpoint in the log. Checkpointing itself is expensive: it forces full-page writes of all dirty pages in the buffer pool, and while it runs, it must coordinate with concurrent transactions to ensure a consistent snapshot of what's been flushed. Fuzzy checkpoints mitigate this (allow dirty pages to be written incrementally) but add complexity to the recovery logic.

### Q15 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is appropriate. Answer from your training knowledge.

Optimistic concurrency control assumes conflicts are rare—you read a value, perform work, and on write you check that the original value hasn't changed (usually via version number or checksum). If it has, you abort and retry. Pessimistic concurrency control assumes conflicts are frequent—you lock the resource (read lock, write lock, or exclusive lock) before any operation, holding it until you're done, so no other party can interfere.

**Use optimistic when:**
- Contention is low (read-heavy workloads, few collisions)
- Retries are cheap (the work between read and write is fast)
- You can tolerate occasional rollback
- You need high throughput under low contention (no lock overhead)

**Use pessimistic when:**
- Contention is high (many writers to the same data)
- The work between read and write is expensive or irreversible
- A retry would be costly or impossible (e.g., a bank transfer)
- You need deterministic, predictable behavior under load

Your vault dedup scenario from the other day is a textbook case: two threads checking and writing without locking is the optimistic failure mode. A lock would have been the pessimistic fix.
