### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design trade-off: you don't overwrite data in place, you write new versions and clean up later. Every write to the memtable is cheap, but that data gets re-written multiple times before it settles.

Three sources, in order of severity:

1. **Compaction cascades.** When a level-0 SSTable is flushed from the memtable (~4 MB), it gets merged into level 1. That merge reads all overlapping SSTables in level 1 and writes a new one. When level 1 fills up, it compacts into level 2. Each level is typically 10x larger than the previous (size ratio `R` = 10). A single write at the leaf level has been re-written roughly `log_R(T)` times where `T` is the total data size — typically 3–4 passes for a terabyte-scale store. This is the dominant term.

2. **Minor compaction** (level-0 to level-1). Level 0 SSTables have overlapping key ranges, so every minor compaction reads all L0 files and writes out sorted L1 files. This alone amplifies each incoming write 2–3x depending on how many L0 files accumulated before compaction triggers.

3. **WAL.** Practical LSM engines write every mutation to a write-ahead log before acknowledging. The WAL write is sequential and cheap, but it's still amplifying the user's logical write by 1x at minimum — the same data gets written twice before it even reaches the memtable flush.

What it costs in practice:

- **RocksDB** with default settings: write amplification factor 10–20x on a sustained write workload. This means 10–20 GB of actual disk I/O for every 1 GB the application thinks it wrote. Tuning level size ratio from 10 → 5 drops this to ~5–8x but increases read amplification because more levels to probe.
- **LevelDB** similar but higher due to lack of LevelDB's newer compaction strategies.
- **SSD wear.** Consumer SSDs endure ~300–500 TBW (terabytes written). A 100 GB/day write workload on a standard LSM setup burns through 1–2 TBW/day after amplification. That's 300–500 days of life — not years. This is why DynamoDB and Cassandra offer tiered storage.
- **CPU cost.** Compaction threads saturate one core per compaction job. On write-heavy workloads, compaction is the throughput bottleneck, not the write path itself. You provision for compaction CPU, not write CPU.
- **Latency spikes.** A compaction that hits a large obsolete-key fraction (say 70% deletion or overwrite) triggers a *write stall* — the engine pauses accepting writes until compaction catches up. In Cassandra this manifests as "Hinted Handoff" pressure; in RocksDB it's the `write-stall` metric.

The LSM response to this is leveled compaction (what most modern engines default to) with tiered or size-tiered as the lower-amplification alternative. Leveled gives better read performance and space efficiency at the cost of the amplification described above. There's no free parameter space — you choose which axis you absorb the tax on.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC achieves non-blocking reads by maintaining multiple physical versions of each row. When a writer begins a transaction, it creates a new version of the rows it modifies — the old version remains visible to any reader whose snapshot started before the write committed. The reader gets a consistent view at its start time (a snapshot isolation level), while the writer proceeds independently. No locks are shared because they never contend on the same physical object.

The garbage this creates is dead row versions — tuples that are no longer visible to any active or future transaction because all snapshots that could have seen them are closed. PostgreSQL calls this accumulation *bloat*: the same logical row may exist as 5 physical copies in a heap page, each tagged with creation and expiry transaction IDs. When a page fills with dead tuples, queries scan more pages than necessary, and the index pointers to those dead versions remain until cleaned.

The cleanup mechanism is **VACUUM** (PostgreSQL) or equivalent garbage collectors (InnoDB's purge thread, Oracle's undo segment reuse). It identifies tuples whose `t_xmax` (the transaction that deleted/superseded them) is older than the oldest active transaction ID in the system, then marks their space reusable within the page. Left uncollected, bloat degrades cache efficiency and amplifies I/O on sequential scans until the table is vacuumed or autovacuum triggers.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration means decomposing a monolithic application into independently deployable services that communicate over a network, each owning its data and domain boundary. The main risks are:

1. **Distributed transaction complexity** — what was a single ACID transaction becomes a saga, and you lose atomicity. Compensation logic is never as clean as a rollback.

2. **Network as a new failure mode** — latency, timeouts, retry storms, partial failures. The monolith had function calls; now every call is an RPC that can fail in ways your code never had to handle before.

3. **Data consistency debt** — sharing a database defeats the purpose, but splitting it means joins disappear, constraints become eventual, and referential integrity becomes application-level responsibility.

4. **Operational blast radius** — N services means N deployments, N sets of logs, N monitoring dashboards, N things that can silently degrade without any single team noticing until a user reports it.

5. **Team coordination overhead** — the hard part isn't the code, it's the API contracts, versioning, backward compatibility, and the fact that every team's "small change" is now a coordinated release.

6. **Premature decomposition** — splitting by technical layer (frontend/backend/database) instead of bounded context (DDD), which gives you distributed monolith. Same coupling, more network calls.
