### Q01 [CHAT] — What is the difference between a monolithic and a microservices architecture? What are the main tradeoffs? Answer from your training knowledge.

Monolithic architecture runs the entire application as a single process. Microservices decompose it into independent services that communicate over a network.

**Tradeoffs:**

| Axis | Monolithic | Microservices |
|------|------------|---------------|
| Deployment | One artifact. Simple but any change ships the whole thing. | Independent deployments per service. Complex orchestration required. |
| Scaling | Scale the entire app even if only one function is hot. | Scale only the services that need it. Finer-grained resource control. |
| Team velocity | Fast early. Slows as codebase grows — merge conflicts, coordination overhead, hidden coupling. | Teams own services independently. Faster at scale, slower to start. |
| Testing | Single integration test surface. Easier end-to-end. | Contract testing per boundary. Much harder to validate cross-service correctness. |
| Failure isolation | One crash takes everything down. | A crash in one service can cascade if dependencies aren't resilient, or stay isolated if they are. |
| Data consistency | ACID transactions trivially available. | Distributed transactions are painful. Eventual consistency becomes the norm. |
| Cognitive load | One codebase to understand. Fewer moving parts. | You now have N codebases, N deployment pipelines, service mesh, observability, distributed tracing. |

The decision rule is temporal: start monolithic, extract services only when concrete constraints force it — a team boundary, a scaling hotspot that can't be solved with caching or reads, a deployment cycle that's blocking a team. Premature microservices add latency, complexity, and operational overhead without delivering the decoupling benefit because you don't yet know where the seams actually are.

### Q10 [CHAT] — What is the difference between symmetric and asymmetric encryption? When is each typically used? Answer from your training knowledge.

Symmetric encryption uses a single shared key for both encryption and decryption — fast, computationally cheap, good for bulk data. Asymmetric encryption uses a public/private key pair: the public key encrypts, the private key decrypts (or vice versa for signatures). It's orders of magnitude slower and used for key exchange, digital signatures, and authentication.

Symmetric is used for encrypting files, disk volumes, database columns, TLS session data — anywhere you're moving large amounts of data and both sides already share a secret. Asymmetric handles the handshake problem: establishing that shared secret without a pre-shared channel (TLS key exchange), proving identity (SSH, GPG signatures), and non-repudiation (code signing, certificates).

Real systems use hybrid: asymmetric to negotiate a session key, symmetric to encrypt the actual traffic.

### Q15 [CHAT] — Explain how Python's asyncio event loop runs many coroutines on a single thread, and what happens to the whole loop if one coroutine performs a long blocking CPU-bound computation. Answer from your training knowledge.

The event loop runs on a single thread using cooperative multitasking. Each coroutine yields control back to the loop at `await` points — typically I/O calls, sleeps, or explicit yields. The loop maintains a queue of ready coroutines and, on each iteration, picks one, runs it until it hits an await, then moves to the next. It's not preemptive — no coroutine is ever forcibly suspended mid-execution by the loop itself.

If one coroutine performs a long CPU-bound computation without any `await` — a tight loop, heavy matrix multiplication, regex backtracking — it never yields. The event loop doesn't get control back until that coroutine completes. Every other coroutine in the system stalls: pending network responses, timer callbacks, WebSocket heartbeats, all of them. The entire loop is frozen for the duration of the computation. For a 30-second CPU burn, that means 30 seconds of zero event processing.

The fix is `loop.run_in_executor()` — that offloads the CPU-bound work to a thread pool (or process pool) and returns an awaitable, so the event loop stays live.
