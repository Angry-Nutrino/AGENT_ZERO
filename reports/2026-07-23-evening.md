### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Three sources, each with a distinct cost profile.

**Where it comes from — the write cascade:**

1. **Memtable flush.** An in-memory sorted table (~4–64 MB) is frozen and written to disk as a new SSTable. That's the unavoidable first write — one copy of the data.

2. **Compaction.** The LSM-tree keeps writes fast by delaying sorting to merge time. Level-0 SSTables overlap arbitrarily, so a background compaction process reads N overlapping SSTables from level *i*, merges them, and writes one new SSTable to level *i+1*. A single key-value insert can be re-written through every level — the write amplification factor is roughly the number of levels × the overlap ratio. For a 7-level tree with 10× size ratios and tiered compaction, a single insert's data is re-written 7–15 times before it settles in the last level. Size-tiered compaction (Cassandra default) amplifies less than leveled compaction (RocksDB default, ~10–30×).

3. **WAL**. Every write hits the write-ahead log *before* the memtable. A separate sequential write, but it counts toward total bytes written to device.

**What it costs in practice:**

- **Device wear.** Consumer SSDs rated for 150–600 TBW die in months under LSM-heavy workloads. A leveled-compaction RocksDB ingesting 100 GB/day wears a 300 TBW drive in ~8 years — manageable for OLTP, catastrophic for high-ingestion (logging, metrics). Size-tiered compaction buys 2–3× more device life at the cost of read amplification.
- **Write stall.** When compaction can't keep up with ingest, the memtable fills and the writer thread blocks. This turns bursty WAF into visible latency spikes — p99 latency goes from 2 ms to 200+ ms until compaction catches up.
- **CPU + I/O contention.** Compaction shares the same I/O queue as the read path. On a single SSD, a compaction read of 2 GB pulls bandwidth from user queries. This is the primary reason production LSM deployments run compaction on dedicated threads with throttled I/O (RocksDB's `rate_limiter`).
- **Space amplification.** Old SSTables aren't deleted until compaction finishes. A compaction of 10 GB input writes a 1 GB output temporarily holding 11× the final data on disk. For tiered compaction with 3 fan-outs, steady-state space overhead is 20–30%.

The fundamental tradeoff: the LSM-tree converts random writes into sequential ones (performance win) by re-writing data multiple times (wear-and-CPU cost). Every compaction policy is a slider between write amplification and read amplification — you pick your poison.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each transaction a consistent snapshot of the database at transaction-start time, isolating it from concurrent writes. Readers never take locks, so writers never wait on them — the writer creates a new version of the modified row (tagged with the writer's transaction ID), while the reader's snapshot continues to see the old committed version. The reader is not blocked because there is nothing to block on.

The garbage is **dead row versions** — old versions of updated or deleted rows that no active snapshot can possibly reference anymore. Over time these accumulate in the table's heap or index pages, wasting space and bloating indexes, and must be reclaimed by a **vacuum** process (PostgreSQL's `VACUUM`, MySQL/InnoDB's purge thread). If vacuum does not keep up, you get table bloat and transaction-ID wraparound, which is how a config oversight can escalate into a system-wide outage.

### Q12 [DELIBERATE] — CLAUDE.md says a rare dropped os.replace in _save_memory 'self-heals on the next save'. From core_logic/crud.py: WHY is that true — what does every save write — and which exception class gets the retry-with-backoff on Windows?

**Self-heal reason:** `_save_memory` serializes the **entire in-RAM `self.memory` dict** with `json.dump(self.memory, f, indent=2, ensure_ascii=False)` (line 80) to a unique temp file, then does `os.replace` to swap it in. If `os.replace` fails silently mid-operation — a rare "dropped replace" — the live file is left unchanged and the in-RAM `self.memory` is still correct. The next caller that writes (e.g. `memorize_episode`, `log_system_episode`, `add_episodic_entry`, etc.) will write the **full current dict** again, overwriting the temp and attempting `os.replace` again. The in-memory state is the source of truth; no partial state was ever written to disk because the atomic write either fully replaced the target or didn't touch it. The dropped replace just delays the write, it doesn't lose data — the next save retries from the full dict.

**Exception class for retry-with-backoff on Windows:** `PermissionError` (line 95). The retry loop (lines 90-96) catches `PermissionError`, sleeps `0.02 * (attempt + 1)` seconds (20ms, 40ms, ... 200ms), and retries up to 10 attempts. This handles the transient Windows `ERROR_ACCESS_DENIED / SHARING_VIOLATION` that occurs when a reader (e.g. a harness `python_repl`) has the file open during the swap.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application—where all functionality lives in a single codebase and deployment unit—into independently deployable services that communicate over a network, each owning its own data and domain boundary.

Main risks:

1. **Network as a new failure domain** — A monolith makes in-process calls that either succeed or fail. Services introduce latency, partial failures, timeouts, retry storms, and network partitions. Most teams underestimate how much of their code needs to become resilient rather than just functional.

2. **Distributed data consistency** — The monolith wraps everything in a single ACID transaction. After splitting, a single user request spans multiple services and databases. You now need sagas, eventual consistency, or two-phase commit—each with sharp tradeoffs. Teams often handwave this and end up with inconsistent state in production.

3. **Coupling that isn't visible in the code** — Schema sharing, implicit ordering of operations, shared libraries that version-drift, synchronous call chains that create hidden dependencies. The monolith's coupling is explicit; distributed coupling is invisible until it breaks.

4. **Operational complexity explosion** — One deployable becomes N deployables. Monitoring, logging correlation, deployment coordination, secret management, CI/CD pipelines all multiply. The team needs infrastructure maturity that didn't exist before.

5. **Premature decomposition** — Splitting before the bounded contexts are understood creates "distributed monoliths" that have all the operational cost of microservices with none of the autonomy benefit. The services can't be deployed independently because they're still coupled at the domain level.

The core tension: microservices solve organizational scaling problems (teams moving independently), not technical problems. Purely technical migrations that don't have a team-structure driver tend to net-negative in complexity cost.
