### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Two strategies for handling concurrent access to shared data, distinguished by when they detect and resolve conflicts.

**Pessimistic concurrency** assumes conflicts are likely and locks the resource before any operation begins — either with a read lock (shared, multiple readers allowed) or a write lock (exclusive, no concurrent readers or writers). The transaction acquires the lock upfront, holds it for the duration, and releases it after commit or rollback. This guarantees serializability but risks contention, deadlock, and reduced throughput when many transactions compete for the same resource. Correct choice when contention is high, writes are frequent relative to reads, data integrity cost of a conflict exceeds the latency cost of holding a lock, or when retries are expensive (e.g., last-seat booking for a flight, inventory decrement for a popular item).

**Optimistic concurrency** assumes conflicts are rare and lets transactions proceed without locking. On commit, the system validates that no serialization anomaly would occur — typically by checking a version number or timestamp on each data item, only aborting if the version changed since the transaction read it. No locks held, no deadlocks, maximum throughput under low contention. Correct choice when contention is low, conflicts are genuinely rare (most reads, few writes), operations are short enough that retries are cheap, or the workload is read-heavy with infrequent writes — think analytics dashboards, document collaboration where same-page edits are uncommon, or a wiki page edited by a small team.

The same system often uses both — pessimistic for high-contention resources (account balance), optimistic for everything else.

### Q04 [DELIBERATE] — In core_logic/crud.py, update_discourse_state merges new entries with the existing list. HOW does it deduplicate the entries, and what ORDER does the resulting list keep?

**Dedup**: Case-insensitive string equality via a `set()` keyed on `e.lower()`. The merge iterates over `new + existing` — entries from `new` (the incoming entities) are processed first. If an entity in `existing` matches one that already appears in `new` (same lowercase key), it is skipped entirely, so the *first occurrence in traversal order* wins. **Order**: Most-recent-first. Because `new` is concatenated before `existing` in the iteration, and duplicates are removed on first-seen, the resulting list has all the new entities at the front (preserving their input order within the batch), followed by any remaining existing entities that are not duplicates of the new ones. The list is then truncated to `cap` (default 8). Since no re-sorting is done, stale topics that weren't re-mentioned simply drift rightward and fall off the cap boundary.

So effectively: prepend uniques, keep existing uniques in their prior order, cap the tail.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Processes have isolated address spaces — each gets its own heap, stack, code, data, file descriptors, and page tables. Threads share the address space of their parent process: same heap, same code/data, same open files. What threads *don't* share: their own stack, register set, program counter, and signal mask. Context-switching between two threads in the same process is cheaper than switching between two processes because the TLB doesn't need flushing and the page table doesn't change.

On multiprocessing vs threading in Python specifically, the GIL is the deciding factor. Threading is cooperative — the GIL allows only one thread to execute Python bytecode at a time, so CPU-bound work sees zero parallel speedup and can actually regress due to contention. Multiprocessing spawns separate interpreter processes, each with its own GIL, giving true parallel execution across cores.

Use **threading** when: I/O latency is the bottleneck (network calls, disk reads, database queries). The GIL is released during blocking I/O syscalls, so threads overlap waiting time efficiently. Use **multiprocessing** when: CPU-bound numerical computation, tight loops, or any work that keeps the GIL hot. You get linear speedup up to core count.

Watch the overhead: multiprocessing means serializing arguments across process boundaries (pickle), separate memory means inter-process communication via queues/pipes/pipes instead of shared variables, and process startup is significantly heavier than thread creation. A common pattern is a hybrid — multiprocessing for worker pools doing CPU work, threading within each worker for concurrent I/O on subtasks.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the response time at the high percentiles — p99 means 99 out of 100 requests complete within that time, p999 within 999 out of 1000. The average hides this: it can look fine while 1% of users wait 10x longer, and in a distributed system those 1% hit *every* user because a single request fans out to dozens of services. A user's experience is the **max** of all sub-request latencies, not the average. If your p99 is 500ms and you fan out to 50 services, the chance at least one of them is slow is 1 - (0.99^50) ≈ 39.5% of requests — nearly half your users see tail delay.

One concrete technique: **hedged requests**. Send the same request to two replicas simultaneously, use whichever responds first, cancel the other. This turns p99 into the min of two independent p99s — drops effective tail latency to roughly p99 * (1 - sqrt(0.01)) ≈ p99 * 0.9 for uncorrelated servers, and more improvement with higher variance. The cost is ~2x load on the slow path, which you accommodate by only hedging after a short wait (e.g., p50 timeout) rather than from the start.
