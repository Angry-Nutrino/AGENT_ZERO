### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design: data is written multiple times as it moves down the leveled structure. A single insert is written once to the memtable, flushed to an SSTable at L0, then compacted into L1, L2, and so on. Each compaction re-reads old SSTables, merges them with new ones, and writes the merged result back — the same bytes get rewritten at every level.

The practical cost is measured in three dimensions:

1. **Disk write endurance** — On SSDs with limited P/E cycles, a write amplification factor of 10x means your drive wears out 10x faster than the application-level write rate suggests. For a consumer NVMe rated at 300 TBW, writing 100 GB/day of real data translates to 1 TB/day of actual writes — the drive dies in under a year.

2. **Write latency tail** — Compaction runs in the background, consuming I/O bandwidth. When a compaction hits the same disk shard as a user write, the user write stalls. This is why production LSM-trees (RocksDB, LevelDB) have explicit compaction throttling and rate limiters: without them, P99 write latency spikes unpredictably.

3. **CPU and memory pressure** — Compaction isn't free compute. Merging sorted runs requires comparison overhead, and triggering multiple simultaneous compactions on a busy node can starve the query path of CPU. This is the tradeoff Kleppmann describes: LSM-trees trade write amplification for lower read amplification compared to B-trees, and the real tuning work is finding the balance.

The canonical number in the literature: a typical leveled LSM with 10x size ratio per tier has a write amplification factor of roughly `(L-1) * T` where L is the number of levels and T is the growth factor. For a 3-level LSM with 10x growth, that's ~20x write amplification at steady state. Tiered (size-tiered) compaction like Cassandra's default is worse — closer to O(N) in the worst case — which is why Cassandra compactions are the single most common operational pain point reported.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works by giving each transaction a snapshot of the database at a point in time — typically the transaction's start timestamp or the most recent committed version before it. When a writer updates a row, it doesn't overwrite the existing value. Instead, it creates a new version of that row tagged with the writer's transaction ID. The old version remains accessible to any reader whose snapshot predates the update. The reader reads the version that was current at its snapshot time, which by definition is not the one being written right now, so there's no lock contention.

The garbage this creates is dead row versions — tuples that are no longer visible to any active or future transaction because they've been superseded and the transactions that could have seen them are all finished. This accumulates in the table's storage pages as bloat, inflating the data footprint and degrading index scan performance because the engine has to skip over invisible versions. Cleaning it up is the job of a garbage collector or vacuum process: it scans pages, identifies versions that no transaction can ever read again, and reclaims that space for reuse.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable, loosely coupled services that communicate over a network, each owning its own data and business capability.

Main risks when splitting a monolith:

**Distributed systems complexity** — Network latency, partial failure, and timeout handling replace what were in-process function calls. You introduce retry storms, cascading failures, and the need for circuit breakers, bulkheads, and distributed tracing where none existed.

**Data consistency** — ACID transactions across services don't exist without a distributed transaction coordinator (which you should avoid). You shift to eventual consistency, sagas, and compensating transactions. Teams that skip this mental model shift corrupt data silently.

**Service boundaries get wrong** — The most common failure. Slicing by technical layer (controllers, services, repositories) instead of business capability creates chatty services that need to call each other for every operation, turning the monolith's tight coupling into network-coupled chaos that's slower and harder to debug than the original.

**Operational blast radius** — A query in service A that backfills a table without an index now degrades service B, C, and D's response times because they share the same database. The monolith's shared infrastructure doesn't automatically become independent — you have to unbundle storage, caches, and queues deliberately, and each unbundling is a migration with its own risk of data loss or downtime.

**Organizational Conway's Law trap** — If the team structure doesn't match the service boundaries, you end up with distributed monolith: a microservices tax with none of the benefits. Teams need clear ownership of entire services, including deployment and on-call, or coordination overhead kills the velocity microservices were supposed to unlock.
