### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design choice to defer and batch writes. When you insert a row, it's written to an in-memory memtable, then flushed to disk as an immutable SSTable. But that's not the end — background compaction processes repeatedly read, merge, and rewrite SSTables across multiple levels to maintain a sorted structure and reclaim space from tombstones and stale records. Each write to the storage engine is therefore multiplied: the initial write to the memtable log (write-ahead log), the flush write, then potentially multiple compaction reads and writes as the data cascades through levels.

The cost is measured as the write amplification factor — the ratio of bytes written to disk versus bytes of new data ingested. Level-based compaction (the default in LevelDB/RocksDB) typically achieves factors between 10–30x depending on level sizes and fan-out. That means every byte you insert causes tens of bytes of disk I/O. Size-tiered compaction (Cassandra's default) can be worse because entire tiers get rewritten at once. The practical costs are:

- **Wear on SSDs** — NAND flash has finite program/erase cycles. A consumer SSD rated for 300 TBW becomes a bottleneck far sooner when compaction inflates writes by 20x.
- **Write latency spikes** — Major compactions consume CPU and I/O bandwidth, causing stalls for incoming writes. RocksDB mitigates this with rate limiters, but the variance remains.
- **Storage throughput overhead** — A significant fraction of disk bandwidth is spent rewriting data rather than serving reads or new writes. On databases ingesting, say, 100 MB/s of writes, compaction can occupy the entire I/O budget of a single NVMe drive.
- **CPU cost** — Merge-sorting and decompressing/recompressing SSTables during compaction burns cycles, especially under heavy write loads.

The tradeoff is that this amplification buys read efficiency — one binary search per level, usually within a few disk seeks — and bounded space amplification (~10–30%) compared to B-trees that suffer write amplification mostly from the log-structured nature at the page level (4x–10x) but have lower background overhead. The LSM design is optimal when writes dominate and you can tolerate latency spikes in exchange for sustained throughput, which is why Kafka's log-segmented storage and RocksDB (used inside Kafka Streams, TiDB, MyRocks) both lean into it.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each transaction a consistent snapshot of the database at a point in time (snapshot isolation). When a writer begins modifying a row, it creates a new version of that row rather than overwriting the existing one. The old version remains visible to any reader whose snapshot predates the writer's commit. Readers never need locks — they simply read the version that corresponds to their snapshot's timestamp or transaction ID. Writers don't block readers because each version is immutable and the reader's snapshot pointer hasn't moved.

The garbage is **obsolete row versions** — versions that are no longer visible to any active or future transaction (i.e., no open snapshot references them anymore). These accumulate as old versions of updated or deleted rows. If not cleaned up, they bloat storage, degrade index scan performance, and increase memory pressure from version chains. The cleanup mechanism goes by different names: PostgreSQL's VACUUM (or autovacuum), MySQL/InnoDB's purge thread, Oracle's undo retention management. All of them identify versions whose visibility horizon has passed (the oldest active transaction's snapshot no longer needs them) and reclaim the space. Failure to clean up is a common source of transaction ID wraparound (PostgreSQL) or runaway table bloat.

**Shared three-step atomic-write pattern** (adopted by every file listed above):

1. **`tempfile.mkstemp(prefix="...", suffix=".tmp")`** — create a unique temporary file in the same directory (unique name per call so concurrent writers don't interleave).
2. **`f.flush()` → `os.fsync(f.fileno())`** — force the OS to flush the write buffer to disk, so no data lingers in the page cache on a crash.
3. **`os.replace(tmp, target_path)`** — atomically swap the temp file into place. On POSIX this is a metadata-only rename (always atomic). On NTFS it is atomic for same-volume moves, but **raises `PermissionError` when another handle has the target open**.

---

**Why `crud._save_memory` retries on Windows:**

`os.replace` on Windows raises `PermissionError` (`ERROR_ACCESS_DENIED` / `SHARING_VIOLATION`) when another process holds an open handle to the target file — e.g., a harness `python_repl` concurrently reading `memory.json`. The contention window is transient (readers hold the handle for milliseconds). Rather than silently dropping the write, `_save_memory` retries up to **10 times** with exponential backoff (`0.02s × (attempt + 1)` per iteration). This was added after a stress test with 12 concurrent threads showed that a bare `os.replace` lost nearly all writes under concurrent reads on Windows. If all 10 attempts fail, the method logs an error and returns — the loss is limited to the current write, and the next save self-heals because every save writes the full in-RAM dict.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application — one codebase, one deployment unit — into a set of independently deployable services, each owning its own data, domain, and lifecycle. The goal is to decouple delivery, scale components independently, and replace big-bang releases with continuous, isolated changes.

The main risks:

- **Distributed data consistency** — the monolith's ACID transactions become distributed sagas. Without careful design, you trade a single database for eventual-consistency failures, partial writes, and compensating rollbacks that are far harder to debug.
- **Network as a new failure mode** — local function calls become remote calls with latency, timeouts, retries, and cascading failures. Circuit breakers, bulkheads, and observability become table stakes, not nice-to-haves.
- **Coupling that doesn't go away** — teams often split along technical layers (frontend vs. backend vs. DB) instead of domain boundaries, producing distributed monoliths: independent deployments that still need coordinated releases because of shared schemas, shared databases, or chatty inter-service calls.
- **Testing complexity** — end-to-end tests now require orchestrating multiple services, their data stores, and their network conditions. The combinatorial explosion of states makes deterministic test coverage impossible without contract testing and consumer-driven contracts.
- **Observability debt** — you go from one application log to distributed traces, metrics per service, and structured logging. If tracing, metrics, and logging aren't unified *before* or *during* migration, debugging a latency spike becomes a hunting expedition across ten services.
- **Team coordination overhead** — API versioning, backward compatibility, and ownership boundaries create negotiation tax. The organizational communication cost often exceeds the technical one (Conway's law cuts both ways: your architecture mirrors your org chart — if the chart isn't aligned, neither is the system).

**Design rule — `threading.Lock` vs `asyncio.Lock`:**

`threading.Lock` is used whenever the protected resource is accessed **across a thread boundary** — a background thread and the async main thread may contend for it. Examples: `memorize_episode` runs on a background thread and needs the vault lock; `_ledger_append` is called from concurrent async shadow verdicts but uses synchronous file I/O; voice processing happens on its own thread; the RAG builder can be triggered by a startup thread racing with `EnvironmentWatcher`.

`asyncio.Lock` is used only when **every accessor is an async coroutine running on the same event loop** — no thread crossing. Currently that's two cases in the codebase: `self._miniLM_lock` (serializing `self.miniLM.encode()` calls from the main async path and the background `memorize_episode` thread — a special case because the lock itself is `asyncio.Lock` wrapped around a synchronous call, covered by Brief 00), and the per-path write lock in `resource_ledger.py` (purely async, held only during `await mcp_client.call()`).
