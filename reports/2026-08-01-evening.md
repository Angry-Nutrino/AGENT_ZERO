### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in an LSM-tree is the ratio between the logical writes the application issues and the physical bytes actually written to storage. The design buys cheap sequential writes by batching random updates in a memtable, then constantly reorganizing the tree in the background — and every reorganization re-writes data that was already on disk. That re-writing is the amplifier.

**Where it comes from**

1. **The durability write.** Every insert first appends to the write-ahead log — sequential, partially amortized by group commit, but still a physical device write (and fsync, if durability demands it) before anything else.

2. **Memtable flush.** When the in-memory buffer fills, its entire contents are written to disk as an SSTable. That's the first physical write of the data.

3. **Compaction — the dominant term.** Compaction is a merge: it reads SSTables, merges them with overlapping SSTables at the next level, and writes new SSTables. Every record that participates is re-read and re-written. In leveled compaction (LevelDB/RocksDB default), each level is ~T× larger than the previous, T typically 10. A record descends one level at a time and is rewritten on each descent — crossing a 4–5 level tree means being physically written roughly T× per level, which is where the classic 10–30× figure comes from. It gets worse because a merge isn't 1:1: a source file's key range may overlap several files at the next level, so the merged output is larger than the input. That fan-out compounds the multiplier.

4. **Tiered variant.** Size-tiered compaction (Cassandra, HBase, RocksDB universal) accumulates same-sized tables in a tier and merges them in bursts. Common-case write amplification is lower — roughly 1–5× — but the cost shifts into space amplification: disk occupancy can temporarily be multiples of live data size.

**What it costs in practice**

- **Disk bandwidth as a hidden tax.** Compaction is invisible throughput work. A workload logically writing 100 MB/s can demand 1–3 GB/s of physical bandwidth. This, not the application's write rate, is usually the ceiling on sustained throughput.
- **SSD endurance.** NAND wears on program/erase cycles. A 1 TB TLC drive rated ~600 TBW behind a 10× amplifier gives ~60 TB of logical writes before rated lifetime — months, not years, for a write-heavy service. And the flash translation layer adds its own internal amplification on top, especially as the drive fills.
- **Latency spikes and write stalls.** Compaction contends with foreground I/O. When the write rate outruns compaction, the backlog grows until the engine applies backpressure — RocksDB's pending-compaction write stall, Cassandra's compaction pressure — producing p99 spikes and sometimes complete write pauses. This is the cost operators feel first: steady-state averages look fine, tail latency breaks the SLO.
- **CPU.** Each merge is a sort, a checksum, and usually a compress/decompress cycle. Since data is compressed at rest, every rewrite decompresses old data, merges it, and recompresses the output. The same record pays that CPU repeatedly across levels.
- **Space amplification.** Old and new SSTables coexist during a merge. A healthy tree runs 1.1–1.5× live data; a misconfigured or overloaded one balloons.

The structural point: you're always picking along the read/write/space amplification triangle. B-trees write each page once in place and pay random I/O plus fragmentation; LSM-trees convert writes to sequential but pay the rewriter multiplier. The correct choice depends on whether your binding constraint is random-write cost or total bytes written — and on flash, total bytes written literally consumes the device's life.

The knobs that control it: level size ratio T (higher T → fewer levels, less rewriting, heavier per-merge work), compression (fewer bytes written, more CPU per pass), compaction rate-limiting and parallelism (background work vs. foreground latency), and tiered vs. leveled selection by workload.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC replaces update-in-place with versioned rows. When a transaction modifies a row, the database doesn't overwrite it — it writes a new version and marks the old one expired. Each version carries metadata for visibility judgment: PostgreSQL tags tuples with xmin/xmax (creating transaction / deleting transaction); InnoDB keeps a transaction ID plus a chain back into the undo log that holds the prior image; Oracle stores before-images in rollback segments.

**Why readers don't block writers.** A reader takes a snapshot at its first statement (or transaction start, depending on isolation level) and then decides visibility purely by comparison — is this version's creator committed before my snapshot, and not already expired? No shared lock is ever requested on the row. A writer only takes a short-lived lock to install its new version header while the write is in flight; it never mutates the bytes a concurrent reader is looking at. So the reader keeps reading the old version even after the writer commits, and the writer commits without waiting for the reader to finish. That's the "readers don't block writers, writers don't block readers" property — the entire reader/writer conflict class disappears. Note the asymmetry: write-write conflicts still require row locks or optimistic conflict detection. MVCC only eliminates the read-versus-write half.

**The garbage it creates.** Every superseded version becomes garbage the moment no active snapshot can reach it, and until then it sits there:
- **Dead tuples / non-current versions** — PostgreSQL heap pages and indexes retain them; the table and indexes bloat, and every scan pays I/O walking dead index entries.
- **Undo / rollback records** — InnoDB's undo log and Oracle's rollback segments must retain before-images as long as any active transaction might need to roll back or read an old version through the chain.
- **Version chains** — under heavy updates of the same row, chains grow long and old-version reads get slower.

**How it's cleaned.** The database computes a safe horizon — the oldest active snapshot across all connections. Anything older is unreachable and reclaimable. PostgreSQL runs VACUUM/autovacuum to remove dead tuples, free the space for reuse, and advance the transaction-id horizon so wraparound (a hard failure if vacuum is starved) never occurs. InnoDB runs a background purge thread that discards undo records whose versions no snapshot can see. The classic operational hazard: a single long-running transaction pins the horizon forward, freezing cleanup and letting bloat accumulate unboundedly until it commits — the mechanism is sound, but it converts a locks problem into a reclamation problem you must actually run the vacuum for.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a running monolithic application into a set of smaller, independently deployable services that communicate over a network — usually via HTTP/REST, messaging, or gRPC — and are owned by separate teams.

The main risks are, in rough order of how often they actually bite:

1. **Distributed systems complexity.** You trade one in-process function call for a network call. That brings latency, partial failure, retries, timeouts, and the need for circuit breakers and bulkheads. The monolith's biggest hidden advantage — atomic, reliable, single-transaction behavior — is gone.

2. **Data integrity and transaction boundaries.** The classic killer. ACID transactions don't span services. You now need sagas, outbox patterns, idempotency keys, and a hard decision about which service owns which data. Splitting a shared database is where migrations stall and where data gets silently corrupted if you're sloppy.

3. **Boundary mistakes.** If you split at the wrong seams — services that share too much data or too many synchronous calls — you get a distributed monolith. Same pain as a monolith, plus network failure modes. This is the most common failure outcome.

4. **Operational overhead.** You now run N distributed systems instead of one: logging is scattered, tracing requires correlation IDs end-to-end, deployment is per-service, and you need containerization, orchestration, CI/CD per service, observability (metrics, logs, traces), environment parity. Teams that aren't already strong at DevOps get buried.

5. **Team and organizational coupling.** Conway's Law cuts both ways. If your org structure doesn't match your service boundaries, you get coordination overhead, ownership ambiguity, and services nobody wants to touch. A migration is as much an org change as a technical one.

6. **Incremental migration traps.** Strangler-fig is the right pattern, but the trap is running the monolith and services in parallel for too long — dual code paths, dual data writes, sync bridges between old and new, and a system that is both a monolith and a distributed system at the same time. The migration implicitly never ends.

7. **Latency and performance regression.** Network round-trips add milliseconds per hop. Chatty service-to-service calls — the ones that were cheap in-process — become visible bottlenecks. Need to measure before, not after.

8. **Versioning and contract drift.** Independent deployability means independent evolution, which means versioned APIs, backward compatibility discipline, and coordinated consumer-driven contracts. Without that, services drift and break each other in production.

The honest summary: a microservices migration is not primarily a code refactor. It's a bet that the operational and organizational maturity you have (or will build) exceeds the cost of the added distributed-systems complexity. For most teams, that bet only pays off at a scale where the monolith is genuinely bottlenecking deployment frequency, team autonomy, or independent scaling — and even then, the right move is usually to start with one well-chosen service carved out via the strangler pattern, not a big-bang rewrite.

**Design rule — threading.Lock vs asyncio.Lock:**

`threading.Lock` guards shared state that is touched from at least one thread *other than* the event loop thread — background threads, worker threads, or sync call paths where an `await` is impossible. It serializes real OS-thread concurrency, so the critical section must never contain an `await`.

`asyncio.Lock` guards state only ever touched on the event loop, but across a suspension point — the holder needs to `await` inside the critical section (e.g. `miniLM.encode()`, an MCP call, a network round-trip). It is cooperative: only correct within a single thread's event loop.

The pattern in practice: every threading.Lock here protects memory shared with the background thread (`memorize_episode`), a watcher thread, or a TTS/IO thread; every asyncio.Lock protects event-loop-only state around an await boundary. Mixing them up — using a `threading.Lock` where the holder must await, or an `asyncio.Lock` where a second thread participates — is the race.

**agent.py holds the most (2), and what each protects:**

- `self._vault_lock` (line 436) — guards **the long-term fact vault** against concurrent writes from `memorize_episode`.
