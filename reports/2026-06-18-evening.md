### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Conceptually clear. Let me give you the engineering reality, not the textbook version.

**Where it comes from:** Every insert doesn't write once — it participates in a cascade. Write to the in-memory memtable (fast, no amplification yet). Memtable fills, flushes to L0 as an SST file (amplification factor ~1 for that write). Then compaction merges overlapping L0 files into L1, reads and rewrites every key involved. That key moves through tier after tier — each compaction that touches it is a full read+write cycle, even if only one byte changed. In LevelDB-style leveled compaction, a key written once gets rewritten ~10-15 times over its lifetime as it sinks from L0 through L6.

**What it costs in practice:**
- **Disk write bandwidth** — the dominant bottleneck on NVMe SSDs. A workload doing 10 MB/s of logical writes can generate 150-200 MB/s of actual disk I/O. On consumer SSDs with 500-700 MB/s sustained write, that caps your insert throughput far before CPU or RAM.
- **SSD endurance** — NAND cells have write budgets (TBW). Write amplification multiplies the wear. A 1 TB drive with 600 TBW rating, running a write-amplified database 24/7 at high load, can degrade cells in months instead of years.
- **Tail latency spikes** — compaction storms. The write path is smooth until a compaction kicks in, saturating disk bandwidth and starving foreground writes. Readers see P99 latency jump 10x until compaction finishes.
- **Cache pollution** — compaction reads data the working set doesn't need, evicting hot keys from OS page cache. Then reads that should be fast hit disk.

The engineering lever to pull is compaction strategy — leveled vs. size-tiered, compression choice, per-tier SST size tuning. Leveled minimizes space amplification at the cost of write amplification; size-tiered inverts the tradeoff. Most real deployments choose the variant whose pain they can absorb.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC lets each read see a consistent snapshot of the database as of when the transaction started, rather than the current live state. When a writer begins modifying a row, it creates a new version of that row with its transaction ID attached; existing readers still see the old version because row visibility is resolved by comparing the reader's snapshot timestamp against the row's creation/deletion timestamps. The writer's new version is not visible to any concurrent snapshot, so the reader never waits for a lock — isolation happens through versioning, not contention.

The garbage this creates is dead row versions — also called "ghost" or "expired" tuples — that are no longer visible to any active transaction. They accumulate in the data pages and in the indexes that still point to them. A vacuum/compaction process must scan for these versions, reclaim their storage space, and rebuild affected index entries. Until it runs, the table bloats, index scans degrade, and write amplification rises because every update that touches a hot row leaves an uncollected corpse behind.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application — where all functionality runs in a single deployable unit sharing a database and memory space — into a set of independently deployable services that communicate over a network, each owning its own data and domain boundary.

The main risks when splitting a monolith into independent services are:

1. **Network as a new failure domain** — In-process method calls in a monolith either succeed or throw. Network calls add latency, partial failure, timeout, retry storms, and cascading failures. You now need circuit breakers, bulkheads, retry policies with backoff, and graceful degradation — code that had no reason to exist before.

2. **Distributed data consistency** — A monolith uses a single ACID transaction across any set of tables. After the split, each service owns its database. A single business operation that spans services — place order, transfer funds, onboard user — now requires sagas, eventual consistency, or two-phase commit. You've traded local atomicity for distributed coordination complexity.

3. **Latency budget blown** — What was a 5ms operation now makes 3-5 network round trips. Service-to-service call chains that aren't designed for asynchrony turn synchronous RPC into waterfall latency. Observability — distributed tracing, correlation IDs, metrics aggregation — becomes a prerequisite, not a nice-to-have.

4. **Wrong boundaries** — If services are split by technical layer (frontend service, backend service, database service) instead of business domain, you get distributed big ball of mud: every change touches 3-4 services, deploys require coordination, and the coupling you escaped in the monolith reappears over the wire. This is the most common failure mode.

5. **Data ownership collisions** — After the split, two services often both need the same data. The natural response — share the database — recreates the coupling you removed. The correct response — define authoritative owners, accept eventual consistency for reads, and duplicate data through event streams — requires organizational discipline most teams don't have at the start of the migration.

6. **Testing complexity explosion** — Unit tests on individual services are cheap. Integration tests that exercise service-to-service contracts are slow and brittle. End-to-end tests across the full distributed system are nearly impossible to run deterministically. You need contract testing (Pact-like), consumer-driven contracts, and canary deploys because your test coverage drops dramatically compared to the monolith.

7. **Operational surface area increase** — One monolith deployment turns into N service deployments with N databases, N log streams, N monitoring dashboards, N health endpoints. If the team hasn't invested in CI/CD, container orchestration, centralized logging, and metrics aggregation before the migration, the operational overhead drowns the team.

8. **Organizational impedance mismatch** — Conway's law applies here directly. If you split into microservices but keep the same single team structure, the services end up coupled because the same group owns multiple services. The correct structure is one team per service boundary — which requires organizational restructuring most companies attempt last, not first.
