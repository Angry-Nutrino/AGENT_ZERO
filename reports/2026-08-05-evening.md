### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in an LSM-tree is the ratio of bytes actually written to storage versus bytes of new data ingested. It comes from three compounding sources, in order of severity:

1. **Compaction is multiplicative, not additive.** Every level gets rewritten multiple times as data cascades downward. A write that lands in L0 may pass through every level before it's tombstoned or read as a final value. With level-based compaction and a per-level size ratio of 10, a byte of data is rewritten roughly once per level per full cascade — so total write amplification scales with the *number of levels*, which grows logarithmically with dataset size. Size-tiered compaction is worse: a file in a tier can be merged into a larger file that then gets merged again, compounding the cost.

2. **Every SSTable rewrite is a full-file rewrite.** Compaction doesn't merge individual key-value pairs in place — it reads entire sorted runs and writes entirely new SSTables. Even if only 1% of the keys in a file changed, the whole file is serialized and flushed again. The larger the SSTable, the more dead weight per compaction.

3. **WAL and memtable flushes add a constant floor.** Every write hits the write-ahead log first (one sequential append if batched well), then the memtable is eventually flushed to an L0 SSTable. That's the unavoidable baseline — roughly 1x to 2x write amplification before compaction even starts.

**What it costs in practice:**

- **SSD endurance.** NAND cells have finite program/erase cycles. At write amplification of 10–30x, a drive rated for 1,000 TBW effectively becomes a 30–100 TBW drive for *useful* data. On high-ingest workloads, this can shave years off a drive's lifespan. This is the cost that bites first in production.
- **I/O bandwidth.** Compaction competes with foreground reads and writes for the same disk bandwidth. On a saturated disk, a background compaction can add significant latency spikes to user queries — the classic LSM "compaction stall."
- **CPU cost.** Compaction isn't just I/O; it's merge-sorting, checksumming, and re-serializing millions of keys. Higher amplification means more CPU burn, which on a CPU-bound node raises p99 latency even when disk isn't the bottleneck.
- **Operational overhead.** More bytes written means more thermal load, more power draw, and faster drive replacement cycles in datacenter fleets. At fleet scale, this becomes a real CapEx line item.

**Mitigations in practice:**

- **Leveled compaction** with a size ratio tuned to the workload — typically 10x, giving ~10–30x write amplification but good read performance and space amplification.
- **Size-tiered compaction (STCS)** for write-heavy workloads — higher write amplification is traded for lower write *latency* and better ingest throughput.
- **Compression** before writing SSTables — reduces bytes-on-disk but doesn't reduce the number of bytes moved during compaction.
- **Tombstone and TTL awareness** in compaction heuristics to drop dead data earlier, avoiding unnecessary cascades.
- **Blob storage separation** (e.g., RocksDB's BlobDB) to keep large values out of the compaction stream entirely.

The bottom line: write amplification is the price LSM-trees pay for turning random writes into sequential appends. The design wins on write *latency* and ingest throughput, but the deferred cost shows up in endurance, bandwidth, and CPU over the life of the data. Tuning compaction is trading those three against each other — there is no free lunch.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC is the mechanism that lets readers and writers not stand on each other's toes, and it works by never mutating a row in place. Every write creates a new version of the row with the writer's transaction ID attached; the old version stays in place for anyone who began their read before the write committed. A reader's snapshot is just a "valid version" filter — it knows which transactions had committed by the time it started, so it walks the version chain and picks the newest row version whose transaction committed before that cutoff. The writer never locks the page the reader is touching, and the reader never blocks because the data it needs literally still exists. That's the trade: you trade lock contention for storage and housekeeping.

The garbage is two kinds:

1. **Dead row versions** — the superseded versions that no active snapshot will ever read again. When a transaction updates or deletes a row, the old version is orphaned (for updates) or becomes a tombstone (for deletes). They can't be physically removed immediately because some long-running reader's snapshot might still need them, so they linger in pages.

2. **Transaction ID bloat** — every transaction gets an ID, and old row versions document "this version was created by transaction N" (and sometimes "deleted by transaction M"). The system needs to know which transaction IDs are still old enough to matter, and the per-transaction status data grows. In PostgreSQL the culprit is a counter that must not wrap around; if it does, old IDs become "future" IDs and current rows look invisible — that's the famous transaction-ID wraparound problem. In MySQL/InnoDB the same concept is the history list, and MVCC garbage is called "purge" there.

The cleanup job is vacuum (Postgres) or purge (InnoDB). It scans for row versions no live snapshot can reach, reclaims the space, and updates the transaction bookkeeping so the system can keep issuing new IDs. The difficulty is the long-running transaction: as long as one old snapshot is alive, vacuum cannot reclaim versions newer than that snapshot's start, so the table bloat grows, index bloat grows, query performance degrades — all because one transaction refused to finish.

The practical consequence: MVCC's design is brilliant for concurrency, but it makes database size and performance a function of your longest-running transaction and your write volume, not just your live data. That's why "bloat" is a metric worth watching, and why an app that keeps a transaction open forever will make the database physically swell underneath it.

3. **Atomic replace** — `os.replace(tmp, self.filepath)` inside a 10-attempt `PermissionError` retry loop with linear backoff (`0.02 * (attempt + 1)`). The replace is atomic on both Windows and POSIX — a crash mid-write can never truncate the live file; worst case is an orphan `.tmp`.

**(3) Why a permanently-dropped replace still self-heals on the next save:** because every save writes the FULL in-RAM dict, not a delta. The authoritative state is `self.memory` in RAM; the disk file is only a serialized snapshot of it. If all 10 retries exhaust against a held handle, the write is dropped — but nothing was lost from RAM, and the live file merely remains one snapshot stale. The next save serializes the entire current dict — which contains all changes from the dropped write — so the deferred snapshot content reaches disk then. Durability is delayed, never destroyed. (The `slog.error` at line 98 records that a snapshot was dropped, but data integrity is preserved by the full-dict rewrite model.)

**(4) What `_load_memory` does BEFORE falling back to defaults** (`crud.py:34–46`): on `JSONDecodeError` it **backs up the corrupt file first** — `shutil.copy2(self.filepath, f"{self.filepath}.corrupt-{time.strftime('%Y%m%d-%H%M%S')}")` — logs a warning via `slog`, and only then returns `_create_default_memory()`. The copy failure is swallowed (the fallback still proceeds), but in the normal path the timestamped backup ensures the next `_save_memory` cannot overwrite and permanently destroy the recoverable data contained in the corrupt file.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of restructuring a monolithic application — where every feature lives in one codebase, one deployable unit, usually sharing one database — into a set of independently deployable services, each owning its own data and lifecycle and communicating over the network. The goal isn't smaller code; it's independent deployability, independent scaling, and fault isolation.

The main risks, in order of how often they actually sink a migration:

**1. Distributed systems complexity.** Function calls become network calls. The network is not reliable — you inherit latency, partial failure, timeouts, retries, and the idempotency problem. This is the Kleppmann terrain you're reading: you cannot design for success, only for failure. What was a stack trace is now a mystery spanning five services.

**2. Data consistency.** A monolith wraps a workflow in one ACID transaction. Split across services, that's gone. Your options — sagas, event-driven eventual consistency, outbox patterns — all have their own failure modes. The single most common mistake: services share a database, which recreates the coupling you were escaping while adding network overhead on top. Draw data ownership boundaries first, or don't start.

**3. False decoupling.** Services split on paper but still coupled implicitly: shared schemas, shared libraries, hidden call-order dependencies, temporal coupling. The test is brutally simple — can you deploy Service B without redeploying Service C? If not, you've built a distributed monolith, which is strictly worse than either alternative.

**4. Operational burden multiplies.** One service means one pipeline, one log stream, one way to trace a request. N services means N of everything, plus distributed tracing, centralized logging, metrics aggregation, secrets management, and alerting you didn't need before. Teams routinely underestimate this and watch the migration stall in the operational swamp.

**5. Organizational mismatch — Conway's law.** The architecture will mirror how your teams communicate. If service boundaries don't match team ownership, you get coordination overhead, blame ping-pong, and nobody owning the seams. Slice services the way you intend to staff them.

**6. The migration strategy itself.** The only pattern that consistently works is the strangler fig: carve out one capability at a time behind an abstraction, redirect traffic, delete the old code. Big-bang rewrites are the canonical failure mode. But even the strangler carries a long dual-maintenance cost — both systems run in parallel, and the translation layer between them becomes its own bottleneck and source of drift.

**7. Wrong boundaries.** Splitting by technical layer — a "database service," a "logic service" — reproduces the monolith's coupling with extra overhead. Split by business capability. If the boundaries are wrong, you pay the full distributed-systems tax and get none of the independent-deployability benefit.

**8. Performance amplification.** One in-memory operation becomes several round trips. Latency budgets that were trivial in-process now require caching, batching, and async design. Microservices are not a performance optimization — they're an organizational scalability play.

The honest verdict: a microservices migration is justified when independent deployability and team autonomy are the bottleneck, not before. If the monolith is still healthy and the org is small, splitting it is adding cost without buying the benefit. The risk isn't the code — it's that you've permanently traded a simpler system for a harder one, and the migration has to actually pay that back.
