### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

You've asked this before — June 1st and 6th. The answer hasn't changed, but let me tighten it.

**Horizontal scaling** — add more machines to a pool. Distribute load across nodes. Stateless tiers scale trivially; stateful tiers need a strategy (consistent hashing, read replicas, distributed caches).

**Vertical scaling** — add more power to one machine. More CPU, RAM, faster disk. Works up to the ceiling of what single hardware can do, and that ceiling exists.

**Tradeoffs:**

| Axis | Horizontal | Vertical |
|------|-----------|----------|
| Ceiling | Theoretically unbounded | Physical limits per node |
| Operational cost | More machines → more management, networking, failure modes | Simpler ops, single point of failure |
| Consistency | Distributed systems problems (CAP, clock drift, partitions) | No cross-node consistency — one box, one truth |
| Latency | Inter-node calls add network overhead | Local memory/bus — fastest |
| Cost curve | Linear or sub-linear with proper sharding | Supra-linear at high end (proprietary hardware, premium pricing) |
| Failure domain | Degrade gracefully (lose a node, traffic rebalances) | Single node goes down → everything goes down |
| Complexity | Requires load balancers, service discovery, retry logic, eventual consistency discipline | Straightforward backup/restore, fewer moving parts |

**Decision rule:** Start vertical until you hit the hardware ceiling or the cost-per-unit-of-compute curves upward. Then go horizontal — but only after you've made your state manageable (stateless services, decoupled storage, idempotent operations). Premature horizontal scaling adds complexity without proportional benefit.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

A **primary key** uniquely identifies each row in a table — one per table, values must be unique and non-null. A **foreign key** is a column in one table that references the primary key of another table, enforcing referential integrity across the relationship. The primary key lives in the "parent" table; the foreign key lives in the "child" table and can contain duplicates or nulls.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database at the moment their transaction begins, identified by a transaction ID. When a writer updates a row, they create a new version of that row with their transaction ID attached; the old version remains visible to any reader whose snapshot predates the writer's commit. The reader never waits because they simply traverse the version chain until they find the one visible to their snapshot.

The garbage it creates is called *bloat* — old row versions that are no longer visible to any active or future transaction. These dead tuples accumulate in table pages and index entries, consuming disk space and degrading query performance (more pages to scan, worse cache hit rates). PostgreSQL requires VACUUM to reclaim that space, and in heavy-write workloads the bloat can outpace autovacuum if it isn't tuned.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of breaking a monolithic application into independently deployable services that communicate over a network, each owning its own data and domain boundary.

The main risks:

1. **Network becomes the new failure domain** — In a monolith, function calls are reliable local memory operations. After migration, every service call is a network hop with latency, timeouts, and partial failure. This is the single biggest source of new bugs. Mitigation: circuit breakers, retries with backoff, timeouts at every layer, and a strong understanding of the fallacies of distributed computing.

2. **Data consistency breaks** — A monolith uses a single database and ACID transactions. Microservices split the database. You lose distributed transactions. You now deal with eventual consistency, sagas, and compensating transactions. Most teams underestimate how much business logic implicitly relied on "read your own write" being guaranteed by the database.

3. **Operational complexity multiplies** — You go from deploying one artifact to deploying N services with coordination, service discovery, configuration management, observability (distributed tracing, metrics per service, centralized logging), and container orchestration. If you don't have the Ops maturity before you start, the migration adds more operational surface than the team can sustain.

4. **Boundary mistakes are expensive** — If you split along the wrong domain boundary (e.g., splitting what should be a shared library into a separate service, or coupling services that should be independent), the cost to re-merge or re-split is far higher than refactoring within a monolith. You discover the wrong boundary only months later when every feature requires a multi-service change.

5. **Distributed monolith** — The most common failure mode. Services end up calling each other synchronously in a chain that mirrors the old monolith's internal call graph, but now with network overhead, no local transactions, and worse latency. You get the complexity of microservices with none of the benefits. If you see a service touching another service's database directly, you're here.

6. **Testing becomes harder** — Integration tests now require standing up multiple services, managing their state, and handling network failures. You trade simpler end-to-end tests in the monolith for a complex test pyramid that requires contract testing (consumer-driven contracts), integration test environments, and careful test isolation.

7. **Team coordination overhead** — If the org structure doesn't match the service boundaries (Conway's Law in reverse), you get cross-team dependencies on every change, shared code ownership that nobody wants to touch, and release coordination that wastes more time than the old monolith ever did.

The migration should start with the Strangler Fig pattern — extract services incrementally, not a big-bang rewrite. And the first service extracted should be the one with the clearest domain boundary and the lowest coupling, not the one causing the most pain in the monolith. Pain-first extraction tends to produce poor boundaries because the pain is frequently a symptom of tight coupling that should be fixed *in* the monolith before it's extracted.
