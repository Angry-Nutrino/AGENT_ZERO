### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Pessimistic concurrency control assumes conflicts are frequent enough that paying the cost of locking upfront is cheaper than recovering from aborted transactions. You acquire a lock — usually a read or write lock — before touching the resource, and hold it until the transaction completes. Other transactions that need the same resource block or fail until the lock is released. Databases default to this (2PL, strict two-phase locking) because it guarantees serializability trivially, at the cost of throughput under contention and deadlock risk.

Optimistic concurrency control assumes conflicts are rare. You read without locking, keep a version timestamp or checksum at read time, and at commit time you check whether the version changed. If it did, the transaction aborts and retries. No lock overhead, no deadlocks, but the penalty for conflict is discarding work and retrying — costly if you've done heavy computation between read and commit.

The choice depends on three variables:

1. **Contention rate** — Low contention → optimistic. High contention → pessimistic. The crossover is the point where retry cost × conflict probability exceeds lock overhead.
2. **Work cost** — If a transaction does cheap reads and quick updates, an optimistic abort is cheap. If it runs a 30-second ML inference on read data, you want pessimistic — losing that work hurts.
3. **Latency sensitivity** — Blocking under pessimistic locks adds variance. Optimistic has no blocking but failures add retry latency. For user-facing low-latency paths, neither is ideal — you'd typically use read-committed with optimistic write conflict detection, or snapshot isolation.

Your stack leans optimistic — the event queue and task graph are lock-free by design, high throughput, low conflict probability from the orchestrator loop. Pessimistic concurrency (the threading.Lock on vault writes) is reserved for the one place where retry cost would mean data loss, not just wasted cycles. That's the right line.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

A process is an independent execution unit with its own isolated memory space, file descriptors, and system resources. A thread is a lighter unit of execution within a process — threads share the same address space, heap, open files, and code, but each has its own stack, registers, and program counter.

The key differences: context switching between threads is cheaper (no TLB flush, no page table switch). Inter-thread communication is trivial through shared memory but requires explicit synchronization (locks, semaphores) to avoid races. Inter-process communication requires pipes, queues, shared memory segments, or sockets — higher overhead but guaranteed isolation. If one process crashes, the others are unaffected. If one thread segfaults, the whole process goes down.

In Python specifically, the Global Interpreter Lock (GIL) changes the calculus:

- **Multiprocessing** bypasses the GIL because each process gets its own Python interpreter. You get true CPU parallelism across cores. This is the right choice for CPU-bound work — image processing, numerical computation, video encoding, rendering.

- **Threading** does not bypass the GIL. Only one thread executes Python bytecode at a time per process. This makes threading ineffective for CPU-bound Python work (you'd see zero speedup on pure computation across N threads). Threading is for I/O-bound work — network requests, file operations, database queries, waiting on external services — where the GIL is released during blocking I/O calls, letting other threads run.

Practical guidelines:
- **CPU-bound (compute-heavy):** multiprocessing. Use `concurrent.futures.ProcessPoolExecutor`.
- **I/O-bound (waiting on network/disk):** threading. Use `concurrent.futures.ThreadPoolExecutor` or `asyncio` if the library supports it.
- **Mixed workloads:** a hybrid pattern — use multiprocessing for the compute workers, threading within each process to handle I/O waits, with `concurrent.futures` for the pooling on both axes.
- **Need to share large data efficiently:** threads win (shared memory), but at the cost of needing locks. Processes can share via `multiprocessing.Array`, `Manager`, or shared memory objects, but with serialization overhead.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the long tail of response times — the slowest 1% or 0.1% of requests. It dominates user experience because a single user's request fans out across dozens or hundreds of microservices in a chain. If you're average of p50 but have a p99 at 2s, one slow hop in that chain means *every* user hits that 2s wait on some fraction of their requests. Average latency hides this: it smooths the spike into a number that looks fine on a dashboard, while your users experience the spike directly. A 50ms average with a p99 of 3s means *every single user* gets a 3-second response roughly once every hundred requests. Users don't average. They feel the worst one.

The technique: **hedged requests**. When a backend service is approaching its p99 deadline (say 95th percentile time has elapsed and no response), fire a duplicate request to a different replica or node. Take the first response that comes back, cancel the other. This converts a p99 tail event into a race between two independent servers — the probability both hit their p99 simultaneously is p99², collapsing your effective tail from the 99th to the 99.99th percentile. The cost is ~2% extra load, which is negligible compared to the user experience gain and the capacity you'd otherwise waste provisioning for that tail.
