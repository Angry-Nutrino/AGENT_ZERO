### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fact that the same piece of data gets written multiple times before it settles. A row insert hits the write-ahead log, then the in-memory memtable. When the memtable flushes, that row is written to level 0 as an SSTable. Then compaction picks it up — merging it downward through levels, rewriting it into new larger SSTables at each level until it reaches its final sorted run. Each compaction pass rewrites that data again. So one logical write becomes 10–30 physical writes depending on the number of levels, the compaction strategy (size-tiered vs leveled), and the size ratio between levels.

The costs in practice are threefold. First, it consumes write bandwidth — on NVMe SSDs rated for 500 MB/s sequential writes, compaction can saturate the IO channel during heavy ingestion, starving read traffic and causing latency spikes. Second, it accelerates SSD wear: consumer TLC NAND is good for roughly 600–1000 P/E cycles, so a write amplification factor of 20 turns a 5-year drive life into a 3-month one under sustained load. Third, compaction creates CPU pressure — merging and compressing blocks is compute-bound, and when compaction falls behind the ingestion rate, read performance degrades because more files must be consulted per query (read amplification).

The practical trade-off is between write amplification and read amplification. Leveled compaction (RocksDB default, 10× size ratio) keeps read amplification near 1 but has high write amplification — each level compaction rewrites the entire input. Size-tiered compaction merges many small files into fewer large ones, reducing write amplification at the cost of more SSTable lookups per read. There is no free lunch; the knob controls which side of the spectrum you optimize for.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a consistent snapshot of the database at the moment the transaction started. Writes create new versions of rows instead of overwriting the current one — the reader continues to see the old version until the writer commits, and even then the reader keeps its snapshot until it finishes. No locks held during reads means the writer never waits on a reader, and the reader never waits on a writer.

The garbage is *dead row versions* — rows that are no longer visible to any active transaction. Every UPDATE or DELETE leaves a tombstone or obsolete copy in the data pages. These accumulate in the heap and indexes, bloating storage and slowing sequential scans. PostgreSQL calls this *bloat* and reclaims it with VACUUM (which can itself be tuned to run concurrently via autovacuum). Without that cleanup, the database degrades from consistent reads to a storage‑capacity or performance wall.

### Q12 [DELIBERATE] — CLAUDE.md says a rare dropped os.replace in _save_memory 'self-heals on the next save'. From core_logic/crud.py: WHY is that true — what does every save write — and which exception class gets the retry-with-backoff on Windows?

There is no incremental or delta write. So if the `os.replace` on a given call fails (the retry loop at lines 90–96 exhausts without breaking, the `else` at line 97 logs the error but does **not** re-raise), `self.memory` remains intact in memory. The next writer that acquires `self._lock` will serialize the full dict again to its own `mkstemp` file and call `os.replace` fresh. The old replace's failure is irrelevant — the new one either succeeds and overwrites the target, or also fails and the next writer tries again. 2. **Exception class that gets the retry-with-backoff on Windows** — `PermissionError` (Python 3's built-in, alias for `OSError` errno 13 — `ERROR_ACCESS_DENIED` / `SHARING_VIOLATION` on Windows). Lines 90–96 show a 10-attempt loop with exponential backoff (`time.sleep(0.02 * (attempt + 1))`), catching only `PermissionError`. Any other exception (disk full, encoding error, etc.) falls through to the broad `except Exception` at line 99, which logs and exits without retrying.

**Summary:** Full-dict serialization every save makes dropped replaces harmless — nothing is lost except that one write, and the next one writes the complete state again. On Windows, `PermissionError` from concurrent readers gets retried up to 10 times with ~2–200ms backoff.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration is the process of decomposing a monolithic application into independently deployable, loosely coupled services, each owning its own data and communicating over a network.

The main risks, in order of how often they collapse projects:

1. **Network becomes the new database call** — what was a local function call now crosses process boundaries. Latency, partial failure, retry storms, and cascading timeouts replace predictable in-memory execution. Most teams underestimate this by an order of magnitude.

2. **Distributed transactions masquerading as business logic** — a single user action that touches three services now requires Saga patterns, compensating transactions, or eventual consistency. Teams that try to preserve ACID across service boundaries end up with a distributed monolith that has worse latency and none of the benefits.

3. **Observability debt** — you go from one application log and one database to N services each with their own logs, metrics, and traces. Without distributed tracing and structured logging from day one, debugging becomes "which service failed silently 400ms ago?"

4. **Data fragmentation without clear ownership** — splitting a database is the hardest part. Shared tables get carved into bounded contexts, but the boundaries are never clean. Foreign keys become API calls. Reports that used to be a single JOIN become orchestration across five services.

5. **Premature extraction** — teams pull out a service because it *might* scale independently, not because it has a real reason to be separate. The cost of network calls, deployment pipelines, and operational surface area for each service is non-trivial. Every service is a liability unless it earns its keep.

6. **Coordination overhead** — what one developer could change in a monolith now requires alignment across teams, versioned API contracts, and coordinated deploys. The organizational complexity often outweighs the technical complexity.

The ones that survive start with the Strangler Fig pattern — extract one bounded context at a time, keep the monolith alive until the replacement is proven, and never split data before you've proven the service boundary is correct.
