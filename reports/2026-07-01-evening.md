### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from three cascading sources: each write to the memtable is re-written to disk in a sorted string table (SSTable) during flush, then repeatedly re-written again as that SSTable is merged into progressively larger levels via compaction. A single application write triggers a write to the WAL, a flush write, and potentially multiple compaction rewrites as data moves from Level 0 through each subsequent level. The total amplification factor is roughly `O(L * T)` where `L` is the number of levels and `T` is the size ratio between levels — typically 10–20x for a common tiered compaction setup, and 3–5x for leveled compaction. The practical cost is that the storage device's write endurance is consumed disproportionately to the logical write volume; on consumer SSDs rated for 150–300 TBW, a 5x amplification with 100 GB/day ingestion means burning through 500 GB/day of physical writes, which shortens the device's usable life from several years to months. The hidden cost is also tail latency: compactions share I/O bandwidth with reads, so a large compaction spike can starve incoming queries of disk throughput, causing noticeable P99 latency degradation — Cassandra and RocksDB installations routinely tune compaction threads and rate limits precisely for this reason.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each transaction a snapshot of the database at a point in time — typically the transaction's start timestamp or its assigned XID. A reader sees only rows that were committed before that snapshot. When a writer updates a row, it creates a new version rather than overwriting the old one. A concurrent reader still sees the old version, so the writer never waits for the reader, and the reader never waits for the writer. The only conflict is writer–writer: two concurrent updates to the same row must be serialized, typically by the first write locking the row and the second blocking or aborting.

The garbage is old row versions that are no longer visible to any active or future transaction. These accumulate in the table's storage pages — each update leaves a dead tuple behind. PostgreSQL calls this *bloat*: the table grows beyond its logical size because its pages are filled with dead row versions, index entries pointing to them, and free space that can't be reused until those tuples are reclaimed.

Cleanup comes in two forms:
- **VACUUM** runs a marking pass and a reclamation pass. The marking pass walks the table and identifies dead tuples — versions whose visibility is behind the oldest still-running transaction's snapshot boundary. The reclamation pass removes those tuples and coalesces free space within each page. In Postgres, autovacuum is the default mechanism; it triggers based on tuple churn counters, not wall-clock intervals.
- **Page-level compaction** happens in-place when VACUUM rewrites a page's line pointer array to remove references to dead tuples, making space for new hot (heap-only tuple) updates within the same page without needing to touch indexes.

### Q12 [DELIBERATE] — core_logic/crud.py's _save_memory writes memory.json atomically. Name the three steps it uses (temp-file creation, the durability call, the atomic swap), and in one phrase why the temp name must be unique per call.

**Three steps:**

1. **`tempfile.mkstemp(prefix=".memory.json.", suffix=".tmp", dir=d)`** — creates a unique temporary file in the same directory as memory.json.
2. **`os.fsync(f.fileno())`** — flushes the file descriptor to disk before closing, ensuring the data is physically written.
3. **`os.replace(tmp, self.filepath)`** — atomically swaps the temp file into place (atomic on both Windows and POSIX; retried up to 10 times with backoff on Windows `PermissionError` from concurrent readers).

**Why unique per call:** concurrent writers (`memorize_episode` in a background thread and `log_system_episode` from autonomous tasks) can be in `_save_memory` simultaneously — a shared temp name would let them interleave writes to the same file and corrupt it despite `os.replace`'s atomicity.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into multiple independently deployable services that communicate over a network, each owning its own data and business capability.

The main risks:

**Coupling that isn't actually broken** — teams split code but keep a shared database, shared schema, or synchronous API chains that create the same failure blast radius as the monolith, just slower. Distributed monolith is the most common failure mode.

**Network as a new failure dimension** — latency, partial failure, timeouts, retry storms, cascading failures from unhandled backpressure. The monolith had function calls with microsecond guarantees. Now every call is a distributed system problem.

**Data consistency** — you lose ACID transactions across services. Eventually-consistent patterns (Sagas, event sourcing, outbox) are considerably harder to reason about and debug than a single transaction rollback.

**Observability debt** — a monolithic application needs one log stream and one APM agent. A 10-service system needs distributed tracing, structured logging aggregation, health check coordination, and correlation IDs threaded through every boundary. Teams often discover this on day one of production traffic.

**Organizational Conway's Law mismatch** — if the service boundaries don't match team ownership, you get coordination overhead that exceeds the monolith's deployment pipeline cost. Migrating for technical reasons without the organizational structure to support it is the fastest path to slower delivery.

**Premature granularity** — splitting into too many services too early, before you understand the actual coupling points. The right first move is usually extracting one bounded context at a time, with a strangler fig pattern, not a big-bang redecomposition.
