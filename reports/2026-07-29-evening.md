ONNX doesn't pre-JIT — it compiles on first inference. That's a one-time cost, but on the first real `speak()` call it would add 2–5 seconds of latency before any audio reaches `_out_stream`.

The code documents this directly at line 112–113:

The warmup at lines 114–119 creates a single dummy synthesis:

```python

```

This absorbs the ONNX JIT compilation cost at startup so the first real `speak()` call runs at full speed (~200ms first-audio latency on CUDA).

**But the warmup must NOT run before the CUDA fix.** Here's the ordering from the actual `load()` method:

1. **Lines 92–94** — `self._kokoro = Kokoro(onnx_path, voices_path)` — loads the model. Kokoro internally creates an ONNX InferenceSession, but it fails to detect GPU because its startup code calls `find_spec("onnxruntime-gpu")`, which always returns `None` — hyphens are invalid Python module names, so `import onnxruntime-gpu` can never succeed.

2. **Lines 99–110** — The CUDA workaround replaces `self._kokoro.sess` with a new `ort.InferenceSession` explicitly configured with `["CUDAExecutionProvider", "CPUExecutionProvider"]`. This is the fix.

3. **Lines 114–119** — The warmup inference runs on the now-CUDA-enabled session.

If the warmup ran at line 94 (immediately after Kokoro construction) instead of at line 114, it would trigger JIT compilation on the **CPU** session that Kokoro created internally — and the CUDA upgrade at line 102 would then replace that session entirely, **discarding the warmup's JIT cache**. The ordering matters: the CUDA `InferenceSession` replacement must happen before the warmup so that the JIT cache is built for the **same provider** that all subsequent inference uses.

### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-tree engines comes from compaction — the repeated rewriting of the same data as it's merged across levels. A key written once to the memtable is flushed to an SSTable at Level 0, then merged down through progressively larger levels. Each merge reads existing SSTables, merges them with new ones, and writes compacted output, moving the same logical data multiple times. The actual bytes written to disk can be 10–50x the logical data size depending on level sizing and compaction strategy (size-tiered vs level-tiered).

In practice, the cost is asymmetric: on HDDs it's throughput erosion — your sustained write speed becomes a fraction of the raw disk bandwidth. On SSDs it's wear — each P/E cycle consumed by compaction reduces drive lifespan proportionally. Latency spikes also appear during major compactions when large levels are merged, starving foreground writes of IOPS. The offset is dramatically better read performance and lower space overhead than B-trees for write-heavy workloads, so you trade sustained write throughput and device endurance for efficient range scans and predictable storage utilization.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each transaction a snapshot of the database at a point in time — typically its start timestamp or transaction ID. A reader sees only rows whose creation version ≤ its snapshot and whose deletion version > its snapshot (or is null). A concurrent writer creates a new version of a row with its own transaction ID; the reader's snapshot still points at the old version. So neither waits on the other — the reader reads the old version, the writer installs the new one, and isolation is maintained by visibility rules rather than locks.

The garbage is **dead row versions** — tuples that are no longer visible to any active transaction because a newer version has replaced them and all snapshots that could see them have committed. These accumulate in the table's heap pages, wasting space and degrading index scans. PostgreSQL calls it bloat; MySQL/InnoDB's purge thread reclaims them once the oldest active snapshot no longer needs them. Without cleanup (VACUUM in Postgres, purge in InnoDB), the table grows unbounded and read performance degrades from having to skip stale versions.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into a set of independently deployable, loosely coupled services — each owning its own data, communicating over a network, and typically aligned to bounded contexts from domain-driven design.

The main risks when splitting a monolith into independent services:

1. **Network as the new failure mode** — Every in-process call becomes a remote call. Latency, timeouts, retries, partial failure, and cascading outages now exist where they didn't before. Most teams underestimate the reliability engineering required.

2. **Distributed data consistency** — ACID transactions that spanned a single database must be replaced with eventual consistency, sagas, or compensating transactions. Inconsistencies become visible between services, and exactly-once processing becomes a real problem.

3. **Decomposition without the right boundaries** — Slicing along technical layers (separate service for DB access, another for business logic) creates chatty, tightly coupled services. The correct boundary is the bounded context — what changes together stays together. A wrong cut is expensive to undo.

4. **Operational complexity explosion** — One deployable becomes many. CI/CD pipelines multiply, monitoring and observability must span distributed traces, log aggregation, and metrics across services. Teams need container orchestration (Kubernetes or equivalent) and often don't have the operational maturity before starting.

5. **Data ownership and query fragmentation** — Joins across databases disappear. Reporting and analytics that relied on a single SQL query now require an API composition layer or event-driven materialised views. Frontends that previously fetched one object must now call multiple endpoints, increasing latency and complexity.

6. **Organizational Conway's Law trap** — Services often reflect team boundaries. If the teams aren't aligned to own services end-to-end (data, code, deploy, operate), the migration stalls in shared ownership ambiguity, coordination overhead, and release dependencies.

7. **Cost of premature extraction** — Extracting a service that isn't under independent pressure to scale or change independently adds latency and operational cost without corresponding benefit. The monolith isn't the enemy; incoherent coupling is.

The common pattern of failure is starting a migration for architectural purity rather than for a specific pain point (deploy bottleneck, scaling contention, team autonomy). Migrating the *right* service at the *right* time, while keeping the monolith intact for everything else, reduces risk substantially.

**Design rule: threading.Lock vs asyncio.Lock**

- **`threading.Lock`** — synchronous mutual exclusion for operations that run in a **dedicated thread or background thread**, where `await` is not available. Protects shared mutable state (flags, lists, file paths) across threads without assuming an event loop. Examples: vault write guard in `memorize_episode` prevents duplicate fact insertion; `rag_db_builder` lock prevents a startup thread and `EnvironmentWatcher` from rebuilding the DB simultaneously; the voice module's state flags are guarded against concurrent thread access.

- **`asyncio.Lock`** — cooperative mutual exclusion for operations inside the **async event loop** where a thread would block the entire system. Used when the critical section itself is async or when coroutines must suspend and allow other tasks to run while waiting. Examples: MiniLM encode calls are serialized via `asyncio.Lock` so the main async thread and background memorization thread don't corrupt the embedding pipeline; the `resource_ledger` acquire-write per path uses `asyncio.Lock` so a write-awaiting task cooperatively yields to other coroutines instead of blocking the reactor.

**The deciding factor is context**: is the protected operation running in a thread where `await` would fail → `threading.Lock`. Is it inside the async event loop, sharing a resource with a background async task → `asyncio.Lock`.
