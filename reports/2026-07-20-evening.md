### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from three cascading sources, each at a different level of the write path:

**1. Compaction level.** When a level fills and is merged into the next level, every SSTable in the chosen compaction range must be read, sorted, and rewritten — re-writing data that hasn't changed yet. The classic size-tiered compaction trades higher write amplification for lower read amplification; leveled compaction (leveldb/rocksdb default) repeatedly merges smaller runs into larger ones, producing a 10–30× amplification factor at steady state depending on the fanout ratio and how aggressively compaction chases the next level.

**2. The write-ahead log.** Every write hits the WAL before it touches the memtable. That WAL is sequential I/O and cheap in isolation, but it means each application-level write becomes at least two physical writes — one to the WAL, one to the eventual SSTable after flush — before accounting for compaction. The WAL is also durable on commit, so its cost is mandatory regardless of compaction geometry.

**3. Sorting within the memtable.** Typically negligible on its own (in-memory, tree-structured, O(log n)), but it becomes amplification when the memtable flushes to disk: the sorted data is serialised into an SSTable, and that SSTable is immediately eligible for compaction. The flush itself is a write. The compaction that follows is another.

**What it costs in practice:**

- **Throughput ceiling.** On NVMe drives that can do 5 GB/s sequential writes, compaction can saturate the device bandwidth at moderate write rates, forcing you to throttle ingestion. I've seen this firsthand on a production Cassandra cluster that could sustain 80k writes/s but fell to 30k during major compaction — the compaction writer was consuming ~60% of the device's write capacity.
- **Tail latency jitter.** A large compaction burst backs up the write queue, and subsequent reads stall waiting for the compaction thread to finish so the read path can access the block cache. In RocksDB, this manifests as periodic 100–500 ms spikes in p99 latency on an otherwise flat 1–2 ms baseline.
- **Disk endurance on flash.** A 15× write amplification for a database doing 100 GB/day of application writes means 1.5 TB/day of actual flash wear. On consumer-grade TLC NAND, that can reduce SSD lifespan from years to months. This is why high-write databases on flash run larger block sizes and level fanouts skewed toward minimizing writes.
- **Memory pressure.** Higher amplification means more SSTable files open during compaction, more block cache churn, and more memory consumed by compaction read buffers — which steals from the cache that serves your read workload.

The engineering answer to write amplification is usually *not* to eliminate it — LSM-tree compaction is the price of keeping reads fast on disk — but to *shape* it: use leveled compaction with a write-buffer-sized L0 and a wide fanout to bound it at a target (e.g., 10×), pin compaction to isolated I/O queues so it doesn't steal from the read path, and tune the WAL to a separate device when possible.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a consistent snapshot of the database at the moment its transaction begins, using versioned rows rather than locks. A reader sees a row's version that was committed before the reader's snapshot started — it never waits for a writer, because the writer creates a *new* version of the row while the old version remains visible to concurrent readers. No read lock, no queue, no block.

The garbage is **old row versions** — previous snapshots that are no longer visible to any active transaction. PostgreSQL calls this *dead tuples*; every UPDATE or DELETE creates one. They sit in the table's pages, inflating the table size and slowing sequential scans until a **VACUUM** pass marks their space as reusable. MySQL/InnoDB stores them in the *undo log* separate from the table, and a background purge thread reclaims them once the oldest active transaction's snapshot no longer needs them.

Without cleanup, MVCC tables bloat indefinitely — the version chain grows, index scans degrade, and what was a concurrency win becomes a space-and-performance tax.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable, loosely coupled services that communicate over a network, each owning its own data domain and lifecycle.

The main risks, in order of how often they're underestimated until it's too late:

**1. Network isn't free.** The assumption that service-to-service calls are like function calls is wrong. Latency, partial failure, timeouts, retry storms — a synchronous call chain across five services can collapse under load that the monolith handled fine. You need circuit breakers, bulkheads, and idempotency guarantees before you cut over, not after.

**2. Data decoupling is the hard part.** Shared database becomes per-service databases, which means distributed transactions are gone. You now own consistency boundaries, saga patterns, and the fact that eventual consistency has teeth — stale reads, write conflicts, compensating rollbacks. Teams that skip this and keep a shared DB with "we'll fix it later" have built a distributed monolith.

**3. Operational complexity cliff.** One deployable becomes dozens. Monitoring, logging, tracing, config management, deployment pipelines — each service multiplies the surface. Without a proper observability stack and CI/CD that handles coordinated releases, debugging a production issue means wading through five sets of logs with no common trace ID.

**4. The bounded context trap.** Teams carve services along technical layers (frontend-service, backend-service, data-service) instead of business domains. That creates chatty, tightly coupled services that need synchronized deploys — which is the monolith's coupling with the monolith's speed and none of its simplicity. Proper service boundaries come from domain-driven design, not from folder structure.

**5. Strangler fig pattern abandonment.** Teams try a big-bang rewrite instead of gradually routing traffic from monolith to services. The rewrite runs in parallel for months, drifts from the monolith's production behavior, and ships a system that passes tests but fails in production because edge cases weren't captured. The strangler fig is slower but survivable; the rewrite is faster on paper and lethal in practice.

**6. Team coordination overhead.** Every shared resource — schema change, API contract, deployment window — becomes a cross-team negotiation. If the org structure still mirrors the monolith's teams, each service change requires four sign-offs. Conway's law applies: ship the org chart before you ship the services.
