### Q01 [CHAT] — What is the difference between a monolithic and a microservices architecture? What are the main tradeoffs? Answer from your training knowledge.

Two architectural patterns at opposite ends of the deployment cohesion spectrum.

**Monolithic** — one binary, one deployment, one codebase for the entire application. Everything runs in a single process: auth, business logic, data access, UI rendering. Scale by running more copies of the same thing behind a load balancer.

**Microservices** — decomposed into independent services, each owning its domain, data store, and deployment pipeline. Services communicate over a network — usually HTTP/gRPC for synchronous, message queues for async.

**Tradeoffs:**

Monolithic:
- **+** Simpler development loop. One repo, one build, one deploy. No network latency between components. Atomic transactions across domains. Easier to reason about end-to-end behavior.
- **+** Lower operational overhead. You need one application server, one monitoring setup, one CI/CD pipeline.
- **–** Scales coarsely. One expensive feature doesn't justify its own instance — you scale everything. Team coupling grows with codebase size. A runtime error in one module takes the whole process down.
- **–** Technology lock-in. Breaking out a component later is a rewrite, not a refactor. You commit to the stack for the life of the system.
- **–** Deployment risk is all-or-nothing. One bad line in a checkout flow ships a billing change.

Microservices:
- **+** Independent deployability. Teams ship on their own cadence. One service fails without cascading — if it doesn't kill the dependency chain.
- **+** Fine-grained scaling. Run 20 instances of the search service, 3 of the auth service. Right-size each resource envelope.
- **+** Technology heterogeneity. The search team wants Rust for latency; the analytics team wants Python for ML libraries. No one blocks anyone.
- **–** Distributed systems complexity is not negotiable. Network latency, partial failure, eventual consistency, debugging across 12 services' logs — these are not fixable. You live with them or you don't go microservices.
- **–** Operational blast radius expands. You now manage service mesh, API gateways, circuit breakers, distributed tracing, sidecars, deployment automation. You need platform engineering capability before you need microservices.
- **–** Data consistency is painful. No cross-service transactions. Sagas, outbox patterns, CDC events — each is a workaround with its own failure modes.

The decision rule: start monolithic. Split only when you have concrete evidence — not intuition — that a boundary is worth the tax. "We might need to scale independently someday" is not evidence. Actual bottleneck data is.

Symmetric encryption uses a single shared key for both encryption and decryption — fast, efficient, good for bulk data at rest or in transit (AES, ChaCha20). Asymmetric encryption uses a public/private key pair — slower, computationally heavier, used for key exchange (Diffie-Hellman), digital signatures (RSA, ECDSA), and authentication.

Real-world systems combine both: asymmetric to exchange a session key, then symmetric for the actual data. TLS does this. So does Signal. The question isn't which one — it's where each fits in the hybrid protocol.

### Q15 [CHAT] — Explain how Python's asyncio event loop runs many coroutines on a single thread, and what happens to the whole loop if one coroutine performs a long blocking CPU-bound computation. Answer from your training knowledge.

The asyncio event loop runs on a single thread by multiplexing coroutines through cooperative multitasking. Each coroutine yields control at `await` points — the loop checks its runnable queue, picks the next ready task, and resumes it from its last suspension point. This works because I/O-bound operations like network calls and file reads are wrapped in non-blocking futures: the coroutine awaits them, the loop registers a callback, and when the OS signals the handle is ready, the coroutine is re-enqueued. The entire mechanism depends on coroutines voluntarily suspending. A coroutine executing a long CPU-bound computation — pure math, heavy parsing, a tight loop — never hits an `await` statement, so it never yields. The event loop can't preempt it. The loop thread is stuck running that one coroutine, and every other coroutine in the scheduler, timer queue, or waiting on I/O simply waits. The whole application freezes until the CPU-bound work completes. That's why CPU-heavy work should be offloaded to a thread pool via `run_in_executor`.
