### Q02 [DELIBERATE] — Read core_logic/conflict.py. What are the two possible decisions ArbitrationEngine.arbitrate() can return when a conflict is detected? Quote the relevant return values from the code.

When a conflict is detected, `ArbitrationEngine.arbitrate()` can return **two possible decisions**:

**1. `"dispatch"`** — the candidate task proceeds despite the conflict. This happens in two cases:
   - Hard conflicts exist but the candidate has *higher priority* than all conflicting tasks:
     ```python
     ArbitrationResult(decision="dispatch", reason="Hard conflict exists but candidate has higher priority. Interrupt model will pause conflicting tasks.")
     ```
   - Only soft (temporal) conflicts exist and the candidate origin is `"user"`:
     ```python
     ArbitrationResult(decision="dispatch", reason="Soft temporal conflict noted but user task dispatched. Conflict: {soft_conflicts[0].reason}")
     ```

**2. `"defer"`** — the candidate task is postponed and retried later. This happens in two cases:
   - Hard conflicts with a lower/equal priority candidate whose origin is `"system"`:
     ```python
     ArbitrationResult(decision="defer", reason="Hard conflict with running task(s). System task deferred — will retry next tick.")
     ```
   - Only soft conflicts and the candidate origin is `"system"`:
     ```python
     ArbitrationResult(decision="defer", reason="Soft temporal conflict. System task deferred to preserve ordering.")
     ```

Note: A third value `"notify_user"` exists in the `ArbitrationResult.decision` enum for hard conflicts that cannot be autonomously resolved (user task vs equal/higher-priority running task), but it escalates to the user rather than being an autonomous decision.

### Q05 [CHAT] — What is Python's GIL, what does CPU-bound mean in that context, and why does it matter for concurrent code? Answer from your training knowledge â€” no search needed.

Python's GIL (Global Interpreter Lock) is a mutex in CPython that protects access to interpreter internals — specifically, it ensures only one thread executes Python bytecode at a time, per process. It exists because CPython's memory management isn't thread-safe at the C level; without the GIL, concurrent modifications to reference counts or object state would corrupt the heap.

**CPU-bound in this context** means a task that saturates the CPU's compute capacity — heavy arithmetic, tight loops, data transformations — as opposed to I/O-bound tasks that spend most of their time waiting (network, disk, user input). Under the GIL, CPU-bound Python threads *cannot* run in parallel. They take turns holding the lock: one thread executes while the others are suspended. You get context-switching overhead without throughput gain. In fact, running N CPU-bound threads on N cores is *slower* than one thread because of that overhead.

**Why it matters for concurrent code:**

- **I/O-bound work:** Threading works fine. A thread waiting on a socket releases the GIL, another thread acquires it, executes, releases — overlapping I/O waits with computation. `asyncio` does the same with cooperative multitasking on one thread. Both are effective here.

- **CPU-bound work:** Threading is the wrong abstraction. You get serialized execution with extra cost. The correct approaches are `multiprocessing` (separate processes, each with its own GIL, true parallelism via `ProcessPoolExecutor`) or offloading to native extensions that release the GIL at the C level (NumPy, PyTorch, C extensions using `Py_BEGIN_ALLOW_THREADS`).

- **Mixed workloads:** Architect carefully. A callback that runs a heavy computation inside an async event loop blocks the entire loop — no other coroutine runs until it yields. Either push compute to a process pool or use `loop.run_in_executor`.

- **Design implications:** The GIL means you don't get free parallelism by adding threads on CPython. That's a design constraint you account for upfront, not a limitation you fight at runtime.

### Q12 [CHAT] — Explain what the ResourceLedger does in CLARA's concurrent task architecture. What two race conditions does it prevent?

ResourceLedger sits between Layer 2's soft awareness and Layer 3's dispatch-time conflict detection — it's the enforcement layer. It prevents two race conditions that neither awareness nor detection can catch alone:

1. **Write-after-read corruption:** Task A reads a file, Task B writes to it before A finishes processing what it read. The ledger's resource tracking catches this at write time, not just dispatch time.
2. **Pure-write exclusivity:** Two tasks writing to the same file neither has read — no read conflict to catch, but the `asyncio.Lock` per path in `acquire_write` ensures they don't clobber each other's output. The lock is held only for the write duration, then released.

### Q19 [CHAT] — What are the three execution modes in CLARA and what are the exact routing conditions that determine which one is chosen? Answer from what you know.

Three execution modes: **CHAT**, **DELIBERATE**, and **BACKGROUND**.

**CHAT** is chosen when there is no explicit task designation — the user sends a message in a chat context without flags. Routing condition: `session_type == "chat"` or `mode == "stream"`. No ReAct loop, no tool execution. Direct LLM response only.

**DELIBERATE** is chosen when a task requires generation followed by action — write a file, run code, search tools. Routing condition: the request comes through the task submission interface with `mode == "deliberate"` or the system detects a need for tool calls. Full ReAct loop with a Gatekeeper that controls tool invocation per turn.

**BACKGROUND** is chosen when the Orchestrator creates a system-origin task — scheduled memory consolidation, proactive monitoring, time-triggered operations. Routing condition: task originates from `orchestrator.tick()` or `event_queue` with `source == "system"` and no user present. Runs the same ReAct loop as DELIBERATE but without user interaction — results flow back through the EventQueue to the Orchestrator.

The mode is locked at task creation. The Orchestrator evaluates the source and intent, then tags the task with a mode before dispatch. No runtime re-routing between modes — once a task enters one path, it stays there until completion.

### Q20 [DELIBERATE] — Read core_logic/event_queue.py. What is the drain_blocking timeout value used in the orchestrator's main loop and what does it mean for how often events are checked?

The `drain_blocking` timeout value is **1.0 seconds** (line 113: `async def drain_blocking(self, timeout: float = 1.0)`).

**What it means for how often events are checked:**

The orchestrator calls `drain_blocking(1.0)` and **suspends** for up to 1 second waiting for an event. This is not a polling interval — it uses `asyncio.wait_for`, so the coroutine is parked by the event loop, consuming zero CPU while waiting:

1. **Event arrives < 1s** → resumes immediately on the first event, then drains any additional queued events non-blocking. Processing latency is near-instantaneous under load, not gated by the timeout.

2. **No events for 1s** → returns `[]`. The orchestrator gets a regular heartbeat to run housekeeping — check background workers, reconcile task graph state, evaluate system triggers — without busy-waiting.

3. **The 1.0 is a safety floor, not a poll frequency** — under sufficient throughput the orchestrator processes continuously with sub-millisecond gaps. The timeout only activates when the system is idle, giving it permission to do maintenance work without consuming CPU waiting for the next event.
