### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design tension: data is written once at the memtable level, then re-written *again* at every compaction level it passes through. A single key-value insert can be written to the WAL, flushed to an SSTable at L0, then merged downward through L1, L2, L3 — each compaction rewriting the data into a new sorted run and discarding the old one. That's not one write on media. It's often 10–30x the logical write size in actual bytes written to disk.

The costs in practice:

- **SSD wear.** Consumer SSDs are rated for 150–600 TBW. An LSM-tree ingesting 10 GB/day with 20x write amplification is actually writing 200 GB/day. That's a $300 drive dead in two to three years. Production databases account for this in drive budgeting.
- **IOPS starvation.** Write amplification doesn't just consume bandwidth — it consumes queue depth. Compaction threads compete with the foreground write path for the same device. When compaction falls behind, read performance degrades too because uncollapsed levels require more SSTable lookups. This is the most common operational failure in LSM-based systems: "Why is my write throughput cratering?" — because compaction is thrashing.
- **Tail latency.** Compaction isn't smooth. A major compaction that merges L4 into L5 can saturate disk bandwidth for seconds. Any foreground write or read arriving during that window sees 5–10× normal latency. Applications notice this as "random pauses."
- **Capacity overhead.** Until compaction collapses older levels, two copies of the same data exist simultaneously (the old file being compacted and the new output). On a drive at 70% utilization, write amplification effectively pushes the system to its true capacity ceiling faster than the raw data size suggests.

The trade is structural, not a bug. LSM-trees exchange write amplification for *sequential* writes (good for HDDs and SSD flash cells) and for fast writes at ingestion (no random page updates). RocksDB, LevelDB, Cassandra, and Scylla all accept this cost and tune around it — bloom filters to reduce read overhead, leveled compaction to bound amplification, rate-limited compaction to protect foreground traffic. The question is never "can we eliminate write amplification" — it's "can we put it where we can afford it."

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database as of a particular point in time — typically the transaction's start timestamp or the last committed value at read time. The reader sees a frozen version of the data for the duration of its read, so a concurrent writer can insert / update / delete rows without ever contending on the same locks the reader would need. The writer works in its own transaction, creating new row versions without touching the versions the reader is currently holding.

The garbage is **obsolete row versions** — every UPDATE creates a new version of the row and leaves the old one in place; every DELETE marks a row as removed but keeps the tombstone. These accumulate in the storage engine's version chain (common implementations: PostgreSQL's heap pages with `xmin`/`xmax` tuples, InnoDB's undo logs plus the rollback segment, or append-only B-tree leaf nodes). A background process — VACUUM in PostgreSQL, purge threads in InnoDB, compaction in append-only engines — must scan for versions that are no longer reachable by *any* active or future snapshot, then reclaim the space. If it stalls, the version chain grows unbounded, read performance degrades from having to skip dead tuples, and index bloat pushes working set past RAM.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Migrating a monolith to microservices means decomposing a single, unified application into independently deployable services, each owning its own data and communicating over a network. It's a structural and operational change, not just a code change.

The main risks:

**Domain boundary errors** — Cutting along the wrong seams (usually by technical layer instead of business capability) creates chatty, coupled services that defeat the purpose. The wrong boundary is the single most expensive mistake; it can virtually lock the system into a worse state than the original monolith.

**Distributed transaction complexity** — What was a local ACID transaction becomes a saga with compensating actions. Teams consistently underestimate how much this raises the cost of correctness. Eventual consistency is not a bug — but the application logic to handle it properly across N services often doubles surface area.

**Network as a new failure mode** — Latency, timeouts, retry storms, cascading failures (thundering herd, circuit breakers opening in a chain). The system now has an "unreliable network" baked into every call path. Most teams discover they've never actually handled partial failure before.

**Data decomposition pain** — Splitting a shared database into service-owned schemas means every query that previously JOINed now needs a fan-out pattern or API composition layer. The impedance mismatch between "my service owns this data" and "the feature needs to show it alongside data from three other services" is a constant tension point.

**Operational surface area explosion** — N services means N deployments, N monitoring dashboards, N logging streams to correlate, N credential rotations, N config files. The infrastructure cost (cognitive and financial) can swamp the business value if migration isn't accompanied by investment in observability and CI/CD tooling.

**The transient coupling trap** — You start with clean boundaries, then a deadline hits and a feature needs to cross two services. Quick solution: add a shared library. Then another. Then a shared database view for "just one thing." Six months later you have a distributed monolith — all the complexity, none of the independence.
