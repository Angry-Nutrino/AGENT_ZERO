### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic assumes conflicts are rare — you read, make changes, and only check for collisions at commit time. If the version changed, you roll back and retry. Good for low-contention systems, read-heavy workloads, or when you can afford occasional retries. The tradeoff is higher abort cost when conflicts do happen.

Pessimistic locks the row or resource upfront — no one else touches it until you're done. Good for high contention, write-heavy workloads, or when a failed transaction is expensive (financial systems, inventory, booking). The tradeoff is reduced concurrency and risk of deadlock.

Your system — billions of rows/month, analytics-heavy — is textbook optimistic territory. Low write contention per row, high throughput requirement, and retries are cheap. Pessimistic locking would be deadlock bait at your scale.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

They share the same memory space — threads within a process have their own stack and registers but share the heap, code, and file descriptors. A process has an isolated virtual address space — one crashing doesn't take down the others. Context switching between threads is cheaper because the TLB doesn't need flushing across threads in the same process.

**Multiprocessing** in Python bypasses the GIL entirely — you get true parallelism for CPU-bound work. Each process has its own GIL, so four cores mean four simultaneous Python executions. Use it for compute-heavy tasks: matrix multiplication, video encoding, web scraping across thousands of URLs. The cost is memory — each process duplicates the Python interpreter and imports. Inter-process communication requires pickle serialization (multiprocessing.Queue, Pipe) or shared memory via multiprocessing.shared_memory — both slower than thread-level shared state.

**Threading** in Python is for I/O-bound work where the GIL is released during blocking calls. The GIL is held during Python bytecode execution but released during I/O waits (sleep, socket.recv, file.read, database queries). On a single CPU core, threading can outperform async for workloads with blocking C extensions (numpy, pandas operations release the GIL). Threads share memory natively — a list append from two threads sees the same object, though you still need locks for mutation safety. The constraint: CPU-bound threads on multiple cores still run one at a time under the GIL.

**The hybrid pattern**: use multiprocessing for parallelism (distribute CPU work across cores) and threading for concurrency within each process (handle I/O without adding process overhead). For example, a web scraper spawning five processes, each running twenty threads — the processes parallelize DNS resolution and parsing across cores, the threads within each process overlap network waits.

### Q15 [CHAT] — Explain how Python's asyncio event loop runs many coroutines on a single thread, and what happens to the whole loop if one coroutine performs a long blocking CPU-bound computation. Answer from your training knowledge.

Single thread, cooperative multitasking. The event loop holds a queue of coroutines and drives them via `await`. When a coroutine hits `await`, it suspends — yields control back to the loop — which then switches to the next ready coroutine. No preemption; the coroutine has to voluntarily yield.

A CPU-bound coroutine that never awaits holds the thread hostage. The event loop can't switch to anything else — it's stuck in that coroutine's frame until it finishes or hits an `await`. The entire loop freezes. No heartbeat checks, no WebSocket pings, no background tasks, no other requests. Fix is `asyncio.to_thread()` or `loop.run_in_executor()` — yeet the CPU work into a thread pool so the event loop stays responsive.
