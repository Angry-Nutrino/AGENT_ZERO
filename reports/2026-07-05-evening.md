### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from three distinct sources layered on top of each other.

First is **compaction**. When an LSM-tree merges SSTables at level N into level N+1, every key-value pair in the input must be read, sorted, deduplicated, and written back out. Even if the data hasn't changed, it's rewritten. Leveled compaction amplifies this by ~10x per level on average (each level is 10× the size of the previous), so a write at L0 can be migrated through L0→L1→L2→...→L6, each time rewriting the data. Size-tiered compaction is gentler—amortized ~2-3x—because it merges within a level before moving up, but it trades for read amplification.

Second is **memtable flushing**. Writes are buffered in memory, then flushed as a single SSTable to L0. That flush writes the batch once. The ratio of this to total writes is negligible, but it's still one pass.

Third is **the write-ahead log** (WAL). Every write is written once to the WAL for durability before it touches the memtable. If you count that as a write, it's +1x right off the bat before compaction even starts.

The practical costs land in hardware you can feel:

- **SSD endurance.** Consumer TLC NAND is rated for 600–1500 write cycles. With 10-20× write amplification, what the application thinks is 100 GB/day of writes becomes 1-2 TB/day of actual flash wear. On a 512 GB drive at 1.5 TB/day, that's six months of endurance before cells degrade. Enterprise drives (3D XPoint, SLC cache) mask it with overprovisioning, but the physics doesn't change.

- **Latency spikes.** Compaction runs in background threads, competing with foreground reads for disk I/O. On HDDs, a compaction read causing a seek stalls user reads by 5–10 ms. On SSDs, the penalty is smaller but still present—NVMe queue depth saturation adds latency to P99 tail latencies. LevelDB and RocksDB throttle compaction for exactly this reason.

- **Memory pressure.** Bloom filters and block caches are sized to the working set. High write amplification means more compaction iterations per ingested byte, which means more block cache churn, which means more evicted pages, which means more reads hit disk. The read path degrades as a second-order effect of write amplification.

- **GC-induced cascade.** When compaction is backed up, L0 accumulates SSTables. Each read must check more files, increasing read amplification. The system enters a positive feedback loop: more read amplification → slower compaction → more L0 files → more read amplification. RocksDB has an L0 -> L0 trivial move optimization specifically to break this, but it only works if the SSTable boundaries align, which they often don't under random inserts.

The practical spread: LevelDB measures ~10-15× write amplification under leveled compaction with default settings. Cassandra with size-tiered compaction achieves ~2-3× but pays 50-100× read amplification for random lookups. RocksDB lets you tune between them with `level_compaction_dynamic_level_bytes`. There is no free lunch—LSM-trees exchange write throughput for read latency, and write amplification is the bill.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC lets readers avoid blocking writers by giving each transaction a snapshot of the database at a point in time — typically the transaction's start timestamp or the last committed state before it began. When a writer modifies a row, it doesn't overwrite the current value in place. Instead, it creates a new version of that row tagged with the writer's transaction ID. Subsequent reads see only the version that was current at their snapshot time, regardless of what writers do concurrently. The writer holds a lock only on the new version (to prevent conflicting writes), never on the old version that readers continue to see.

The garbage this creates is **dead row versions** — versions that are no longer visible to any active or future transaction. Each update or delete leaves behind a prior version that must eventually be removed. This accumulates as:

1. **Version chains** — rows linked backwards through older versions. Long chains make reads slower because each read must walk the chain to find the correct version for its snapshot.
2. **Table bloat** — dead tuples occupy space in the table's heap pages, inflating storage and degrading sequential scans.
3. **Index bloat** — index entries pointing to dead row versions aren't cleaned up immediately, so index scans touch pages that hold nothing useful.

PostgreSQL calls its cleanup **VACUUM** — a background process that marks dead tuples' space as reusable and updates the visibility map. It's not optional. If VACUUM falls behind, transaction ID wraparound becomes a hard stop: the database shuts down to prevent data corruption. MVCC trades write lock contention for a bounded amount of garbage that must be collected on a schedule, or the system stalls.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration is the process of breaking a monolithic application — where all functionality runs as a single, tightly-coupled deployment unit — into a set of independently deployable services that communicate over a network, each owning its own data and business domain.

The main risks:

**Network as the new primitive.** In a monolith, a function call is reliable and fast (~nanoseconds). In microservices, every call becomes a network round-trip — milliseconds, potentially flaky, subject to timeouts, retries, and cascading failures. Teams consistently underestimate the shift from local to distributed.

**Data consistency breaks.** A monolith uses a single database transaction. Microservices enforce service-owned data, which means distributed transactions are off the table. You now live in the world of eventual consistency, sagas, and compensating transactions — patterns that are significantly harder to reason about and debug.

**Coupling doesn't disappear — it moves.** The monolithic coupling between modules becomes runtime coupling between services. If services share a database, you've just added network latency to what was already coupled. If they share schemas via message contracts, versioning becomes a coordination problem that slows every team.

**Observability becomes mandatory.** In a monolith, a single log file and a stack trace tell you where the problem is. In a distributed system, a single user request fans out across N services — each with its own logs, metrics, traces. You need distributed tracing, structured logging, and centralized monitoring *before* you migrate, not after. Most teams add observability as an afterthought and pay for it in debugging time.

**Organizational Conway's Law trap.** If your engineering teams are organized around layers (frontend, backend, database), you'll naturally create microservices that mirror those layers — chatty, tightly-coupled, every cross-service call needing coordination. The inverse: services aligned to bounded contexts (product catalog, payments, fulfillment) reduce cross-team dependencies but require teams to own the full stack for their domain. This is a management change as much as a technical one.

**Premature decomposition.** The most expensive mistake is splitting before understanding where the actual seams are. A clean bounded context identified from real usage and domain modeling is cheap to extract. A service carved out because "it feels right" or "everyone else is doing it" creates years of coupling debt across service boundaries that don't actually align with the business domain.
