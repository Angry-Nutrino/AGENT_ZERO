### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

It comes from the fundamental data flow of an LSM-tree: every write is first buffered in a memtable, then flushed to an immutable SSTable on disk, then repeatedly merged with older SSTables during compaction. Each level of compaction reads back the data you just wrote, merges it with older versions, and writes it out again. So a single key-value insert at level 0 might be written to disk once on flush, then re-read and re-written through three or four compaction cycles as it descends to the base level. That's 5–10× write amplification per key by the time it settles.

The costs are real and not merely academic:

On consumer SSDs, write amplification accelerates wear to the NAND cells. A typical TLC SSD is rated for ~600–1000 program/erase cycles per cell. At 10× amplification, a drive that would survive 5 years of your workload might die in 6 months. This is why early RocksDB deployments on vanilla consumer hardware had a reputation for killing drives.

On the throughput side, compaction competes directly for disk I/O with incoming writes. A compaction burst can saturate the write bandwidth of a SATA SSD (~550 MB/s sequential). When that happens, the memtable fills faster than it can flush, writes stall, and your P99 latency spikes from microseconds to hundreds of milliseconds. This is the classic LSM write-stall pattern. The practical cost is that you overprovision either disk bandwidth or RAM by 2–3× to handle compaction without stalling the foreground write path.

On memory, every level beyond L0 requires bloom filters and block indexes loaded or cached to avoid reading every file on lookups. Those structures are sized proportional to the data — they don't cause amplification directly, but they make the total memory budget for a write-heavy LSM higher than an equivalent B-tree because you're paying for both the active working set and the compaction overhead structures.

In practice, the worst-case amplification is bounded by the size ratio between levels (typically 10× per level), so total amplification across N levels with tiered compaction is roughly (size_ratio ^ N - 1) / (size_ratio - 1). A 4-level LSM with 10× ratio gives about 111× for a full write from memtable to base level. Leveled compaction trades some of that for better read performance — typical numbers look like 5–15× depending on configuration. The tuning knob is compaction policy: write stalls are the system telling you you've pushed amplification too high for your hardware budget.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database at a point in time — the transaction's start timestamp or its assigned read-view identifier. Writes create new versions of rows rather than overwriting them in place, so a concurrent writer's changes go into a new version that is invisible to the ongoing snapshot. The reader never needs a lock on the writer's row because it simply traverses the version chain until it finds the entry whose visibility range includes its own read timestamp. Writer and reader proceed in parallel, each seeing their own consistent view.

The garbage is **dead row versions** — rows whose most recent committed version is too old to be visible to any open snapshot. Those accumulate in every index that points to them. PostgreSQL calls this bloat; the cleanup mechanism is `VACUUM`, which must both reclaim page space and prune index entries. The cost is real: a long-running read transaction delays cleanup because the system cannot safely remove versions still reachable by that snapshot, and bloat degrades cache locality and increases scan IO until vacuum catches up.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration is the process of decomposing a monolithic application into independently deployable services, each owning its own data and communicating over a network.

Main risks, from most destructive to most subtle:

**1. Distributed transaction failure.** The monolith had ACID guarantees via a single database. After splitting, a single user operation (say, "place order") now touches 3–6 services. You lose local transactions. The naive fix — distributed transactions (2PC, XA) — collapses under network partitions. The real answer is saga patterns with compensating transactions, but that shifts complexity from the database layer into application code, which is where most teams fail to handle partial failures correctly.

**2. Network becomes the new database.** Latency that was a 1ms in-process call becomes 10–100ms of serialized gRPC/HTTP. Teams don't account for this upfront. The result: chatty service-to-service calls that make the system slower than the monolith it replaced.

**3. Data consistency boundaries drawn wrong.** The most common error: splitting by organizational reporting lines ("team A owns this, team B owns that") instead of by business transaction boundaries. You end up with services that need to join across each other's databases constantly, which isn't possible without tight coupling, so you get denormalized caches that drift.

**4. Observability gap.** A monolith is one process — you log in one place, profile with one tool, trace a request by grepping a timestamp. After splitting, you need distributed tracing (OpenTelemetry), structured logging with correlation IDs, and metrics aggregation across N services. Most teams add this as an afterthought, then spend months in production fires with no way to tell which service is causing the cascade.

**5. Testing complexity explosion.** Integration tests that were "spin up the one app, hit the API" become "spin up every dependent service or their mocks". Teams compensate by testing each service in isolation and hoping the interactions work — they don't.

**6. Premature extraction.** Teams extract the wrong service first — something tightly coupled to the rest of the monolith — which creates the worst possible state: you've paid the migration cost (network, distributed state, new deployment pipeline) but gained none of the benefits because that service can't be deployed independently anyway.

The one rule that saves most migrations: start with something that can be extracted with its own database, that has clear domain boundaries, and that will immediately enable independent deployment velocity for some team. Everything else is optional.
