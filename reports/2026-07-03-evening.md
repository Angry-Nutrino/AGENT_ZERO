### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees has three distinct sources, each with a different cost profile:

**Where it comes from:**

1. **Level compaction** — Data is written once to the memtable, flushed to L0 as an SSTable, then rewritten up the tree as it merges into L1, L2, etc. A row may be written 10–50× depending on level count and compaction policy (size-tiered vs leveled). Each merge reads existing SSTables and writes new ones — that's the bulk of it.

2. **Compaction read-back** — During a merge, the engine must read all overlapping SSTables before it can produce the new output. Those reads are themselves I/O that wouldn't exist in a B-tree. SSD reads don't wear the media like writes do, but they consume bandwidth and latency budget.

3. **Bloom filter and metadata writes** — On every flush and compaction, the engine rewrites bloom filters, index blocks, and summary metadata for each new SSTable. Small in absolute terms, but multiplied across thousands of compactions per day.

**What it costs in practice:**

- **SSD endurance** — Consumer SSDs are rated for ~300–1500 TBW. A write amplification factor of 15× means every byte your application writes burns 15 bytes of NAND endurance. For write-heavy workloads (logging, time-series, metrics), this shortens drive lifespan significantly — I've seen LSM-backed databases burn through entry-level SSDs in under a year at ~50 MB/s sustained write.

- **CPU overhead** — Compaction threads consume CPU for sorting and merging. On an 8-core machine doing leveled compaction with 30 GB of incoming writes per day, compaction can use 1–2 full cores continuously. Burst compaction spikes will steal from query-serving threads unless you're careful with compaction thread pools.

- **Tail latency spikes** — When a compaction kicks off and thrashes the I/O queue, pending read requests see increased p99 latency. This is the hidden tax — your average latency looks fine, but the tail is what kills user experience. RocksDB's subcompaction (parallelizing a single level compaction across multiple threads) helps, but doesn't eliminate it.

- **Space amplification at peak** — Compaction needs room to write output before deleting input. In size-tiered compaction, peak storage usage can be 2–3× the logical data size. Combined with high write amplification, this makes capacity planning harder than a B-tree's predictable 1.1–1.5× overhead.

The trade-off is worth it for write-heavy, insert-mostly workloads because LSM-trees turn random writes into sequential ones — and sequential SSD writes are ~10× faster than random. You pay in endurance and CPU to get throughput. For read-heavy or update-in-place workloads, a B-tree is usually the more predictable choice.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database at the moment its transaction began — logically, a point-in-time view. Writes create new versions of the rows they touch without overwriting or removing the existing ones. The reader sees the old version as if nothing happened. No lock, no wait, no conflict.

The garbage is **old row versions** that no active snapshot still references. When every transaction that could have seen version N has committed or aborted, version N becomes dead — it occupies space in the storage engine (B-tree pages or append-only segments) and must be reclaimed. Two cleanup approaches:

- **PostgreSQL / InnoDB (tuple-level MVCC):** A background VACUUM or purge thread scans pages, removes dead row versions, and marks the space reusable. If this falls behind, table bloat sets in — same logical rows but spread across more pages, degrading cache efficiency and scan speed.

- **CockroachDB / FoundationDB (append-only / LSM-tree MVCC):** Compaction merges SSTable levels, discarding versions whose MVCC timestamps fall below the current garbage‑collection threshold. Uncompacted old versions waste disk and slow point lookups through tombstone pruning.

Same trade-off in both cases: the concurrency model trades space for no blocking, and that space debt compounds until amortized cleanup catches up.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application — where all functionality runs in a single process — into independently deployable services that communicate over a network, each owning its own data and lifecycle.

The main risks:

- **Network as the new reality.** What was an in-process function call becomes an unreliable network hop. Latency spikes, transient failures, and partial availability become normal. Most teams underestimate how much resilience machinery — retries, circuit breakers, timeouts, idempotency — they need to add just to stay where they were.

- **Data consistency becomes a distributed systems problem.** ACID transactions don't span services. The same logical operation — "place an order and deduct inventory" — now requires sagas, outbox patterns, or eventual consistency. Teams that ship a monolith split without solving this first end up with corrupted state and silent data loss.

- **The bounded context trap.** Teams often split along technical layers (separate frontend, backend, database into "services") instead of business domains. The result is a distributed monolith — all the pain of microservices with none of the autonomy. Correct decomposition requires understanding the bounded contexts in the domain, not the layers in the code.

- **Operational complexity multiplies.** One deployable becomes ten. One database becomes many. Monitoring, logging, tracing, CI/CD, secret management, container orchestration — every ops concern scales by the number of services, not by total code size. Teams that don't invest in platform tooling before the split drown in firefighting.

- **Premature extraction.** Extracting a service before its boundaries are stable guarantees future rewrites. The best migration strategy — and the one Kleppmann outlines — is to keep the monolith until the seams are known, extract only when the cost of staying coupled exceeds the cost of the network boundary.
