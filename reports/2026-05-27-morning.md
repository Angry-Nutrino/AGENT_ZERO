### Q01 [CHAT] — What is the difference between TCP and UDP? When would you use each one? Answer from your training knowledge â€” no web search.

TCP is a connection-oriented protocol. It guarantees delivery, maintains order, and handles retransmission of lost packets. UDP is connectionless — fire and forget. No guarantee of delivery, no ordering, no retransmission.

Use TCP when completeness and order matter more than speed: file transfers, email, web pages, database queries — anything where a dropped byte corrupts the entire payload.

Use UDP when latency is the constraint and occasional loss is acceptable: real-time video calls, online gaming, DNS lookups, live audio streaming. A single dropped frame in a video call is invisible. A single dropped TCP packet that stalls the stream for a retransmission round-trip is not.

Threshold rule of thumb: if you'd rather skip a packet than wait for it, you want UDP. If you'd rather wait for it than skip it, you want TCP.

### Q04 [CHAT] — What is gradient descent and why is it the standard optimization algorithm in machine learning? Answer from your training knowledge.

Gradient descent is a first-order iterative optimization algorithm that minimizes a function by moving parameters in the direction opposite the gradient — the vector of partial derivatives — scaled by a learning rate. At each step, you compute the gradient of the loss function with respect to the model's parameters, then update:  
`θ := θ − η · ∇_θ J(θ)`.

It's the standard in machine learning for three converging reasons:

1. **Scalability to high dimensions** — Closed-form solutions like the normal equation require inverting an n×n matrix (O(n³)). Gradient descent works with parameter counts in the millions because each step is O(n) and you only need to store the gradient, not a full Hessian or matrix inverse.

2. **Generalization beyond convex functions** — Ordinary least squares has a single minimum, so any solver works. Neural networks are non-convex with enormous parameter spaces. Gradient descent, with its variants (SGD, Adam), is one of the few algorithms that empirically finds useful minima in these landscapes. There's no closed-form solution for a 100M-parameter transformer loss surface; gradient descent is computationally tractable where alternatives aren't.

3. **Compositionality with automatic differentiation** — Modern frameworks (PyTorch, JAX, TensorFlow) compute gradients automatically via the chain rule on arbitrary computational graphs. That makes gradient descent a universal "plug this loss function in and optimize" engine. You don't need analytic derivatives for every new architecture — backpropagation + gradient descent is the generic solution.

Second-order methods (Newton's, L-BFGS) converge in fewer iterations but each iteration is far more expensive — computing or approximating the Hessian doesn't scale to deep learning's parameter counts. Gradient descent's per-iteration cost is constant in the model size, and its convergence, while linear, is good enough with modern momentum and adaptive learning rate schemes.

### Q16 [CHAT] — Explain what a context window is in large language models and why it matters for systems like CLARA.

We're live.

A context window is the maximum token budget the model can see in a single inference pass — the combination of user instructions, system prompt, memory, tool outputs, and model response combined. It's finite on every model. For CLARA running on a local model, this is the hard constraint your system must operate within.

What it means for you:

1. **Memory isn't free** — every sentence in your instruction prompt, every retrieved RAG chunk, every past interaction from episodic memory eats into the same budget. A 32K context window with a 2K response leaves 30K for everything else. That fills fast.

2. **Clip decisions are architectural** — when you reach the budget, something gets evicted. The question is what. If the system prompt is strict but a critical search result gets cut, the model hallucinates tool names. If memory gets cut mid-interaction, the model forgets what file it was writing to. The clipping strategy *is* the architecture.

3. **RAG isn't infinite recall** — retrieval gives you dense relevant information, but it still lands in the context. If your retrieval pipeline returns 10K tokens per turn and the budget is 16K, half of that is gone before the model generates a token. The retrieval strategy must account for what the model can *hold*, not just what's *relevant*.

4. **Contrasting with commercial models** — GPT-4 at 128K is a different regime. The constraints you face (presumably a 32K or 64K local model) mean you can't trade context for complexity. Every function call, every message chain, every tool output shape has to be measured against the budget.

The practical consequence: your memory architecture, tool schemas, and instruction prompt together define the *usable* context window for the model to think in. If those three take 10K, the model actually has 22K. Design the three, and the window sizes itself.
