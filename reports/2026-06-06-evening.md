But you're asking from training knowledge this round, so here it is:

**Horizontal scaling** — add more machines. **Vertical scaling** — add more resources (CPU, RAM, disk) to one machine.

**Horizontal tradeoffs:**
- Pro: Essentially infinite scale, higher fault tolerance (one node dies, the rest carry), commodity hardware
- Con: Application must be designed for distribution (state management, data consistency, coordination), operational complexity (orchestration, networking, monitoring), latency from network calls between nodes

**Vertical tradeoffs:**
- Pro: Simple to implement — no code changes needed, predictable performance, lower latency (shared memory), simpler operations
- Con: Hard ceiling (max CPU/memory on a single box), single point of failure, increasingly expensive at the high end (diminishing returns on premium hardware)

**Decision rule:** Default to vertical until you hit the ceiling, then go horizontal — but build the application for horizontal from day one so you don't have to rewrite later.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

**Primary key:** Uniquely identifies each row in its own table. One per table. Unique, non-null, immutable by convention.

**Foreign key:** A column (or set of columns) in one table that references the primary key of another table. Establishes and enforces the relationship between the two tables. Multiple per table, can be null, values must exist in the referenced primary key (or be null).

The distinction is directional — the primary key is *the thing being pointed to*; the foreign key is *the thing doing the pointing*. Together they enforce referential integrity: you cannot have a foreign key value that doesn't exist as a primary key on the other side, and you cannot delete a row whose primary key is still being referenced.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database at the instant its transaction began, using transaction IDs and a visibility map to decide which row versions are "visible" — the reader never takes locks, it just reads whatever committed state existed at its start time. A concurrent writer creates a new version of the row (copy-on-write) with its own transaction ID, never touching the old version the reader is still looking at. No lock contention, no reader-writer conflict.

The garbage is **dead row versions** — old versions that are no longer visible to any active transaction. Two kinds: expired versions (the transaction that created them committed long ago and no running transaction still needs that snapshot) and in-progress aborted versions (the writer rolled back, leaving an uncommitted row version no one will ever read). PostgreSQL calls this accumulation *bloat* and reclaims it via `VACUUM`, which marks the space as reusable. Left uncollected, bloat inflates table size, degrades index scans, and eventually forces the database to do more I/O per query than it should.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable, loosely coupled services that communicate over a network, each owning its own data and business capability.

The main risks:

1. **Premature decomposition** — splitting without understanding service boundaries leads to chatty inter-service calls, distributed monoliths, and constant coordinated changes. Data coupling is the hardest to untangle post-split.

2. **Distributed transactions** — the monolith's ACID guarantees vanish. You now handle eventual consistency, sagas, compensating transactions, and the failure modes of two-phase commit across network boundaries.

3. **Network as new failure domain** — latency, timeouts, retry storms, cascading failures, partial availability. Code that worked fine in-process breaks in new ways when every call can fail.

4. **Data ownership ambiguity** — multiple services reading from the same database or needing shared state creates coupling at the storage layer that defeats the purpose of the split.

5. **Operational surface area explosion** — one deployable becomes N. Monitoring, logging, tracing, CI/CD, configuration management, secrets, and incident response all multiply. Without investment in observability and deployment tooling, the team is drowning.

6. **Testing complexity** — integration testing across service boundaries requires contract testing, consumer-driven contracts, or running multi-service environments. The confidence you had from a monolith's end-to-end tests does not survive the split.

7. **Team coordination overhead** — when services are tightly coupled despite the split, every change requires a hallway conversation, a Slack thread, or a coordinated deploy window. The architecture must reflect the team's communication structure (Conway's Law — ignored at your peril).

The Strangler Fig pattern is the only safe approach — extract one bounded context at a time behind a facade, route traffic incrementally, validate in production, and keep the monolith alive as a fallback until a service is proven stable.
