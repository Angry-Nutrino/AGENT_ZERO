### Q01 [CHAT] — Explain the difference between a hash table and a binary search tree. What are the average time complexities for lookup, insert, and delete in each? Answer from your training knowledge.

### Hash Table

An associative array that maps keys to values using a **hash function** to compute an index into an array of buckets.

**Lookup: O(1)** average, O(n) worst-case (hash collision cascade)
**Insert: O(1)** average, O(n) amortized if resizing triggers rehash
**Delete: O(1)** average, O(n) worst-case

Key constraint: no inherent ordering. Iteration order is effectively random (dependent on hash function and bucket layout). Collision resolution strategy (chaining vs open addressing) determines worst-case behavior. Space overhead: typically 30–70% load factor ceiling, so allocated memory exceeds element count by 30–100%.

### Binary Search Tree

A hierarchical node structure where every node's left subtree contains only keys smaller than the node's key, and the right subtree only keys larger.

**Lookup: O(log n)** average, O(n) worst-case (degenerate chain)
**Insert: O(log n)** average, O(n) worst-case
**Delete: O(log n)** average, O(n) worst-case

The worst-case O(n) applies to an **unbalanced** BST where insertion order creates a linear chain. **Self-balancing variants** (AVL, Red-Black) enforce height constraints, guaranteeing O(log n) across all operations. Traversal yields sorted order — an O(n) operation that hash tables cannot do.

### The operational difference

Hash tables win on raw speed for point queries if you have a good hash function and adequate capacity. BSTs win when you need **range queries** (keys between X and Y), ordered iteration, or when worst-case guarantees matter more than average-case speed. The BST's O(log n) is constant regardless of data distribution — a hash table's O(1) average depends on uniform key distribution and collision resistance. If your keys form patterns that collapse into the same bucket, the hash table degrades to O(n) while a balanced BST stays at O(log n).

### Q04 [CHAT] — What is the difference between optimistic and pessimistic locking in databases? When would you use each one? Answer from your training knowledge.

Optimistic locking assumes conflicts are rare. You read the data without acquiring locks, make your changes, and at commit time check if the version or timestamp has changed since the read. If it has, the transaction aborts and retries. Pessimistic locking assumes conflicts are likely and locks the record at read time — no one else touches it until the transaction commits or the lock is released.

**When to use each:**

- **Optimistic** — read-heavy workloads, low contention, or systems where latency matters. Classic case: content management, product catalogs, user profiles. The retry cost is tolerated because collisions are infrequent. Also works well when connections are short-lived or transaction duration is unpredictable.
- **Pessimistic** — high contention on specific rows, write-heavy operations where retries are expensive, or when the operation side effects are irreversible once started. Classic case: inventory systems, ticket booking, banking transfers where two transactions can't concurrently reduce the same balance.

The tradeoff comes down to conflict probability × retry cost. If either is high, go pessimistic. If both are low, optimistic wins on throughput. There's no universally correct choice — only the one matched to your contention pattern.

### Q10 [CHAT] — What is a memory leak, and what are three common causes of memory leaks in long-running programs? Answer from your training knowledge.

A memory leak is when a program allocates memory from the heap but fails to release it back to the operating system after it's no longer needed, causing the program's resident set size to grow monotonically until it exhausts available memory or triggers an OOM kill by the kernel's OOM killer.

Three common causes in long-running programs:

1. **Forgotten references in long-lived collections** — objects added to a static list, cache, or global registry that are never removed, even after the logical owner is done with them. The garbage collector cannot reclaim them because the collection holds a transitive reference root. This is the most common leak in managed languages like Java, C#, and Python.

2. **Event listener / callback accumulation** — registering observers, signal handlers, or closures without unregistering them when the subscriber's lifetime ends. The publisher holds a strong reference to the listener, preventing its entire object graph from being collected. Common in GUI frameworks, pub/sub systems, and dependency injection containers.

3. **Unclosed external resources** — opening file handles, database connections, network sockets, or GPU allocations without deterministic cleanup. In languages without automatic RAII (Python, Java pre-try-with-resources), a missing `close()` or `dispose()` in the error path or early return leaks both the OS resource handle and any Native heap memory backing it. The GC may never run on the wrapper object, and even if it does, finalization is non-deterministic.
