### Q01 [CHAT] — What is the difference between a monolithic and a microservices architecture? What are the main tradeoffs? Answer from your training knowledge.

Monolithic architecture means the entire application runs as a single process — one deployment unit, one codebase, one database. Microservices decomposes the system into independently deployable services, each owning its own data and communicating over a network.

Tradeoffs:

**Monolithic wins:** Simple development and debugging (single process, local calls), straightforward deployment (one artifact), low operational overhead, strong data consistency via transactions, fast inter-service communication, no network latency between components.

**Monolithic loses:** Scaling must be horizontal for the entire app even if only one component needs it, deployment risk is all-or-nothing, codebase coupling makes teams step on each other, any change means rebuilding and redeploying everything, technology lock-in is absolute.

**Microservices wins:** Independent scaling per service, independent deployment and release cycles, team autonomy (own service, own data, own tech stack), failure isolation (one service down doesn't bring down the system), technology heterogeneity, each service can be optimized independently.

**Microservices loses:** Network latency and failures become first-class problems, distributed data consistency requires sagas or event sourcing instead of ACID transactions, operational complexity explodes (service discovery, monitoring, logging aggregation, container orchestration), debugging requires tracing across service boundaries, eventual consistency means stale reads are a design constraint, organizational alignment must match service boundaries or you get distributed monolith.

The decision rule is straightforward: start monolithic. Extract services only when concrete constraints force it — a team can't ship because of code coupling, a component needs different scaling characteristics, a technology lock-in is blocking. Premature microservices trade simple problems for complex ones without justification. Every published microservices horror story starts with "we decomposed before we needed to."

### Q10 [CHAT] — What is the difference between symmetric and asymmetric encryption? When is each typically used? Answer from your training knowledge.

Symmetric encryption uses a single shared key for both encryption and decryption — same key in, same key out. Asymmetric encryption uses a public-private key pair: one encrypts, the other decrypts, and they are not interchangeable.

**Symmetric** is used for bulk data encryption where speed matters — file encryption, disk encryption (AES-256 for BitLocker, LUKS), database column encryption, TLS session encryption once the handshake is done. Fast, but key distribution is the problem.

**Asymmetric** is used for key exchange, digital signatures, and authentication — HTTPS handshakes (RSA or ECDH key exchange), SSH, PGP, certificate signing, blockchain wallets (ECDSA). Solves key distribution, but 100-1000x slower than symmetric.

**Real systems use both together**: asymmetric to exchange a temporary session key, then symmetric for the actual data. That's how TLS works, how Signal's double-ratchet works, how any sane encryption protocol works.

### Q15 [CHAT] — Explain how Python's asyncio event loop runs many coroutines on a single thread, and what happens to the whole loop if one coroutine performs a long blocking CPU-bound computation. Answer from your training knowledge.

Python's asyncio event loop runs on a single thread via cooperative multitasking. It maintains a queue of scheduled coroutines and ticks through them by calling each one's `__next__` or `send(None)` — the coroutine runs until it hits an `await`, at which point it suspends, yielding control back to the loop along with an awaitable object (typically a Future). The loop registers a callback on that Future, then picks the next ready coroutine from its queue. This works because every `await` is an explicit yield point — the coroutine promises to suspend, and the loop promises to resume it once the awaited operation completes. All I/O (sockets, file descriptors, timers) goes through the loop's epoll/select/kqueue selector, so the loop can service hundreds or thousands of connections by switching between coroutines that are waiting on I/O, never blocking on any single one.

If a coroutine performs a long CPU-bound computation without `await` points — e.g., a tight loop, a big matrix multiplication, a cryptographic hash — the entire event loop freezes for the duration. No other coroutine runs, no I/O is processed, no timers fire, no new connections are accepted, and any queued callbacks pile up. The loop is literally stuck in that coroutine's `__next__` call because the coroutine never hit `await` to return control. The fix is to explicitly yield control periodically with `await asyncio.sleep(0)` inside the computation, or — much better — offload the CPU-bound work to a thread pool via `loop.run_in_executor(None, blocking_func)`, which moves it off the event loop thread entirely.
