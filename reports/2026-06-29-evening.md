### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the simple fact that the same data is written multiple times over its lifetime. Each insert hits the write-ahead log, then the in-memory memtable, then gets flushed as a sorted SSTable — and then, piece by piece, a compaction picks it up again and merges it into larger runs.

There are three concrete sources:
- **Flush:** The memtable is written to disk as a new SSTable.
- **Compaction (leveled):** SSTables are merged from one level to the next, reading old data and writing merged output.
- **Compaction (size-tiered):** Smaller SSTables are merged into larger ones as they reach a size or count threshold.

The cost in practice isn't just extra I/O — it's a direct trade against read performance. On a leveled LSM (RocksDB default, LevelDB), write amplification runs 10x to 30x: every 1 GB of user data written triggers 10–30 GB of actual disk writes from compaction. This eats into SSD endurance (TBW rating becomes a real ceiling under heavy write workloads) and consumes write bandwidth that could go to user traffic. On a size-tiered approach (Cassandra default, older HBase), write amplification is lower — 4x to 10x — but read amplification climbs because more files must be consulted per query.

The textbook cost breakdown from the RocksDB team's measurements (Mark Callaghan's work): leveled compaction at 10x is considered efficient; 30x+ is degraded and usually comes from a poor level ratio or too-small L0 files. The practical constraint is that once compaction cannot keep up with the ingest rate, write stalls begin — the system pauses writes to let compaction catch up, which is where throughput collapses.

LSM-trees absorb this cost because it buys sequential writes. The fundamental insight: random writes to a B-tree cost a random I/O per page modified; an LSM batching those writes and compacting sequentially can sustain far higher write throughput on spinning disks and consumer SSDs alike. You pay in write amplification, you gain in sustained ingest rate and compression efficiency.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a snapshot of the database as of the moment its transaction began. Writes create new versions of rows — they don't overwrite the old ones in place. The reader's snapshot query sees the version that existed when its transaction started, so it doesn't need locks and doesn't block the writer that's busy creating the next version of the same row.

The garbage is old row versions that are no longer visible to any active transaction — two kinds:

1. **In-row old versions** — PostgreSQL stores them in the same table pages (dead tuples); MySQL/InnoDB keeps them in a separate undo log. Either way, they accumulate in the buffer pool, consuming memory and bloating index scans.

2. **Transaction ID wraparound** — Each new version tags its row with a monotonically increasing transaction ID. The counter is finite (32-bit in PostgreSQL). If old rows holding ancient XIDs are never cleaned, the counter wraps and suddenly "old" looks "new" — data becomes invisible or corrupt. This is why `VACUUM` is mandatory, not optional.

The cleanup is a background process: PostgreSQL's autovacuum marks dead tuples as reusable space; MySQL's purge thread sinks undo log entries once no transaction needs them. If the cleaner falls behind, the database degrades — table bloat, performance cliff, then forced downtime to run `VACUUM FULL` or rebuild.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration is the process of decomposing a monolithic application into independently deployable services that communicate over a network, each owning its own data and domain logic.

The main risks when splitting a monolith:

1. **Network fallacies** — Services that communicated via in-process calls now face real latency, partial failure, and network partitions. Timeouts, retries, and circuit breakers are no longer optional; they're structural requirements.

2. **Distributed data consistency** — The monolith's ACID transactions across bounded contexts become distributed sagas or event-driven eventual consistency. No two-phase commit over HTTP. You trade strong consistency for availability and partition tolerance, and that trade hits hardest at the seams between services.

3. **Coupling via shared infrastructure** — Teams extract services but keep sharing the same database, schema, or queue topology. You get the operational complexity of microservices with none of the independence. That's the worst outcome: distributed monolith.

4. **Boundary errors** — Splitting along technical layers (controllers, services, repositories) instead of business domains. The result: chatty services that can't be deployed independently because they depend on each other's internal representations. Domain-driven design's bounded contexts exist specifically to prevent this.

5. **Operational surface area explosion** — One deployable becomes ten. Monitoring, logging, tracing, CI/CD pipelines, configuration management — all multiply. If the observability investment doesn't match the migration velocity, you're debugging blind.

6. **False granularity** — Splitting too early, before understanding the actual coupling patterns. A monolith that's well-structured internally is easier to evolve than a distributed system with wrong boundaries. The right first step is almost always "extract the smallest independently useful service and validate the operational model before doing another."
