### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic concurrency control assumes conflicts are rare. You read data, perform work, and only check for conflicts at commit time — if another transaction modified the same data since you read it, you roll back and retry. No locks held during the work phase. Pessimistic concurrency control assumes conflicts are common enough that you lock the data before touching it (read locks, write locks, range locks) and hold those locks until the transaction finishes.

**Optimistic is the right choice when:**
- Low contention — most transactions don't touch the same rows
- Read-heavy workloads where conflicts are genuine exceptions
- You can tolerate and recover from rollbacks cheaply
- Your contention window is short (read-to-commit gap is milliseconds, not minutes)
- Distributed systems where distributed locks are expensive or unavailable — optimistic avoids the coordination overhead

**Pessimistic is the right choice when:**
- High contention — many transactions compete for the same rows (booking systems, inventory, financial ledgers)
- Conflict cost is high — a rollback means real money or reputational damage
- Write skew must be prevented — optimistic CC can't detect phantom reads or certain write-skew patterns without range locks
- Transactions are interactive and long-running — the time between read and write is large, making optimistic retries wasteful
- You need strong isolation guarantees (serializable) with predictable latency

CLARA uses pessimistic locking for the vault write guard — the contention window is nanoseconds in practice, but the cost of a silent corruption from a race condition is absolute. When autonomy dispatches multiple tasks to the same memory file, the correct move is to serialize. Optimistic would mean silent rollback cascades in the data path — not acceptable.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

A process has an isolated virtual address space — heap, code, data, file descriptors, everything — while threads share the address space, file descriptors, and signal handlers within a single process. Each thread gets its own stack, registers, program counter, and errno; context-switching between threads is cheaper because they share the same page tables and TLB, whereas switching processes requires an MMU flush.

For Python specifically, the GIL is the deciding factor. CPU-bound work in CPython runs one thread at a time, so threading gives you no parallelism — only concurrency for I/O-bound tasks where the GIL is released (network calls, disk reads, sleeps). Multiprocessing sidesteps the GIL entirely by forking separate interpreters, making it the right choice for CPU-bound computation. The tradeoff is cost: processes have higher memory overhead (each has its own Python runtime) and IPC is heavier than shared-memory coordination between threads.

You use threading when the bottleneck is waiting — HTTP requests, database queries, file I/O. You use multiprocessing when the bottleneck is the CPU — matrix operations, data transforms, model inference. For the mixed case where you need both throughput and compute, the pattern is a thread pool feeding a process pool via a queue.

### Q11 [DELIBERATE] — In core_logic/event_queue.py, events are stored in the asyncio.PriorityQueue as a 3-tuple so higher-priority events sort first. Give the three elements in order, and say what the middle element does for equal-priority events.

The three elements, in order:

1. **`1.0 - event.priority`** — priority inverted so the min-heap sorts higher-priority events to the front.
2. **`self._counter`** — a monotonically increasing integer that breaks ties when two events have the same priority.
3. **`event`** — the `Event` dataclass instance itself.

The middle element (`self._counter`) exists because `asyncio.PriorityQueue` wraps a **min-heap**, and Python's `heapq` compares tuples element-by-element. If two events have identical priority, the first tuple element ties — without a counter, the heap would fall through to comparing the `Event` dataclass directly, which is **not** comparable and would raise a `TypeError`. The counter guarantees FIFO order for equal-priority events: the one emitted first gets a lower counter value and is popped first.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the long end of the distribution — the 1 in 1000 requests that takes 5 seconds while the median finishes in 50ms.

Average latency conceals the real experience because every user hits tail requests. A single service at p50=50ms and p99=1s looks manageable on paper, but chain that across 20 microservices: each user's request touches all of them, and the probability of hitting *at least one* p99 slowdown per request becomes 1 - (0.99^20) ≈ 18%. Almost one in five requests is slow. Drops that rate to p99=200ms and the same chain gives you 1 - (0.998^20) ≈ 4% chance of a slow request. That's the difference between a product feeling "snappy" versus "why is this always loading."

The dominant technique is **hedged requests** — send the same request to two replicas, use whichever responds first, cancel the other. Amazon and Google use this at scale. It converts p99 tail into ~p50+p50 latency (two fast copies competing, so you almost always get the faster one's response time) at the cost of 2x outgoing load. The variants (tied requests for non-idempotent operations, backup requests after a small delay) reduce that cost while still capping the tail.

One number tells you the system is working. The other tells you whether users think it is.

### Q20 [DELIBERATE] — In core_logic/mcp_client.py, each MCP server's state keeps `command` and `args` (beyond process/lock/id_counter). What recovery does retaining them enable, and what failure mode did it fix?

Retaining `command`/`args` lets the client recreate the subprocess without requiring external config re-supply.
