### Q03 [CHAT] — Explain what a race condition is and how a lock prevents it. Give a concrete example. Answer from your training knowledge.

A race condition occurs when the correctness of a program depends on the timing or interleaving of concurrent operations. If two threads (or processes) read and write a shared resource without synchronization, the final state depends on which one finishes last — and that order is unpredictable.

**How a lock prevents it:**
A mutex (mutual exclusion lock) wraps the critical section — the code that reads and then writes the shared state — so that only one thread can execute it at a time. The second thread waits at the boundary until the first releases the lock. This turns an interleaved, unpredictable sequence into an atomic, serialized one. The shared state is never observed mid-write.

**Concrete example (the vault dedup bug we fixed):**

Two requests arrive simultaneously. Both call `memorize_episode` with the same text.

1. **Thread A checks vault** — sees fact doesn't exist (empty or below cosine threshold).
2. **Thread B checks vault** — sees the same, because A hasn't written yet.
3. **Thread A writes** — inserts fact.
4. **Thread B writes** — inserts the same fact again.

**Result:** Duplicate entries. No correctness violation in the individual reads, but the combined outcome is wrong.

**With a `threading.Lock`:**

1. **Thread A acquires lock** → checks vault (empty) → writes fact → releases lock.
2. **Thread B acquires lock** → checks vault (now has fact at exact string match or above 0.85 threshold) → skips write → releases lock.

The lock ensures exactly one write. The dedup check is performed against the authoritative, up-to-date state because no other thread can interleave between the read and the write.

### Q04 [DELIBERATE] — Read core_logic/crud.py. How does _save_memory write the file atomically? Quote the lines that write the temp file and replace the original.

The `_save_memory` method in `core_logic/crud.py` writes atomically by (1) creating a unique temp file via `tempfile.mkstemp` in the same directory as the target, (2) writing the full JSON dump to it, flushing and fsyncing, then (3) replacing the original with `os.replace` — which is atomic on both Windows and POSIX. If the process dies mid-write, the live `memory.json` is untouched; the worst case is an orphan `.tmp` that gets cleaned up.

Here are the exact lines:

**Temp file creation and fsync (lines 60–65):**
```python
fd, tmp = tempfile.mkstemp(prefix=".memory.json.", suffix=".tmp", dir=d)
with os.fdopen(fd, 'w', encoding='utf-8') as f:
    json.dump(self.memory, f, indent=2, ensure_ascii=False)
    f.flush()
    os.fsync(f.fileno())
```

**Atomic replace with Windows retry (lines 69–79):**
```python
for attempt in range(10):
    try:
        os.replace(tmp, self.filepath)
        tmp = None
        break
    except PermissionError:
        time.sleep(0.02 * (attempt + 1))
else:
    print("❌ Failed to save memory: target locked after retries.")
```

Key design choices baked into the implementation:
- **Unique temp name per call** via `mkstemp` — two concurrent saves (e.g. background `memorize_episode` and autonomous `log_system_episode`) get separate temp files and won't interleave on the same path. A shared temp name would corrupt despite `os.replace`.
- **fsync before replace** — guarantees the data is on physical media before the swap, so a power failure after replace leaves a complete file rather than a partially-written one.
- **10 retries with linear backoff on PermissionError** — Windows raises `ERROR_SHARING_VIOLATION` when another handle has `memory.json` open (e.g. the `/soul` endpoint or a harness `python_repl` reading it concurrently). The retry loop recovers writes that would otherwise drop silently under concurrent reads.
- **Cleanup in finally**: if `os.replace` succeeded, `tmp` is set to `None` so the orphan cleanup skips it. If all retries failed, the temp file is removed to avoid accumulation.

### Q05 [CHAT] — What is the difference between SQL and NoSQL databases? When would you pick each one? Answer from your training knowledge.

SQL and NoSQL databases differ fundamentally in data model, consistency guarantees, and scaling approach.

**SQL (Relational):** Fixed schemas, tables with rows and columns, ACID transactions (atomicity, consistency, isolation, durability). Strong consistency — when a write completes, every subsequent read sees it. Vertically scalable (bigger server). Examples: PostgreSQL, MySQL, SQLite.

**NoSQL:** Flexible or schemaless, four main types — document (MongoDB), key-value (Redis), column-family (Cassandra), graph (Neo4j). BASE model (Basically Available, Soft state, Eventually consistent) — trades immediate consistency for availability and partition tolerance. Horizontally scalable (more servers). No joins — data is denormalized or queried differently.

**Pick SQL when:**
- Data has clear relationships and joins are unavoidable (inventory→orders→customers)
- You need ACID guarantees — financial transactions, booking systems, anything where partial writes are unacceptable
- Schema is stable and known upfront — you're not rediscovering the data shape every sprint
- You need complex queries, aggregations, reporting — SQL is decades ahead of NoSQL here

**Pick NoSQL when:**
- Schema is unpredictable or evolving rapidly — IoT sensor data, user-generated content with varying fields
- You need horizontal scale beyond what a single SQL instance can handle — millions of writes per second
- The data model maps naturally to the storage type — social graphs to Neo4j, session caches to Redis, time-series to Cassandra
- You're willing to handle consistency at the application layer and can tolerate eventual consistency

The common mistake is treating it as dogma. The correct answer for most projects is PostgreSQL for transactional data and Redis for caching — they solve different problems and coexist in the same stack.

### Q08 [CHAT] — Explain the difference between depth-first search and breadth-first search. When is each preferable? Answer from your training knowledge.

**Depth-First Search (DFS)** explores as far down a branch as possible before backtracking. It uses a stack (LIFO) — either explicitly or via recursion. **Breadth-First Search (BFS)** explores all neighbors at the current depth before moving deeper. It uses a queue (FIFO).

**When each is preferable:**

**DFS is better when:**
- You only need to check *if* a path exists, not find the shortest one
- Memory is constrained — BFS can explode in wide graphs; DFS's stack grows with depth
- You need topological sorting (DAGs) or cycle detection
- The solution is likely deep in the tree and the branching factor is high
- You're doing exhaustive search and can prune with backtracking constraints (e.g., Sudoku, N-Queens)

**BFS is better when:**
- You need the *shortest path* in an unweighted graph — BFS guarantees minimal edge count
- The solution is close to the root (shallow) — BFS will find it without descending deep branches
- The graph is infinite or very deep but shallow solutions exist (DFS could get lost)
- You're implementing web crawling or social network "degrees of separation" queries

**Key tradeoff:** BFS guarantees optimality on unweighted graphs at the cost of O(b^d) memory (where b = branching factor, d = depth of solution). DFS uses O(d) memory but may find a suboptimal path or get stuck in infinite branches without proper depth limiting.
