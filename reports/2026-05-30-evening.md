### Q03 [CHAT] — Explain what a race condition is and how a lock prevents it. Give a concrete example. Answer from your training knowledge.

A race condition occurs when two or more concurrent operations access shared state, and the final outcome depends on the unpredictable timing of their execution — specifically, when at least one operation is a write and the ordering of reads and writes overlaps in a way that can produce incorrect results.

A lock prevents it by enforcing mutual exclusion: it serializes access to a critical section so that only one thread or coroutine can read or modify the shared state at a time. The lock's acquire guarantees that any other contender sees either the state before the write or the state after — never a partial or interleaved intermediate.

Concrete example from the vault dedup code: two concurrent requests arrive to memorize the same new fact. Both check the vault — it's empty. Thread A doesn't find a match; Thread B doesn't find a match. Both write the fact, producing a duplicate. With `_vault_lock`, Thread A acquires first, checks *within the lock*, writes the fact, and releases. Thread B acquires next, but now the vault contains the fact, the cosine check returns a match, and the write is skipped. One copy survives. Without the lock, the window between check and write corrupts the invariant.

### Q05 [CHAT] — What is the difference between SQL and NoSQL databases? When would you pick each one? Answer from your training knowledge.

SQL databases are relational — they organize data into fixed-schema tables with rows and columns, enforce ACID transactions (Atomicity, Consistency, Isolation, Durability), and use Structured Query Language for access. NoSQL databases are non-relational and typically sacrifice strict consistency for scale or flexibility — they fall into four main types: document stores (MongoDB), key-value stores (Redis), column-family stores (Cassandra), and graph databases (Neo4j). Each NoSQL type has its own query model, and most are eventually consistent by default.

---

**Pick SQL when:**
- Your data is highly structured and relationships between entities are central (users, orders, products).
- You need strong consistency guarantees — financial transactions, inventory systems, any domain where a stale read is a bug.
- Your schema is stable and migrations are infrequent.
- You need ad-hoc querying across arbitrary joins.

**Pick NoSQL when:**
- You need horizontal scaling across many nodes — SQL can do this (sharding, read replicas), but NoSQL was designed for it from day one.
- Your schema is unpredictable or evolves constantly — document stores let different records have different fields.
- You're handling very high write throughput or low-latency key-based lookups — Redis can do millions of ops/second in-memory.
- Your data model is inherently a graph — social connections, recommendation engines, supply chains. SQL can model this with recursive CTEs and join tables, but it becomes painful beyond a few hops.

---

The choice is rarely absolute. Most production systems use both — PostgreSQL for the transactional core, Redis for caching/sessions, maybe a document store for semi-structured logs or content. The question isn't which database to use. It's which problem you're solving and what you're willing to trade.

### Q08 [CHAT] — Explain the difference between depth-first search and breadth-first search. When is each preferable? Answer from your training knowledge.

DFS and BFS are the two fundamental graph traversal strategies. DFS goes deep before wide — it explores a branch to its end before backtracking. BFS goes wide before deep — it explores all neighbors at the current depth before going deeper.

**DFS** uses a stack (LIFO). It's preferable when:
- You need to check existence of a path quickly (mazes, puzzles)
- Memory is constrained — DFS only stores the current path, not the entire frontier
- Topological sorting, detecting cycles, or solving problems with recursion-friendly structure
- You want to visit every node and don't care about shortest path

**BFS** uses a queue (FIFO). It's preferable when:
- You need the shortest path in an unweighted graph (GPS routing, social network degrees of separation)
- The graph is infinite or very deep but shallow solutions exist
- Finding all nodes within a certain distance
- Web crawlers — you want to stay close to the seed URL

**Tradeoff**: BFS guarantees shortest path but uses more memory (stores the frontier, which grows exponentially with depth in dense graphs). DFS uses the least memory of any graph traversal but doesn't guarantee shortest path and can loop infinitely in cyclic graphs without visited tracking. Both are O(V+E) time, but BFS's memory footprint is the key constraint in practice (O(width) for BFS vs O(depth) for DFS).
