### Q01 [CHAT] — What is the difference between asyncio.gather and asyncio.create_task in Python? When would you use each one? Answer from your training knowledge.

`asyncio.gather` runs a fixed set of awaitables concurrently and returns a single coroutine that waits for all of them to complete, collecting results in order. `asyncio.create_task` schedules a coroutine onto the event loop immediately and returns a `Task` handle — the task runs in the background regardless of whether you await it.

Use `gather` when you have a known, finite set of coroutines and you need all their results before proceeding. It's cleaner for fire-and-collect: results arrive as a list, exceptions can be collected with `return_exceptions=True`, and you can pass multiple coroutines directly.

Use `create_task` when you need fine-grained control over individual task lifecycles — cancelling selectively, checking `.done()` before awaiting, or firing off tasks that should run independently while the caller continues executing other logic. It's also the right choice for dynamic workloads where the set of tasks isn't known upfront, since you can create them one at a time in a loop without restructuring your code into a single `gather` call.

The critical distinction: `gather` is declarative and collective, `create_task` is imperative and per-task. If you don't need per-task handles or staggered scheduling, `gather` is simpler and less error-prone. If you do, `create_task` is the only option.

### Q04 [CHAT] — Explain the CAP theorem in distributed systems. What are the three guarantees and why can a system only ever satisfy two of them at once? Answer from your training knowledge.

Consistency — every read receives the most recent write or an error. Availability — every request receives a response, without guarantee that it contains the most recent write. Partition Tolerance — the system continues to operate despite arbitrary message loss or failure between nodes.

A system can only satisfy two because network partitions are unavoidable. You don't choose *whether* to tolerate partitions — you choose what happens when they occur:

- **CP (Consistency + Partition Tolerance):** During a partition, you stop serving requests from nodes that can't confirm the latest write. You preserve consistency but sacrifice availability — the system returns errors until the partition heals.
- **AP (Availability + Partition Tolerance):** During a partition, all nodes continue serving requests independently. You preserve availability but sacrifice consistency — two clients reading from different nodes during a split may see different data.
- **CA (Consistency + Availability):** Only possible if partitions never happen. Since partitions are a physical reality of distributed networks (packet loss, node crashes, network cuts), this is a theoretical artifact, not a deployable choice. Any real distributed system that claims CA is actually CP or AP, it just hasn't hit a partition yet.

The theorem is often misstated as "pick any two." The correct reading: **P is mandatory. You choose between C and A when P happens.**

### Q10 [CHAT] — What is the difference between a mutex and a semaphore? When would you use each one? Answer from your training knowledge.

A mutex is a binary lock with ownership — the thread that acquired it must release it. A semaphore is a counter with no ownership; any thread can increment (post) or decrement (wait), making it a signaling mechanism, not strictly a lock.

Use a mutex when protecting a shared resource from concurrent access — one writer, exclusive access, same thread locks and unlocks. Use a counting semaphore when managing access to a finite set of identical resources (e.g., 5 database connections in a pool) or for producer-consumer patterns where one thread signals another that work is available. A binary semaphore can replicate mutex behavior but lacks ownership enforcement, so it's weaker — you'd choose it only if you intentionally need cross-thread release semantics.
