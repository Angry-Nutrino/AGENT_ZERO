### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-tree engines is the ratio of total bytes written to storage divided by the bytes the application asked to write — a measure of how much redundant I/O the engine performs internally for each logical write.

**Where it comes from:**

- **Compaction.** LSM-trees defer writes to immutable sorted runs, then merge them in the background. Each key-value pair is rewritten multiple times as it moves through levels — Level-0 to Level-1 compaction might rewrite every pair, then Level-1 to Level-2 re-rewrites a subset, and so on. The write amplification factor is roughly `L * T / (T - 1)` where `L` is the number of levels and `T` the size ratio between levels (the classic formula from LevelDB/RocksDB literature). A typical 10-level tree with a 10× size ratio pushes amplification close to 10–15× on the coldest levels.

- **Double-write at ingest.** A write first hits the write-ahead log (WAL) for durability, then the memtable, then gets flushed to a sorted run. That's already writing the data twice before compaction even starts.

- **Fragmentation and tombstone propagation.** Deletes and overwrites leave tombstones that must be carried through compaction levels until the compacted output finally drops the dead key. During those intermediate merges the data is rewritten even though it's logically dead.

**What it costs in practice:**

- **SSD endurance.** Consumer-grade TLC NAND drives are rated for ~600–1500 program-erase cycles. A write amplification of 20× means that a logical 1 TB written consumes 20 TB of physical writes, eroding the drive's useful life proportionally. For write-heavy workloads (metrics ingestion, time-series logging), this is often the bottleneck that kills drives within a year rather than five.

- **Throughput ceiling.** Even if the SSD has spare endurance, write amplification consumes I/O bandwidth. A single 200 MB/s sequential write stream can appear as 2–4 GB/s of internal writes during a major compaction, saturating the device and starving foreground reads. This is why compaction throttling exists in RocksDB — without it, P99 read latency spikes badly during compaction bursts.

- **CPU and memory pressure.** Compaction is CPU-intensive: merging sorted runs requires comparison of keys and computation of new blocks. High write amplification means more compaction work per ingested byte, competing with query execution for cores and page cache.

- **Space amplification tradeoff.** Reducing write amplification typically requires making levels smaller or merging less aggressively, which increases space amplification (more stale data on disk before it's cleaned). The tuning knob is the size ratio between levels — higher ratio reduces write amplification at the cost of more space wasted by obsolete versions. There's no free lunch.

Practical numbers: LevelDB/PebblesDB tuned for 10–20× on HDD-centric workloads; RocksDB with tiered compaction and blob files can get down to 4–8× for large-value workloads; Cassandra's leveled compaction strategy targets ~10×, while its size-tiered compaction often exceeds 20–30× on heavily updated workloads. Each point of amplification shaves roughly proportional lifetime off flash storage and subtracts linearly from sustainable write throughput.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC decouples readers from writers by keeping multiple physical versions of each row at different transaction timestamps. A reader sees the database as it existed at its snapshot time — either its transaction start time or statement start time — by following a version chain that stops at the first version committed before that snapshot. The writer creates a new version of the row with its own write timestamp; the new version is invisible to concurrent readers because its transaction hasn't committed yet (or its commit timestamp is later than the reader's snapshot). No lock, no contention — the writer appends, the reader walks the chain backward.

The garbage is **dead row versions** — versions that are no longer visible to any active or future transaction because their transaction's commit timestamp is older than the oldest running snapshot's cutoff. These accumulate until cleaned by **vacuum** (PostgreSQL) or **purge** (InnoDB). Left uncollected, they bloat the table, degrade index scan performance, and waste disk space. The collector must also clean up the version chain pointers — `t_ctid` in PostgreSQL or the `DB_ROLL_PTR` in InnoDB — so the surviving version's link doesn't dangle. Some systems also garbage-collect transaction ID wraparound metadata alongside the row versions.

## (2) The shared three-step write pattern

Every caller follows the same sequence:

> **Step 1 — Write to a unique temp file in the same directory.**  
> `crud`, `ambient`, `screen_sensor`, and `admissibility` use `tempfile.mkstemp(prefix=..., suffix=".tmp", dir=...)`. The two `ambient_loop` functions use the simpler `filename + ".tmp"` string concatenation.
> 
> **Step 2 — Flush + fsync the data to physical storage.**  
> `f.flush()` → `os.fsync(f.fileno())` before closing. Guarantees the temp file content is on disk, not in a buffer. (The two `ambient_loop` callers omit `fsync` — they rely on the `with open` close to flush.)
> 
> **Step 3 — Atomic rename with `os.replace(tmp, target)`.**  
> Replaces the target file atomically — on both Windows and POSIX — so readers see either the old or the new content, never a truncated or partially-written file. A crash after `os.replace` is harmless (the temp survives or doesn't); a crash before it leaves an orphan `.tmp` and the live file untouched.

## (3) Why `crud._save_memory` retries `os.replace` on Windows

Windows raises `PermissionError` (specifically `ERROR_ACCESS_DENIED` / `SHARING_VIOLATION`) when another process has the target file open while `os.replace` tries to swap the temp over it. The common case is the harness's `python_repl` reading `memory.json` for `/soul` queries — a reader holds a file handle for milliseconds. Without a retry, the write would be silently dropped. The retry loop (up to 10 attempts with `0.02 × (attempt + 1)` second backoff) is the solution. This was discovered in a **12-thread stress test** where bare `os.replace` lost nearly all writes under concurrent reads on Windows — the retry made it reliable.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independent, deployable services that communicate over a network, each owning a bounded context and its own data store.

The main risks:

1. **Network fallacies** — The network is *not* reliable. Latency, partial failures, timeouts, retry storms, and cascading failures require circuit breakers, bulkheads, and proper timeout policies. The fallacy of assuming zero latency or a reliable transport is the most common first failure.

2. **Data consistency** — Distributed transactions via two-phase commit are impractical at scale. You trade ACID for eventual consistency, sagas, and compensating transactions. Every cross-service read becomes a potential consistency headache.

3. **Operational blast radius** — A monolith has one deployable. N services means N deployment pipelines, N sets of logs, N health checks, N distributed trace spans. Without mature observability (structured logging, metrics, distributed tracing), debugging becomes guesswork.

4. **Boundary mistakes** — Cutting the monolith along the wrong seams creates a distributed monolith: services that are tightly coupled through synchronous calls, shared databases, or chatty interactions. This is the worst outcome — all the cost of distribution with none of the independence.

5. **Testing overhead** — Unit tests stay cheap. Integration tests now require service stubs, contract testing (Pact/Spring Cloud Contract), and end-to-end tests that are fragile and slow. Confidence in a release shifts from "passed tests" to "staged rollouts and canary analysis."

6. **Organizational drag** — Conway's law is not optional. Service boundaries that don't match team boundaries create coordination hell. Every cross-team API change becomes a negotiation. The migration itself stalls because there's no clear ownership of the transition state.

7. **Premature extraction** — Extracting a service for technical purity before understanding real coupling patterns adds complexity without payoff. The right sequence is: extract for a measurable improvement (scaling bottleneck, team autonomy, deploy frequency) — not for architecture aesthetics.
