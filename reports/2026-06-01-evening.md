### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

Horizontal scaling means adding more machines to distribute load across a cluster. Vertical scaling means adding more resources (CPU, RAM, disk) to a single machine.

**Horizontal tradeoffs:**
- **Pro:** True elastic scaling — you can keep adding commodity hardware indefinitely. Better fault tolerance since failure of one node doesn't bring the system down. Can span geographic regions.
- **Con:** Architectural complexity — you now have data consistency, service discovery, load balancing, inter-node communication to manage. Network latency between nodes becomes a factor. Not all workloads can be distributed (stateful systems like relational databases are much harder to scale horizontally).

**Vertical tradeoffs:**
- **Pro:** Simplicity — your application code barely changes. Lower latency for inter-component communication since everything stays on one machine. Transactional consistency is trivial (shared memory, single filesystem).
- **Con:** Hard ceiling — there's a maximum hardware limit per machine (128 cores, 2 TB RAM, etc.), and the cost curve goes exponential as you approach it. Single point of failure. No geographic distribution possible.

**The decision rule:** Start vertical until you hit a resource ceiling or need redundancy. Go horizontal when vertical costs exceed the complexity tax of distributed systems. Most production systems end up hybrid — horizontally scaled stateless app servers backed by vertically scaled stateful databases.

### Q03 [CHAT] — What is a connection pool and why do applications use one? Answer from your training knowledge.

A connection pool is a cache of pre-established database (or service) connections kept in memory, ready to be reused by multiple requests.

Applications use them for two reasons. First, **latency** — establishing a TCP connection and authenticating (especially TLS handshakes) takes milliseconds to seconds per connection. Pooling eliminates that setup time for every subsequent request. Second, **resource limits** — databases cap concurrent connections. A pool lets you enforce a fixed ceiling (say 20 connections) across hundreds of request handlers; without it, a traffic spike can exhaust the database's connection limit and crash the service.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

A primary key uniquely identifies each row in a table — one per table, no nulls, implicitly indexed. A foreign key is a column or set of columns in one table that references the primary key of another table, enforcing referential integrity across the relationship.

The tradeoff: primary keys give you row-level identity and fast lookups. Foreign keys give you data consistency — you cannot insert a row with a value that doesn't exist in the parent table — but they add write overhead on every insert, update, and delete that touches the relationship, and can cascade failures if not designed with care.

### Q08 [CHAT] — What is the difference between blocking and non-blocking code? Give an example of each. Answer from your training knowledge.

Blocking code holds the thread until an operation completes. Non-blocking code initiates the operation and returns control immediately, notifying completion via callback, future, or event loop.

**Blocking example** — a web server that serves one request at a time per thread:
```python
def handle_request():
    data = socket.recv(1024)        # thread blocks here until data arrives
    result = database.query(sql)    # thread blocks here until DB responds
    socket.send(result)
```
Each line waits its turn. The thread cannot do anything else — not even handle another connection — while waiting for the network or database.

**Non-blocking example** — async I/O with an event loop:
```python
async def handle_request():
    data = await socket.recv(1024)        # suspends, event loop handles other tasks
    result = await database.query(sql)    # suspends again
    await socket.send(result)
```
`await` suspends the coroutine, not the thread. The event loop picks up other work while the network or database responds. Same thread, many overlapping operations.

### Q15 [CHAT] — What is the difference between a checked and an unchecked exception? When is each appropriate? Answer from your training knowledge.

Checked exceptions must be declared in a method's signature or caught at compile time — the compiler enforces handling. Unchecked exceptions (subclasses of `RuntimeException` and `Error`) do not require declaration or handling at compile time.

Checked exceptions are appropriate for recoverable, foreseeable failures outside the program's control — file not found, network timeout, malformed input. The caller *must* acknowledge the possibility and decide how to respond. Unchecked exceptions are for programming errors (null pointer, illegal argument, out-of-bounds index) or unrecoverable system failures (out of memory, stack overflow) — the caller typically cannot meaningfully recover at the call site.

The design rule: if a well-written client can reasonably recover and retry, use checked. If recovery is impossible or the fault belongs to the caller's logic, use unchecked. Java's overuse of checked exceptions in early APIs pushed the ecosystem toward unchecked dominance in frameworks like Spring — practical consensus now favors unchecked for most application code, reserving checked for genuinely external contract failures.
