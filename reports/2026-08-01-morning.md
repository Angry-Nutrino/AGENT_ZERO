### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

The core difference is *when* you check for conflict — before doing the work, or after.

**Pessimistic** assumes conflicts are likely and prevents them up front. You acquire a lock before touching the data and hold it until commit. The database form is two-phase locking: shared locks for reads, exclusive locks for writes, all released at commit — which is what makes it serializable. The application forms are `SELECT ... FOR UPDATE`, a mutex around a critical section, or a file lock. Conflict never happens because it's structurally impossible for two transactions to hold incompatible locks at once.

**Optimistic** assumes conflicts are rare and detects them at the end. No locks; transactions run freely, and at commit the system validates that nothing it depended on changed. The canonical pattern is version numbers: read row + version, do the work, then `UPDATE ... WHERE version = ?`. Zero rows affected means someone else won — abort and retry. HTTP ETags with If-Match, CAS, write-if-not-exists (`O_EXCL`), and git itself (conflicts only surface at merge) are all optimistic.

**Choose optimistic when:**
- Contention is low — transactions touch different rows. Locks would serialize work that never actually collides; that's pure overhead.
- Workload is read-heavy. Reads almost never conflict, and optimistic reads cost nothing.
- The system is distributed. Distributed locks are fragile — leases, fencing tokens, handling a client that died holding the lock. Conditional writes and CAS are simple and composable.
- Retry is cheap. A short transaction that aborts and reruns has a negligible cost.

**Choose pessimistic when:**
- Contention is high — many transactions hit the same rows. Optimistic control degrades badly here: every transaction does the full work, then aborts, then retries, and the retries add more load. Enough of that collapses into a retry storm.
- A conflict is expensive to undo. If retrying means redoing significant work or showing a user a failure, locking up front is the cheaper insurance. Booking systems, seat selection, inventory decrements on hot SKUs.
- The operation outlives a single short transaction and its partial effects would be visible before validation.

**The tradeoff in one line:** pessimistic trades concurrency for certainty; optimistic trades wasted work for concurrency. Locking's failure mode is waiting and deadlock; optimistic's is aborting and redoing.

The nuance that matters most: it's not about "databases are pessimistic" — it's about conflict rate and retry cost. High-contention short writes want pessimistic or atomic operations; low-contention or long-lived work wants optimistic.

This is exactly where Kleppmann lands in DDIA chapter 7. Serializable snapshot isolation is the synthesis — run optimistic, use version data to detect write skew at commit, abort the loser. You get serializable behavior without lock overhead, as long as conflicts are genuinely rare. When they aren't, it breaks down the same way every optimistic scheme does.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

A **process** is an isolated execution environment — its own virtual address space, file descriptors, and signal handlers. Context switching between processes is expensive because the OS must swap memory mappings and flush caches.

A **thread** is a single execution flow *within* a process. All threads in a process share the address space, heap, and open files, but each has its own stack, registers, and program counter. Context switching between threads is cheap — no address-space swap.

The decisive factor in Python is the **GIL** (Global Interpreter Lock):

- **Threading** — one thread holds the GIL and executes Python bytecode at a time. So CPU-bound Python code does *not* speed up with threads; they may even run slower due to lock contention.
- **Multiprocessing** — each process gets its own interpreter and its own GIL. True parallelism across CPU cores.

**Use threading when the work is I/O-bound** — network requests, file reads, database calls. The thread releases the GIL while blocked on I/O, so another thread can run. Hundreds of concurrent connections handled gracefully; light overhead per thread.

**Use multiprocessing when the work is CPU-bound** — heavy computation, data processing, ML inference loops. The `multiprocessing` pool (`ProcessPoolExecutor` or `Pool.map`) splits work across cores and each process runs Python independently.

Practical notes:
- Between the two, for I/O-bound work, **asyncio** is often the better answer than threads — single-threaded, event-driven, essentially zero per-task overhead. Threads make sense when you have blocking libraries that asyncio can't await.
- Process creation is expensive on Windows (fork doesn't exist; spawn re-imports the module — your `if __name__ == "__main__":` guard matters).
- Multiprocessing requires picklable arguments and has IPC costs. If the data transfer between processes exceeds the computation, the parallelism doesn't pay off.

The rule of thumb: **I/O-bound → threads (or async). CPU-bound → processes.** And if it's both, split the pipeline — threads for the I/O stages, a process pool for the compute stage.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

**What it is.** p99 is the latency below which 99% of requests fall — 1 in 100 exceeds it. p999, 1 in 1,000. The mean is what dashboards show; the tail is what users feel. They diverge dramatically: a service averaging 20ms can still show p999 at 3 seconds.

**Why the tail dominates.** Two compounding effects:

1. **Sequential chains.** A single user action is rarely a single request — it's a chain: API → auth → cache → database → aggregation. Perceived latency is the *sum* of hops, and the probability that at least one hop hits its tail compounds. Ten hops, each slow 1% of the time, means ~10% of user-visible actions suffer a tail event even when every hop's average looks clean.

2. **Fan-out amplification.** One user request fans out to dozens or hundreds of internal calls — sharded databases, search shards, microservice dependencies. The user waits for the *slowest* one, not the average. With 100 parallel calls, aggregate latency is the max of 100 distributions, so the system-level p99 is far worse than any single component's. This is tail-latency amplification — the Kleppmann point.

Underneath both: tail events are real-world artifacts — GC pauses, scheduler preemption, network retransmits, lock contention, noisy neighbors, queue buildup. Rare per machine, but a fleet produces these "rare" events constantly. Averages hide that; the tail is where they surface. And users perceive variance harshly: a stable 100ms feels better than 50ms with intermittent 5-second hangs, because one slow response blocks the entire interaction.

**One technique: hedged requests.** From Dean & Barroso's "The Tail at Scale": if a request hasn't returned within a cutoff — typically the service's p95 — fire a duplicate to a different replica or instance. Take whichever responds first; cancel the loser. The math is the point: if a single replica has a 1% chance of being slow, two independent replicas are both slow with roughly 0.01% probability. The tail collapses nearly quadratically without making anyone's hardware faster.

Constraints are real: it doubles load precisely during tail conditions, so it belongs on idempotent reads or with duplicate suppression on write paths; and the cutoff must be set so you're not speculating on the 95% that would have finished anyway. Done right, it converts a p99 experience into something indistinguishable from p50.

### Q20 [DELIBERATE] — core_logic/mcp_client.py multi-hop. (1) _ensure_alive restarts a dead server via connect(); what exception class does call() raise on a tool error? (2) Why must MCP calls use a direct await and never asyncio.to_thread?

Read the file. Both answers are confirmed from source.

**(1) Exception class on tool error:** `MCPError` — defined at line 19-21 (`class MCPError(Exception)`). `call()` raises it in two places: line 133 when the response carries `isError: true` (message includes the tool result), and line 107 when the server isn't connected at all. Additionally, `_send_request` raises `MCPError` for JSON-RPC-level errors (line 182) and for unexpected stdout closure (line 173) — those propagate up through `call()` unchanged. So the answer is unambiguous: every failure path in `call()` raises `MCPError`, never a generic `Exception`.

**(2) Why direct `await`, never `asyncio.to_thread`:** Because `call()` and `_send_request` are genuinely async operations that must stay on the event loop — a `to_thread` wrapper would push them onto a worker thread, and the JSON-RPC framing depends on the per-server `asyncio.Lock` and cooperative suspension. Three concrete reasons visible in the code:

1. **Lock correctness** — `_send_request` holds `state["lock"]` across write + read (lines 152-186). The lock is an `asyncio.Lock`, which is not thread-safe. If the call ran in a thread, the lock acquire/release would happen off the loop and silently lose serialization, allowing interleaved frames on stdin.
2. **Blocking the loop is the point** — the `await process.stdout.readline()` with the 30s `asyncio.wait_for` timeout (lines 169-171) *requires* running on the loop. Shipped to a thread, that `readline()` blocks the worker thread — you'd need a second thread pool just to handle the timeout, and you'd lose the natural cancellation semantics.
3. **No CPU-bound work to offload** — `to_thread` exists to unblock the loop for blocking I/O or CPU work. Here the I/O is already non-blocking via subprocess pipes and `drain()`; there's nothing for a thread to buy. It would only add a context-switch penalty and complicate the per-server state.

The threading model in the codebase keeps `asyncio.Lock` and subprocess state on the loop; mixing in threads would break that invariant. Direct `await` is the only correct call pattern.

Does the raw path ever appear? No — not in the ledger. This is enforced at both ends:
1. **Module docstring, lines 22-25 (PRIVACY FLOOR)** — "Raw file contents / full paths / conversation NEVER enter the envelope. Local adapters additionally receive local_ctx (the real path) which NEVER leaves the machine; a remote adapter gets the envelope alone."
2. **The private path exists only in `local_ctx`** (line 483: `{"path": str((args or {}).get("path", ""))}`), which is passed to local adapters at evaluation time and is never included in either `_ledger_append` call (lines 458-461 and 498-501 — both persist only `{receipt_id, verdict, reason, adapter, mode, enforced, envelope}`).

So a reviewer looking at `admissibility_ledger.json` can tell *which file* was targeted only in the weak sense that the hash is reproducible given a candidate basename — e.g. `sha256("notes.txt".encode()).hexdigest()[:16]` will match. That's the design intent: the ledger is local telemetry, gitignored, and privacy-hardened so a remote adapter (the future remote partner) only ever sees the hash and the risk labels.
