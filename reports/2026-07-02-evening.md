### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental mismatch between the size of a user write and the amount of data the storage engine must rewrite to the device to accommodate it.

There are three sources in order of increasing cost:

1. **Compaction** — the dominant contributor. When the memtable is flushed to Level 0 as an SSTable, and the background compaction process merges that file with overlapping SSTables in the next level, every byte in those overlapping files must be read, sorted, and rewritten. A single user write that lands in a busy key range may be re-written dozens of times as it cascades down 7 or more levels.

2. **WAL writes** — every write must first hit the write-ahead log for durability. That log is sequential—low cost on SSDs—but it still doubles the user write's bytes if WAL and compaction are already factored in.

3. **Flush** — when the memtable spills to disk as Level 0, the user's key is serialised into an SSTable structure with index blocks, bloom filters, and compression dictionaries. That's typically 1–2× the original write before compaction even starts.

In practice, the cost is devastating on two axes:

- **SSD endurance.** Consumer SSDs are rated for around 300–600 TBW (terabytes written). An LSM-tree with write amplification of 20–30× means a user who believes they are writing 10 GB/day is actually wearing the NAND by 200–300 GB/day. A drive expected to last 5 years burns out in 6–12 months.

- **Write latency tail.** Compaction runs in the background, but it competes for disk I/O with the foreground writes. When a large compaction job is in progress—especially at the upper levels where files are hundreds of MB to GB—user writes stall waiting for the I/O scheduler to service them. P99 latency spikes from tens of microseconds to hundreds of milliseconds, sometimes seconds on heavily loaded systems.

The trade-off is deliberate: LSM-trees sacrifice write endurance and latency predictability for superior read performance and write throughput on append-only workloads. RocksDB, LevelDB, and Cassandra all tune compaction strategies (size-tiered vs. leveled, write stall triggers, compression, bloom filters) to keep amplification between 3× and 15× in production, but below 5× is expensive in CPU and space amplification.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a consistent snapshot of the database as of a particular transaction ID — when a writer holds a lock on a row, the reader simply reads the pre-write version from an older snapshot rather than waiting for the writer to finish. The writer's new version is staged in the transaction's private workspace and only becomes the "current" version on commit, so readers already holding an older snapshot ID never see a partially written row and never contend on the writer's locks.

The garbage it creates is obsolete row versions — tuples that are no longer the current committed version of a row but are still referenced by active snapshots (snapshot too old) or have no remaining snapshot that could ever reference them. PostgreSQL calls these "dead tuples"; they bloat indexes, increase sequential scan cost, and fragment storage. Cleaning them up requires a periodic vacuum process (either manual or autovacuum in PostgreSQL, or a background compaction/rewrite thread in databases like CockroachDB) that marks the dead tuple space as reusable and defragments the heap pages.

1. **Temp-file creation** — `tempfile.mkstemp(prefix=".memory.json.", suffix=".tmp")` produces a unique temporary path via the OS
2. **Durability call** — `os.fsync(fd)` flushes all buffered writes to physical storage before the swap

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application — where all functionality runs in a single process sharing a single database — into a set of independently deployable services that communicate over a network, each owning its own data store.

The main risks:

1. **Network as a new failure mode** — Within a monolith, a function call either succeeds or raises an exception within milliseconds. In a distributed system, every call can fail from timeout, partial failure, network partition, or cascading overload. You now handle retries, circuit breakers, timeouts, and partial degradation — three to five new failure classes that didn't exist before.

2. **Data consistency across boundaries** — A monolith uses ACID transactions across any tables it needs. After splitting, a single business operation (say, "place order") touches Order Service, Inventory Service, Payment Service, and Notification Service. Distributed transactions (2PC) are slow and fragile. You end up with eventual consistency, sagas, and compensating transactions — all harder to reason about and test than a single database transaction.

3. **Latency compounding** — What was a 2ms in-process call becomes a 5-50ms network round trip with serialization overhead. A request that touched four modules in the monolith now makes four network hops. If any of those services fan out further, you can hit hundreds of milliseconds before a page renders. Teams often discover this only in production.

4. **Operational surface area explosion** — One deployable becomes ten. One database connection pool becomes ten. Monitoring, logging, deployment pipelines, configuration management — each multiplies. Without mature tooling (Kubernetes, service mesh, distributed tracing), operational overhead can consume more engineering time than feature work for months.

5. **The bounded context guessing game** — The hardest part isn't technical. It's deciding where the boundaries go. A wrong split means services that must be deployed together anyway, shared databases that should have been separate, or chatty calls between services that should have been one. Fixing a bad boundary later means a re-split, which is effectively a second migration atop a system that's already running in production. More services get decomposed than should be — a boundary that crosses a transaction boundary or a frequent join is a signal it's too early to split there.
