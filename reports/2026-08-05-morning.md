### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Core difference is *when* you detect a conflict and what you pay for it.

**Pessimistic concurrency control** assumes conflicts are likely, so it locks the resource before touching it. Others block until the lock releases. You pay in *waiting time* — plus deadlock risk, which requires detection and abort of one party.

- Mechanisms: shared/exclusive locks, two-phase locking, `SELECT ... FOR UPDATE`, mutexes.
- Failure mode: deadlock → one transaction aborted.

**Optimistic concurrency control** assumes conflicts are rare, so it proceeds without locks and verifies at commit time that nothing changed since the read — via a version number, timestamp, or compare-and-swap. On mismatch, it aborts and retries. You pay in *redone work*.

- Mechanisms: version columns, CAS, MVCC snapshots, ETag + `If-Match` in HTTP.
- Failure mode: retry; livelock under extreme contention.

**Choosing — it's simple once you frame it correctly:** pessimistic wastes time *waiting*; optimistic wastes time *repeating*. Pick whichever waste is cheaper for your actual workload.

- **Pessimistic** when: contention is high, conflicts are frequent, transactions are short (locks held briefly), retries are expensive or unsafe (non-idempotent operations), and immediate consistency is non-negotiable. Think inventory decrements, ticket booking, financial ledgers.
- **Optimistic** when: contention is low, reads dominate, transactions are long (holding locks for hours is catastrophic), retries are cheap and idempotent, or you're in a distributed system where distributed locks are costly and fragile. Think document editing, CRUD APIs, ETag-based web updates.

The cliché "optimistic for reads, pessimistic for writes" is too blunt. The real rule: **short transactions + high conflict rate → pessimistic. Long transactions + low conflict rate → optimistic.** A long transaction under pessimistic control creates a convoy — everything queues behind it. A short transaction under optimistic control in a hot spot retries more often than it succeeds.

Most modern databases don't make you choose globally. Postgres and InnoDB use MVCC — readers get lock-free snapshots (optimistic), writers still serialize (pessimistic). SQL Server leans lock-first. Postgres leans MVCC-first.

Your own vault guard is the grounded example: you used `threading.Lock()` — pessimistic — and it was correct, because under the autonomy model the write race is near-guaranteed and the corruption is silent. Retrying a written memory isn't a safe fallback; blocking is. That's the deciding factor in miniature: *can you afford to replay the work, and is the conflict actually going to happen?*

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

**Process vs Thread — the core distinction**

A process is an isolated execution environment: its own virtual address space, file descriptor table, signal handlers, and PID. A thread is a single execution stream *within* a process. Threads in the same process share the heap, code, global variables, and open file descriptors — but each has its own stack, program counter, and register state.

That one architectural fact drives almost everything else:

- **Isolation:** One process crashing doesn't take down the others. One thread segfaulting takes down the entire process, because they share the address space.
- **Communication:** Processes need IPC — pipes, sockets, shared memory, queues. Threads just read/write shared variables (with locks to prevent races).
- **Cost:** Creating a process is expensive — the OS must allocate a new address space, page tables, and kernel structures. Creating a thread is cheap by comparison. Context-switching between threads is also cheaper than between processes because the TLB and address space don't need to be flushed.

**Python-specific: the GIL changes the calculus**

CPython's Global Interpreter Lock means only one thread executes Python bytecode at any instant. So:

- **Threading does NOT give you true parallelism for CPU-bound Python code.** Two threads doing pure Python computation on 8 cores still use roughly one core. The GIL ensures only one runs bytecode at a time.
- **Threading DOES work for I/O-bound work** — network requests, file reads, database calls, sleeps. During the `await` or I/O wait, the GIL is released, so other threads run. This is why `ThreadPoolExecutor` and `asyncio` shine for HTTP scraping, API calls, and similar workloads.
- **Multiprocessing gives you true parallelism** — each process gets its own Python interpreter and its own GIL. CPU-bound work scales across cores. The cost is IPC overhead and the memory duplication of forking/spawning.

**When to use each**

Use **threading** when:
- The bottleneck is I/O: waiting on network, disk, subprocesses, APIs.
- You need to share state fluidly between concurrent units, and you're disciplined with `threading.Lock` / `RLock`.
- Overhead of process spawn and IPC isn't justified.
- You want low-latency coordination — a producer-consumer queue, event-driven architecture.

Use **multiprocessing** when:
- The work is CPU-bound and the Python bytecode is the bottleneck — number crunching, ML inference, image processing, parsing large files.
- You need crash isolation between workers.
- You're using the `concurrent.futures.ProcessPoolExecutor` with `map` — which handles the pickling and pooling for you.

**The hybrid pattern that matters in practice**

The most common production shape is both: a `ProcessPoolExecutor` for CPU-bound chunks, and threads (or `asyncio`) for the I/O orchestration around them. A web server with a thread pool that fans out to a process pool for heavy computation. Don't treat it as either/or — thread the waiting, process the computing.

**One-line decision rule:** I/O-bound → threading. CPU-bound → multiprocessing. Both → thread the I/O, process the compute.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the latency of the slowest fraction of requests: p99 is the value below which 99% of requests fall; p999 is the 99.9th percentile. You don't feel averages — you feel single requests. One user's interaction is one request, and if it lands in the slow tail, that user perceives a broken service. A 100ms mean with a silent 3-second p99 is a service that looks healthy in a dashboard and feels unreliable in practice.

The reason it's worse in distributed services is tail latency amplification through fan-out. A user-facing action decomposes into N downstream calls, and a fast page requires all N to be fast. Take N = 100 sub-requests, each at p99: the probability of a fully fast page is 0.99^100 ≈ 0.37 — meaning roughly 63% of user requests hit at least one straggler. The mean stays flat while the tail grows, and queueing plus head-of-line blocking make it worse under load. This is the amplification math in Designing Data-Intensive Applications, which you're reading.

The architectural technique to tame it: hedged requests — send the request to two replicas, take the first response that returns, and discard the straggler. When one replica hits a noisy neighbor or a GC pause, the other still answers on time. The practical refinement is tied requests: dispatch the second copy only after the first misses a small initial deadline (say the p50), so you pay double load only for requests already drifting toward the tail, not for all of them. Cost is redundant compute and higher aggregate load — hedge deliberately and measure the p99 before and after.

Same principle lives in your orchestrator: wherever a single operation sits in the agent loop's critical path, its p99 — not its mean — is what the user perceives as the pause between turns. A straggler in the event drain stalls the whole loop.

### Q20 [DELIBERATE] — core_logic/mcp_client.py multi-hop. (1) _ensure_alive restarts a dead server via connect(); what exception class does call() raise on a tool error? **(1) The exception class:** `MCPError`, defined at lines 19–21 as a subclass of `Exception`. On a tool error, `call()` raises it at lines 132–133 when the response carries `isError`: `raise MCPError(f"Tool '{tool_name}' returned error: {result}")`. It's the single fault class the whole module surfaces — also raised for server-not-connected (line 107), closed stdout (line 173), JSON-RPC error fields inside `_send_request` (line 182), and the `_ensure_alive` reconnect path (line 99: `connect()` raises it if the restart fails, which the caller surfaces untouched).

Direct await keeps the lock meaningful, the transport single-owner, and every failure mapped to `MCPError`.
