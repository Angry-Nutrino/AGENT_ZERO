### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

They're different dimensions of capacity.

Horizontal scaling: add more nodes. Vertical scaling: make the existing node bigger.

Horizontal tradeoffs:
- Higher operational complexity — you're now managing a distributed system with network partition, consensus, data synchronization.
- Near-linear cost scaling at low-to-moderate load. Diminishing returns as coordination overhead eats the marginal gain.
- Graceful degradation under failure — one node goes down, traffic shifts to the rest. No single point of total loss.
- State becomes the hard problem. Session affinity, cache invalidation, database replication — everything that was trivial on one box now has edge cases.

Vertical tradeoffs:
- Ceiling is hard — there is a maximum machine your cloud provider sells, or a physical limit on what you can rack.
- Cost superlinear at the high end — the jump from 64GB to 128GB RAM costs more than just doubling, because you're buying the top of the SKU stack.
- Zero benefit for fault tolerance. If the single node fails, everything fails. No graceful path.

Decision rule: vertical first until you hit either the cost inflection point or the absolute ceiling. Horizontal only when vertical is no longer viable — because horizontal introduces complexity you don't need before then.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

Primary key uniquely identifies each row within its own table. Foreign key is a column (or set of columns) in one table that references the primary key of another table, enforcing referential integrity — ensuring every value in that column exists in the referenced table. A table can have only one primary key (though it can be composite), but can have multiple foreign keys. Primary keys disallow NULLs; foreign keys typically allow them depending on the relationship.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works because every write creates a new row version rather than mutating the existing one. Readers see a snapshot from the database's visibility rules — typically tied to a transaction ID or timestamp — so they read the version that was committed *before their snapshot started*. The writer creating a new version doesn't touch that old one. Neither waits on the other.

The garbage is *bloat*: row versions that are no longer visible to any active or future transaction but still occupy space on disk. They pile up in index entries and table pages, slowing scans and inflating storage. The cleanup mechanism is VACUUM (PostgreSQL) or equivalent — it walks dead tuples, marks their space as reusable, and can physically compact them when needed. Let the bloat grow unchecked and you'll see query latency climb from index bloat alone, before the table even fattens.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services that communicate over a network, each owning its own data and domain boundary.

The main risks, in rough order of how often they cause real damage:

**Distributed transactions and data consistency.** The monolith had ACID transactions across tables. Now those same operations span services with independent databases. You either accept eventual consistency (and the developer cognitive load that comes with it) or introduce sagas, outbox patterns, or two-phase commit — each adding complexity and latency.

**Network as the new primitive.** Latency that was a local function call becomes a network hop. Every inter-service call adds serialization, deserialization, transport overhead, and the possibility of partial failure. Teams that don't invest in circuit breakers, retry logic with exponential backoff, and observability (distributed tracing, metrics per service) discover these gaps in production.

**Coupling that doesn't go away.** Shared databases, shared schemas, shared libraries, shared deployment pipelines — teams that split code but keep shared infrastructure end up with all the operational overhead of microservices and none of the autonomy benefit. The hardest coupling to remove is organizational: Conway's Law means service boundaries that don't match team boundaries create friction that no architecture can fix.

**Test and deployment complexity.** A single monolith integration test becomes a multi-service integration test that requires orchestrating dependencies, managing test data across databases, and handling async event flows. Deployment shifts from one deployable to a coordinated release across potentially dozens of services with their own cadences. Rollbacks are no longer atomic.

**Observability debt.** In a monolith, a single log file and a monitoring dashboard cover the entire system. Microservices require centralized logging (ELK, Loki), distributed tracing (Jaeger, Zipkin), metrics aggregation (Prometheus + Grafana), and structured logging conventions across every service. Teams that don't build this infrastructure *before* splitting services spend the first three months fighting fires blind.
