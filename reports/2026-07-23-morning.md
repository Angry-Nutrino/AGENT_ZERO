### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic assumes conflict is rare — you let operations proceed without locking, then check at commit time whether anything stepped on your work. Pessimistic assumes conflict is inevitable — you lock the resource before touching it and hold the lock until done.

Pessimistic is the right choice when contention is high, writes dominate reads, or the cost of a rollback is unacceptable — think inventory systems where two customers shouldn't both buy the last unit, or financial ledgers where every write must be final. The tradeoff is throughput: locks serialize access, and you can deadlock if the granularity or ordering is wrong.

Optimistic wins when contention is low, reads dominate writes, or the data lives across a network where distributed locks would be expensive — think collaborative document editing (most edits don't collide), or read-heavy web endpoints with a write rate under 5%. The tradeoff is abort overhead: if contention spikes, you waste work retrying, and under high load the system can thrash with repeated aborts.

The pragmatic answer: start optimistic, instrument abort rate, and if it crosses 5-10%, escalate the hot paths to pessimistic. That's how you avoid premature locking without getting blindsided by a contention spike.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

A process is an independent execution unit with its own isolated memory space, file descriptors, and system resources — the OS treats it as a self-contained program. A thread is a lighter unit of execution *within* a process; threads share the same heap, code, and file descriptors but have their own stack and program counter. Context-switching between threads is cheaper because they share an address space (no TLB flush), while switching processes requires a full register save/restore plus MMU state reload.

In Python, the GIL adds a practical constraint: only one thread holds the Python bytecode lock at a time, so CPU-bound work sees *no* parallelism from threading — it actually runs slower due to lock contention. Multiprocessing side-steps this entirely by spawning separate interpreter processes, each with its own GIL, giving true parallelism on multi-core hardware.

**Use multiprocessing when:**
- The task is CPU-bound (computation, image processing, number crunching)
- You need to fully utilize multiple cores
- Memory isolation is a feature, not a bug (crash in one worker doesn't take down others)

**Use threading when:**
- The task is I/O-bound (network requests, file reads, database queries)
- You're waiting on external resources most of the time and the GIL is released during that wait
- You need lightweight concurrency with shared state (and you're careful with locks)

There's a middle path: combine them. For example, a pool of processes each running a thread pool for I/O within its own sandbox — rare but useful when you need both CPU parallelism *and* concurrent I/O from each worker.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the gap between what the system *can* do and what a single unlucky request actually gets. p99 tells you the worst 1-in-100 experience; p999 is 1-in-1000. In a distributed service, a single user's request fans out across dozens of nodes — if any one of them hits its p99, that user's entire request lands at p99. A 10ms average doesn't matter when 1% of your users wait 500ms.

The architectural technique that matters most: **hedged requests** (Google's approach from the Chubby/Zanzibar era). Fire the same request to two replicas, take whichever responds first, cancel the other. You trade a marginal increase in load (typically 5-10%) for a dramatic compression of the tail — because the probability that *both* replicas are in their p99 simultaneously is p99². 1% becomes 0.01%.
