### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design decision: writes are buffered in memory (the memtable) and then flushed to disk as immutable sorted SSTables, but reads need to find data across a growing set of these files. This forces two background processes:

First, **compaction** — merging several overlapping SSTables into one sorted output. Every byte written to level \( L \) as part of a compaction will be read back, sorted, and rewritten into level \( L+1 \). For a leveled compaction strategy (LevelDB, RocksDB's default), each byte journeys through roughly \( O(\log_{k} N) \) levels, resulting in a write amplification factor typically between 10–30× depending on the size ratio between levels and how aggressively compaction is tuned. Size-tiered compaction (Cassandra's default, older Bigtable-style) can be milder in small setups but collapses catastrophically when many overlapping SSTables get compacted simultaneously — amplification can spike past 50× under write-heavy loads.

Second, **the WAL (write-ahead log)** adds its own overhead. Every write hits the WAL first (sequential, so cheap), but physical replication of the write to the memtable and then to each subsequent SSTable and compaction output means the logical byte the application wrote may account for 10–40 total bytes of device I/O by the time it's stable in the last level.

The costs are not abstract:

- **Throughput ceiling becomes a function of storage bandwidth, not CPU.** A single SSD that can do ~500 MB/s sequential writes gets consumed entirely by compaction overhead once write rates exceed ~15–25 MB/s sustained for a 15× amplification. The application sees a latency cliff: throughput stays flat, then drops sharply as compaction falls behind and read-merge depth grows.
- **SSD endurance is the harder constraint.** Consumer TLC NAND is rated for ~600–1500 program/erase cycles. A write amplification of 20× on a 512 GB drive means every terabyte the application writes burns ~20 TB of device wear. On a drive rated for 300 TBW (terabytes written), that's 15 TB of application data before the drive is statistically at end-of-life. This is why large LSM deployments (Cassandra clusters, RocksDB in Kafka streams) mandate either high-endurance SSDs (Optane, enterprise TLC with 3000+ P/E) or explicit wear-aware compaction tuning.
- **Write stalls from compaction backpressure.** When compaction cannot keep pace with the incoming write rate, the memtable fills and the application blocks. In practice this manifests as p99 write latency spikes — a steady 2 ms average can see 200 ms tails under compaction storms. Tuning the number of compaction threads, throttling write rate, and using partitioned compaction (LSM-tree variants dividing the key space) are the standard mitigations, each trading write amplification against read amplification or complexity.

Database designers typically respond by exposing knobs: `write_buffer_size`, `max_bytes_for_level_base`, and `level0_file_num_compaction_trigger` in RocksDB, or `compaction_throughput_mb_per_sec` in Cassandra. But the core tension is structural — LSM-trees amortize write cost against read cost, and write amplification is the tax you pay for making point lookups fast on write-optimized storage.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works by giving each transaction a snapshot of the database at a point in time — typically when the transaction begins or when the statement starts, depending on the isolation level. When a writer modifies a row, it creates a new version of that row rather than overwriting the existing one. The old version remains visible to any reader whose snapshot predates the write. The reader never acquires locks, never waits, and the writer doesn't block waiting for readers to finish.

The garbage it creates is old row versions that are no longer visible to any active transaction. These accumulate in the storage engine as "dead tuples" (PostgreSQL calls them) or "ghost records" (InnoDB's term). The longer transactions run, the more versions they pin. A long-running read transaction can delay cleanup of millions of versions, cascading into index bloat, increased page-level fragmentation, and degraded cache efficiency.

The cleanup process — VACUUM in PostgreSQL, purge threads in InnoDB — identifies versions whose visibility horizon has passed (no active transaction can _see_ them anymore) and reclaims the space. It's not free: scanning dead tuples and updating visibility maps costs I/O and CPU, and if cleanup falls behind, the table grows monotonically even if the logical row count stays flat. That's why you set `autovacuum` tunables and watch for transaction ID wraparound, which is the nuclear failure mode when cleanup stalls entirely.

Every `_save_memory` call writes the **entire in-RAM `self.memory` dict** to a fresh temp file via `json.dump(self.memory, f, ...)` (line 80) then atomically swaps it in with `os.replace`. A dropped `os.replace` leaves the old live file **untouched** — it still holds the previous complete save. The next `_save_memory` call writes the current `self.memory` to a new temp and tries `os.replace` again. The dropped write is a transient miss, not data loss, because the full state is always re-serialized from RAM every time.

The retry-with-backoff catches **`PermissionError`** (line 95). The loop retries 10 times with a linear backoff: `time.sleep(0.02 * (attempt + 1))` (20ms, 40ms, ..., 200ms).

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable, single-responsibility services that communicate over a network. The goal isn't just smaller codebases — it's independent scaling, deployment velocity by team, and failure isolation.

The main risks, ordered by how often they actually take down a migration (not by how much they're talked about):

1. **Network as new primitive** — The monolith called functions; now you have real network calls with latency, partial failure, and non-deterministic timeouts. Teams that don't internalize the fallacies of distributed computing end up with cascading failures from what was a local call.

2. **Data entanglement** — The single database was the true coupling point. Splitting it into service-owned databases means either eventual consistency (which most product owners won't accept until they see the downtime) or distributed transactions (which don't truly exist in the 2PC sense at scale). Most migrations stall here because nobody wants to own the data decomposition.

3. **Transactional integrity collapse** — In the monolith, a business operation spanning five tables worked because of ACID. Now that same operation spans five services. Teams default to sagas, but compensating transactions for every failure mode are almost never fully specified before going to production.

4. **Observability debt** — You had one APM agent and one log stream. Now you have N services, each generating its own logs, metrics, and traces. Organizations typically discover they have no distributed tracing infrastructure about three weeks into the migration. Debugging becomes "search across 12 dashboards."

5. **Team topology mismatch** — If you split the monolith but keep the same team structure, you get distributed monolith: services that are independently deployable in theory but have to be deployed together because nobody untangled the ownership. Conway's Law works in reverse here — you can't get service independence without team independence.

6. **Premature extraction** — Teams start by extracting the smallest, most isolated module (high success, low value), declare victory, then attempt the core domain (tight coupling, shared state, no clear boundary) and hit a wall. The first extraction should be the hardest one, where the real coupling lives — if you can't untangle it, you don't have a migration strategy, you have a rehosting plan.
