### Q05 [CHAT] — Explain the difference between process isolation and thread isolation in Python. When does multiprocessing outperform threading and why? Answer from your training knowledge.

Thread isolation in Python is cooperative within the same process — each thread shares the same memory space, GIL, and object graph. Thread switches happen at bytecode boundaries (every 100 bytecode instructions by default, or on I/O). The lock protects interpreter internals but means only one thread executes Python bytecode at a time.

Process isolation gives each child its own Python interpreter, GIL, memory space, and file descriptor table. Switching between processes requires a full kernel context switch — more expensive than a thread switch — but each process runs Python code in true parallel across CPU cores.

Multiprocessing outperforms threading when the workload is CPU-bound and compute-intensive: matrix multiplication, image processing loops, numerical simulation, any loop where 90%+ of time is spent executing Python bytecode rather than waiting on I/O. In that scenario, threading gives you N threads competing for one core's worth of CPU time, plus context switch overhead — strictly worse than a single thread. Multiprocessing gives you N processes running on N cores, dividing wall-clock time by core count (minus IPC overhead).

Threading wins when the bottleneck is I/O — network requests, file reads, database queries, HTTP API calls — where threads spend most of their life blocked on system calls, voluntarily releasing the GIL so other threads can make progress. Async I/O often beats both for I/O-heavy workloads, but between threading and multiprocessing for I/O-heavy, threading wins by a wide margin.

### Q08 [CHAT] — I'm deciding between fully normalizing my database schema versus leaving some denormalization for read speed. What are the real tradeoffs? Answer from your training knowledge.

You're weighing read throughput against write integrity and schema complexity. Here's the real tradeoff landscape.

**Denormalization wins on:** read latency (single table lookup vs 3-5 joins), query simplicity, and materialized view avoidance. Data that's read 1000x more than written — dashboards, analytics feeds, leaderboards — benefits significantly.

**Denormalization costs:** update anomalies (update one place, miss the other), write amplification (one logical update hits multiple rows), and schema drift over time. The second developer who doesn't know the implicit invariant creates orphan data.

**Normalization wins on:** write integrity (single source of truth), schema evolution safety, and concurrent write handling. Foreign keys enforce invariants the application layer forgets to check.

**Normalization costs:** query complexity, join overhead at scale (100M-row joins hit memory limits), and the N+1 query problem in ORMs that aren't aggressively optimized.

*Where the line actually matters*: the write-to-read ratio and the consistency requirement. If reads need *absolute* consistency (a financial dashboard that must reconcile to the penny), normalized is safer — denormalized caches drift under concurrent writes. If reads tolerate eventual consistency (a recommendation feed showing "people also bought"), denormalize aggressively and batch-update on a schedule.

The pragmatic middle path: normalized storage layer, denormalized read models. Write normalized, project to read-optimized views via materialization or a caching layer. You get write integrity and read speed without choosing one.

### Q19 [CHAT] — What are the three execution modes in CLARA and what are the exact routing conditions that determine which one is chosen? Answer from what you know.

There are three execution modes — **FAST, CHAT, and DELIBERATE** — not including BACKGROUND, which is a separate orchestration concern for autonomous system-origin tasks, not a user-interactive execution mode.

**FAST**
- **Trigger:** tool known (tool ≠ null), confidence ≥ 0.75, uncertainty ≤ 0.30, requires_planning = false
- **LLM calls:** Interpreter (non-reasoning) + format_llm (non-reasoning)
- **Latency:** ~2-4s
- **Escalation:** On failure, failure context (tool attempted, args, error, partial result) is injected as an assistant block and it escalates to DELIBERATE

**CHAT**
- **Trigger:** tool = null, confidence ≥ 0.75, uncertainty ≤ 0.30, requires_planning = false
- **LLM calls:** Interpreter (non-reasoning) + direct stream via `_run_chat()` — non-reasoning, no ReAct loop, no tool calls
- **Latency:** ~1.5-2.5s

**DELIBERATE**
- **Trigger:** requires_planning = true OR confidence < 0.75 OR uncertainty > 0.30 OR FAST failed
- **LLM calls:** Interpreter + ReAct loop (reasoning, max 8 turns)
- **Latency:** ~5-30s

Routing is handled by the **Interpreter** (which replaced the old Gatekeeper). It outputs an `InterpreterOutput` schema with `intent`, `tool`, `args`, `confidence`, `uncertainty`, `requires_planning`. The route logic is:

```
if confidence >= 0.75 and uncertainty <= 0.30 and requires_planning == False:
    if tool is not None → FAST
    if tool is None    → CHAT
else:
    DELIBERATE
```

BACKGROUND isn't an execution mode in this sense — it's a separate orchestration pattern where the Orchestrator's background tick creates system-origin tasks and dispatches them to workers, independent of user interaction.
