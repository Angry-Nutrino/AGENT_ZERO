### Q01 [CHAT] — What is the difference between a monolithic and a microservices architecture? What are the main tradeoffs? Answer from your training knowledge.

Monolithic architecture packages everything into a single deployable unit — one codebase, one process, one database. Microservices decomposes the application into independently deployable services, each owning its own data and communicating over a network.

Main tradeoffs:

| Axis | Monolithic | Microservices |
|------|-----------|---------------|
| **Complexity** | Low initially, grows as codebase expands | High initial complexity from distributed systems patterns |
| **Deployment** | One deploy, all or nothing | Independent per service, canary deploys, rollbacks per service |
| **Scaling** | Scale the whole application or nothing | Scale only bottleneck services independently |
| **Development speed** | Fast early, slows as coordination overhead grows | Slower initially, faster at scale with clear ownership |
| **Testing** | Simple integration tests, one environment | Complex contract testing, consumer-driven tests, mocking |
| **Failure domain** | One crash takes everything down | Failure is contained (but cascading failures via network are a real risk) |
| **Data consistency** | ACID transactions across all features | Eventual consistency, saga patterns, no distributed transactions |
| **Team autonomy** | Tight coupling requires cross-team coordination | Teams own their services end-to-end |
| **Observability** | One log stream, one APM agent | Distributed tracing, centralized logging, metrics per service |
| **Latency** | In-process calls, sub-millisecond | Network calls, 1-10ms per hop, serialization overhead |

The real decision point: if you don't know you need microservices, you don't. Start monolithic, decompose when you hit a concrete scaling or organizational constraint that a monolith genuinely cannot solve. Premature microservices buy you distribution complexity without any of the benefits — that's the most common failure mode.

### Q04 [CHAT] — What is a write-ahead log (WAL) and why do databases use it for durability and crash recovery? Answer from your training knowledge.

A write-ahead log is the single source of truth for uncommitted and in-flight transactions, stored on disk before any change touches the actual data pages.

Here's the mechanics: Every transaction writes its changes to the WAL first (a sequential append-only log), then writes to the actual data pages sometime later. If the database crashes midway, on recovery it replays the WAL — committed transactions that didn't reach the data pages are redone, uncommitted ones are rolled back. The database never loses a committed write because the log on disk proves it happened.

Three properties make this work:

- **WAL Protocol** — The log entry for a change must reach stable storage *before* the corresponding data page write is allowed. No "write data first, log later" under any path.
- **Checkpoint** — Periodically, all dirty pages (modified in memory) are flushed to disk, and the WAL is trimmed up to that point. Without checkpoints, the WAL grows forever and recovery takes forever.
- **Atomic writes at the log level** — Each log record has a checksum or length field so the recovery process can detect torn writes (a partial page write from a crash during the write itself).

Why this design instead of writing directly to data pages? Two reasons. First, the WAL is sequential I/O — appending to the end of a file — which is orders of magnitude faster than random I/O to scattered data pages. Second, the log provides a single, deterministic recovery point. Without it, after a crash you'd have to scan every data page for inconsistency, with no reliable way to tell which writes succeeded and which didn't.

### Q10 [CHAT] — What is the difference between symmetric and asymmetric encryption? When is each typically used? Answer from your training knowledge.

Symmetric encryption uses a single shared key for both encryption and decryption. Asymmetric (public-key) encryption uses a pair — a public key to encrypt, a private key to decrypt.

**Symmetric** is used where both parties already share a secret and the priority is speed: bulk data encryption (AES for file storage, disk encryption, database columns), VPN tunnels, Wi-Fi (WPA2/3), and TLS session encryption after the handshake. Blowfish/ChaCha20 variants are common in messaging protocols (Signal). Typically 100–1000x faster than asymmetric on equivalent hardware.

**Asymmetric** is used for key exchange and authentication where no pre-shared secret exists: TLS handshake (RSA or ECDHE to agree on a session key), SSH key-based login, PGP/GPG email encryption, HTTPS certificate validation, and blockchain wallets (ECDSA). It solves the key distribution problem symmetric encryption cannot — Alice and Bob never need a secure channel to establish their first secret.

In practice, almost every secure system uses both: asymmetric to negotiate a symmetric session key (TLS), then symmetric for the actual data. Hybrid encryption — the combination — is the standard, not either one alone.
