### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification is the engine's way of paying for order. An LSM-tree converts random writes into sequential ones, and the cost of that transformation is that every logical write is physically rewritten multiple times.

**Where it comes from**

1. **WAL + memtable flush.** Every write first hits the write-ahead log (durability), then the in-memory memtable. When the memtable fills, it flushes as an SSTable. That's the base multiplier — roughly 1–2× physical write per logical write.

2. **Compaction — the dominant term.** The sorted structure only stays sorted because background jobs continuously merge SSTables. In level-based compaction (LevelDB/RocksDB), each level is ~10× larger than the last, and every time a key participates in a compaction into the next level, the same logical data is physically written again. A key that lives to the deepest level gets rewritten roughly once per level it crosses.

   The standard result: write amplification scales with the number of levels, O(L), and lands at **10–30×** with typical tuning. Fewer levels → less amplification but larger per-level files and costlier reads. It's a knob, not a fixed property.

   Size-tiered compaction (Cassandra, the original LSM paper) merges only when a tier reaches enough SSTables. Each merge is cheaper, but the freshly merged giant overlaps heavily with its siblings — so **space amplification** climbs, sometimes transiently holding 2–3× the logical data on disk.

3. **Everything that rides along.** Bloom filters, index blocks, checksums, and compressed data all get rewritten with their SSTable. With compression enabled, every merge decompresses and recompresses the same payload, burning CPU both ways. Tombstones and overwritten values propagate down through every level until a compaction finally reaches the deepest one holding the old version.

**What it costs in practice**

- **SSD endurance.** NAND has finite program/erase cycles. A drive rated 1 PBW under 10× amplification wears out after a mere 100 TB of logical writes. For write-heavy ingestion systems, amplification — not capacity — decides drive lifespan.

- **Throughput ceiling.** Compactions compete with foreground writes for the same device bandwidth. Sustained logical write throughput is bounded by the disk doing background work, not by your application. The gap between your write rate and what the disk actually sustains is the wasted capacity you're provisioning for.

- **Tail latency and stalls.** When compaction falls behind — write burst, degraded disk — the engine throttles or pauses incoming writes until the background catches up (RocksDB's classic L0-file-count and pending-compaction-bytes stalls). Median latency stays low; p99 spikes hard. B-trees write in-place, no compaction storm, so their tails are steadier. That's the fundamental trade you're reading about in DDIA.

- **CPU and headroom.** Compression makes compaction a decompress-merge-recompress loop, which is real CPU even at modest load. And since old and new SSTables coexist during a merge, you need 10–20% free disk just to compact. Size-tiered pushes that toward 2–3×.

- **The compounding catch on SSDs.** Logical writes smaller than the erase block trigger the drive's internal read-modify-write — so LSM amplification and SSD FTL amplification stack. A 4 KB logical write can hit flash at 16–64 KB granularity. Aligning batch and SSTable sizes to that is how production systems shave the top off the combined cost.

The reason LSM engines own ingestion-heavy workloads — HBase, Cassandra, RocksDB, InfluxDB — is that they turn high-rate random writes into sequential compaction streams, which are cheap on any physical media. The bill arrives as total device bytes written, a multiple of your logical rate, and you either provision for it or you surface the stalls.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC decouples readers from writers by never mutating data in place. When a transaction wants to update a row, it creates a *new version* of that row and leaves the old version intact. The old row still exists because some reader with an older snapshot may still legitimately see it.

Each row version carries visibility metadata — typically the transaction IDs that created and invalidated it. A reader takes a snapshot at its start (a transaction ID watermark, or a timestamp in some systems) and walks the version chain, reading only the newest version that was committed before its snapshot. So a reader never touches the writer's uncommitted changes, and a writer never has to wait for a reader to finish before writing its new version. Readers block neither writers nor other readers; writers may still block writers, but that conflict is separate from MVCC.

The garbage is dead row versions. Once every active snapshot that could possibly see the old version has ended, that version becomes unreachable — it has no future reader and no future writer. That includes rows that were updated (old version superseded) and rows that were deleted (the tombstone version marking the deletion must survive until all older snapshots are gone, otherwise a snapshot would see a row that "disappeared"). Each dead version also leaves stale index entries pointing at it.

That's what vacuuming / garbage collection exists for: Postgres runs `VACUUM`, InnoDB runs a purge thread, SQL Server has ghost cleanup. The collector scans table and index pages, identifies versions invisible to *all* open snapshots, and reclaims the space. Left alone, dead versions accumulate into table and index bloat — pages filled with versions no one can see, which hurt scan performance and cache efficiency.

The classic failure mode is a long-running transaction. It pins an old snapshot watermark, so every version created between its snapshot and now is still "visible to someone" and the garbage collector must leave it alone. One long read transaction, and bloat grows until that transaction commits. MVCC moved the cost out of the critical path but didn't eliminate it — it deferred it into background cleanup with a sharp edge: the length of your longest read transaction is the price you pay.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the incremental process of decomposing a monolith into independently deployable services — not a rewrite. The canonical path is the strangler pattern: carve out one bounded context at a time behind an API gateway, route traffic to the new service, and delete the old path only when parity is proven. The destination is organizational as much as technical: Conway's law means the service boundaries will end up mirroring your team boundaries, for better or worse.

The main risks, in order of how badly they hurt:

1. **Data splitting.** The hardest problem is the database, not the code. A monolith's tables are implicitly coupled; splitting them into per-service databases turns every cross-service join into a network call and every transaction into a distributed saga. Teams routinely underestimate how much business logic lives implicitly in shared tables and foreign keys. This is where migrations stall.

2. **Distributed systems fallacies become real.** The monolith hid latency, partial failure, and concurrency behind a function call. Once services talk over HTTP, you need timeouts, retries, circuit breakers, idempotency keys, and a failure-handling philosophy — most teams discover they need all five only after the first cascading outage.

3. **Contract drift.** Two services evolving independently will break each other unless you version contracts, implement consumer-driven testing, or both. The coupling doesn't disappear; it moves from code to the API boundary, where it's harder to detect at compile time.

4. **Premature decomposition.** Splitting on the wrong seam — before the bounded contexts are actually understood — bakes the worst coupling into the architecture and makes it *harder* to change than the monolith was. Migration is not a complexity-reduction strategy on its own; it's a complexity-relocation strategy. The monolith's complexity has to go somewhere, and if it isn't deliberately assigned to a service boundary, it becomes emergent and worse.

5. **Operational cost.** Observability, deployment, testing, and debugging all multiply with service count. A monolith has one log stream and one deployable artifact; ten services have ten of each plus the interactions between them.

The pattern worth remembering: a successful migration is measured in months, not weeks, and the teams that succeed treat it as a data-and-operations problem first, a code problem second.

### Q16 [DELIBERATE] — core_logic/tool_executor.py _number_read_file_lines. (1) What does it add to read_file output and using which arg? (2) What class of result does it REFUSE to touch, and why would numbering it be wrong?

Read the function body (lines 307–331) and the call site (lines 300–302). Both questions answered from verified source.

**(1) What it adds, and using which arg:**

It re-stamps every content line with a **correct absolute line-number prefix** in the format `{off + i + 1}: {line}` — where `off` comes from the read_file call's **`offset` arg** (`args.get("offset", 0)` at line 302, passed as the function's second parameter), and `i` is the 0-indexed position within the returned body. The first displayed line therefore gets `offset + 1`, matching the file's true 1-indexed line numbers. It preserves DC's `[Reading N lines from line M ...]` header, strips the blank separator line that DC inserts after it, and re-emits the header plus numbered body.

Purpose (from the docstring, 2026-06-02): fixing the long-standing **coordinate-drift bug**. DC's read_file returns raw content with no per-line numbers, and its offset is 0-indexed while the header prints the raw offset — so the header is off by one and the model derived line numbers from a wrong base (drift pattern: 369→368, 377→378). It must run only *after* `resource_ledger.record_read`, because the ledger needs the raw bytes for its hash to match `check_write`'s hash of the on-disk file.

**(2) What it refuses to touch, and why:**

Anything whose first line doesn't begin with `[Reading` — line 324: `if not parts or not parts[0].lstrip().startswith("[Reading"): return raw`. That covers error strings, empty results, and any output that isn't DC's formatted read_file window; the call site at line 301 doubly gates it away from `error:`/`tool error:` results.

Numbering it would be wrong because the `offset` value is only meaningful against DC's `[Reading...]` header, which defines the coordinate base of the returned window. Output without that header has no defined base — stamping numbers onto it would fabricate line coordinates for content that isn't a line-numbered file window, and the model would read those as true file positions and drift again. That re-introduces the exact bug the fix exists to eliminate.

**Design rule — threading.Lock vs asyncio.Lock:**

`threading.Lock` is used whenever the critical section can be entered from a *real OS thread outside the event loop*. The canonical case is the background memory pipeline: `memorize_episode` runs via `asyncio.to_thread`, so an `asyncio.Lock` could never be awaited by it — the vault guard (`_vault_lock`) and the episodic double-append guard (`_episodic_lock`) must therefore be threading locks, because one contender (the to_thread worker) is not a coroutine. The same logic applies to the module/class-level locks protecting files, registries, and device streams that can be touched from sync code paths.

`asyncio.Lock` is used when *every contender is a coroutine on the same event loop* — the exact counterpart is `agent.py:434`, `_miniLM_lock = asyncio.Lock()`, guarding `miniLM.encode()`, where all callers are loop coroutines and the cooperative lock suspends rather than blocks the loop.

The shorthand: **threading locks protect state shared across thread boundaries; asyncio locks serialize coroutines on one loop.** If the section can be reached from `asyncio.to_thread` or any non-loop thread, it must be `threading.Lock` — confirmed by CLAUDE.md's Vault Write Protection section ("`memorize_episode` runs inside `with self._vault_lock`"), which explicitly documents the threading lock for that cross-thread path.
