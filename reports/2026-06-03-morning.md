### Q01 [CHAT] — What is the difference between a monolithic and a microservices architecture? What are the main tradeoffs? Answer from your training knowledge.

Two architectural patterns for structuring applications.

**Monolithic**: single deployable unit — one codebase, one process, one database. Everything runs together.

**Microservices**: decomposed into independently deployable services, each owning its own data store and communicating over a network (HTTP, message queue, gRPC).

**Primary tradeoffs:**

| Axis | Monolith | Microservices |
|------|----------|---------------|
| Development velocity | Fast early, slows as codebase grows | Slower initial setup, scales horizontally with team size |
| Testing | Simple end-to-end | Complex — need contract tests, integration test harnesses per service |
| Deployment | Single artifact, one pipeline | Multiple pipelines, orchestration required |
| Scaling | Scale the whole thing | Scale only the hot path |
| Fault isolation | One crash takes everything down | A crash takes one service; bulkhead patterns protect the rest |
| Operational complexity | Low — one app to monitor | High — distributed tracing, service mesh, log aggregation |
| Data consistency | ACID transactions across entire domain | Eventual consistency, sagas, compensating transactions |
| Team autonomy | One team owns the monolith | Each team owns its services, works asynchronously |
| Refactoring cost | High — changing a module affects the whole | Lower — a service can be rewritten without touching others |
| Startup cost | Minimal — `docker compose up` | Significant — CI/CD, container registry, service discovery, API gateway |

The decision rule: start monolithic, extract services only when concrete constraints force it — a team bottleneck on a specific bounded context, a scaling ceiling on one hot path, or a reliability requirement that demands bulkhead isolation. Premature decomposition adds complexity without delivering the upside worth paying for.

### Q10 [CHAT] — What is the difference between symmetric and asymmetric encryption? When is each typically used? Answer from your training knowledge.

Symmetric encryption uses one shared key for both encryption and decryption — fast, efficient for bulk data. Asymmetric encryption uses a public/private key pair: the public key encrypts, the private key decrypts (or the private key signs, the public key verifies). It's slower but solves key distribution.

Typical usage: symmetric for encrypting files, disk volumes, database columns, TLS session data after the handshake. Asymmetric for key exchange (Diffie-Hellman, ECDH), digital signatures, certificate-based authentication, and the initial TLS handshake where the session key is established. Real-world systems almost always use hybrid — asymmetric to agree on a symmetric session key, then symmetric for the actual data.

### Q15 [CHAT] — Explain the difference between a process and a thread, and when you would choose multiprocessing over threading in Python. Answer from your training knowledge.

A **process** has its own isolated virtual address space, file descriptors, signal handlers, and PID — the OS scheduler treats it as a heavyweight unit. A **thread** shares the address space, heap, code/data, and open files within its parent process but has its own stack, registers, program counter, and errno. Context-switching between processes is expensive (TLB flush, page table swap); switching between threads is cheap (CPU cache likely warm).

In Python specifically, the **GIL** is the deciding factor. CPython's GIL prevents more than one thread from executing Python bytecode at a time, even on multiple cores. So threading in CPython is useful only for I/O-bound work where threads spend most of their time waiting (network I/O, disk reads, `time.sleep`) — they release the GIL during the wait. For CPU-bound work, threads provide zero parallelism and only add contention overhead.

**Use multiprocessing when:**
- The work is CPU-bound (computation, data processing, number crunching) and you need to utilize multiple cores.
- You need true parallelism — each process gets its own Python interpreter and GIL.
- Fault isolation matters — a crash in one process doesn't take down the others.

**Use threading when:**
- The work is I/O-bound (HTTP requests, database queries, file reads) — GIL is released during the blocking call.
- You have shared state that's expensive to pass via IPC (queues, shared memory, serialization overhead of multiprocessing).
- The number of concurrent tasks is very high — threads have lower creation and memory overhead than full processes. (Though for very high concurrency, `asyncio` usually beats both.)

**Hybrid pattern**: Use a multiprocessing `Pool` to distribute CPU-bound work across cores, and within each worker process, use threads or `asyncio` for I/O-bound sub-tasks. That's how you handle mixed workloads efficiently.
