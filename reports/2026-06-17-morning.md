### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Two approaches to the same problem — how to handle concurrent access to shared data without corruption.

**Pessimistic concurrency control** assumes conflict is likely. You lock the resource before touching it. No one else can read or write until you release the lock. Database row-level locks, `SELECT ... FOR UPDATE`, mutexes — all pessimistic.

Right choice when:
- Contention is high (same rows, same files, same data)
- Conflicts are expensive to resolve (financial transactions, inventory)
- Write frequency exceeds read frequency for the contested data
- You can afford the throughput cost of serialization

**Optimistic concurrency control** assumes conflict is rare. You read without locking, do your work on a local copy, and check before committing whether the underlying data changed since you read it. If it did — rollback and retry. MVCC in PostgreSQL, Git merges, `CompareAndSwap` operations.

Right choice when:
- Contention is low (reads vastly outnumber writes, or writes hit different records)
- Retries are cheap (computation is fast, conflict probability is small)
- Read latency matters more than write throughput
- You're building for scale where lock overhead becomes the bottleneck

The decision hinges on one variable: **cost of conflict times probability of conflict**. If the product of those two exceeds the cost of locking — go pessimistic. If not — go optimistic. Systems that need both (like CLARA's event queue with the gatekeeper) use pessimistic for the critical write path and optimistic for the read path. Correct system design usually ends up using both, at different boundaries.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Processes have isolated memory spaces — each gets its own virtual address space, file descriptor table, and PID. A crash in one process takes nothing else with it. Threads share the heap, code, data segments, and open file descriptors within a single process; only the stack, registers, and program counter are per-thread. Context switching between threads is cheap because you stay in the same address space. Switching processes requires a TLB flush and kernel-mode page table swap — orders of magnitude more expensive.

In Python specifically, the GIL adds a hard constraint: CPython threads cannot execute Python bytecode in parallel. Threading is therefore correct for I/O-bound work — waiting on network, disk, database — where threads spend most of their time releasing the GIL in C-level `select()`, `read()`, `send()` calls. Multiprocessing bypasses the GIL entirely by forking separate interpreters, so CPU-bound work that saturates cores — image processing, number crunching, batch transforms — needs multiprocessing.

Rules of thumb:
- Multiprocessing for CPU-bound: matrix multiplication, video encoding, anything where the task is "spend 100% of a core on computation."
- Threading for I/O-bound: scraping a thousand URLs, reading many files, serving an API — where the task is "wait, then do a little work, then wait again."
- Hybrid when you have both: a multiprocessing `Pool` feeding results through a queue into a threaded consumer.

One trap: multiprocessing serializes data between processes via pickle. Passing large NumPy arrays or complex objects through a `Queue` can eat your speed advantage. Memory-sharing via `multiprocessing.shared_memory` or `Array`/`Value` exists but adds coordination complexity. Threading shares memory trivially but risks race conditions — the `threading.Lock` you wrote in `_save_memory` is the right pattern.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency describes the worst-case response times at the tail of the distribution — p99 means 99% of requests finish faster, 1% take longer; p999 is the 1-in-1000 case. Average latency is dominated by the common path, so a 5ms average can hide a 500ms p999 that affects every thousandth user — and in a distributed service, that user's request fan-outs across dozens of internal calls, each with their own tail, so the probability of hitting *some* slow upstream rises exponentially with service depth. One user in fifty experiences aggregate tail if the service graph has depth 10 and each hop has a 1% p99 miss rate; that's not acceptable.

The dominant technique is **hedged requests** (Dean, 2013): issue the primary request to one replica, but if it hasn't responded within the p95 latency budget, send a second request to another replica. Use whichever returns first and cancel the loser. This collapses p999 by introducing redundancy only when the primary is already slow, not on every call — typically 5-10% extra load for 2-5x p999 improvement, depending on variance. Paid for in capacity, worth it because tail drives user-perceived slowness, and users leave at the tail.
