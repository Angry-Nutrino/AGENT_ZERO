### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design choice: data is never updated in place. Every write goes to a memtable first, then gets flushed to a sorted SSTable on disk. Over time, the system runs **compaction** — merging overlapping SSTables into new ones — which rewrites the same data multiple times.

**Where it comes from, in order of cost:**

1. **Memtable flush to L0** — the initial write. Minimal amplification (~1x). Data lands on disk once.

2. **L0-to-L1 compaction** — L0 files overlap in key range, so a single L0 file often merges with multiple L1 files. This is where amplification first becomes significant. If 4 L0 files each overlap with 4 L1 files, each byte might be rewritten 3–4 times just clearing L0.

3. **L\(_i\)-to-L\(_{i+1}\) compaction** — same pattern at each level. The deeper the data goes, the more times it's rewritten. A size-tiered compaction strategy that doubles size per level means a byte may be compacted log\(_2\)(total_data / target_sst_size) times before reaching the final level.

4. **Major compaction** — rewrites every level from scratch. Rare, but when it runs, amplification is proportional to total dataset size.

**What it costs in practice:**

- **Disk write bandwidth consumed** — for every 1 MB the application writes, the storage engine may write 10–50 MB to disk. On a 100 MB/s SSD, a sustained 2 MB/s application write rate with 20x amplification consumes 40 MB/s of the disk's bandwidth — 40% gone to compaction overhead alone. Under heavy write load, the disk saturates and write latency spikes.

- **CPU spent on merge-sort** — each compaction pass sorts and deduplicates records. At 50 MB/s compaction throughput, a single thread is often pegged. LevelDB and RocksDB use background thread pools specifically because compaction is CPU-bound.

- **SSD endurance tax** — NAND flash cells wear with each erase cycle. A 256 GB TLC drive rated for 150 TBW (terabytes written) would, at 20x amplification, die after only 7.5 TB of application data written. For write-heavy workloads — logging, time-series ingestion, event streaming — the drive fails in months instead of years.

- **Read latency jitter** — compaction consumes I/O and CPU concurrently with reads. A read request that arrives during a large compaction pass may see latency 10–100x higher than normal because the disk queue is full of compaction writes and the CPU is busy merging. Compaction also invalidates the block cache, causing more cache misses for ongoing reads.

- **Write stall** — the most visible cost. If memtable flush falls behind the write rate, or if compaction can't keep up, the engine throttles the write path. Levels 0–1 fill up → backpressure → client writes block for milliseconds to seconds. RocksDB's `WriteStall` is a direct countermeasure traded against these same costs.

LSM-trees accept this amplification because it enables the compensating advantage: sequential writes to disk, which on HDDs and SSDs alike are 10–100x cheaper per byte than random writes. The cost is real and must be budgeted in capacity planning, but the tradeoff works when you measure it properly and don't let it surprise you at 3 AM when compaction saturates your NVMe.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each reader a consistent snapshot of the database at the moment the transaction began, and that snapshot lives for the duration of the read transaction. When a writer updates a row, it doesn't overwrite the old data in place — it creates a new version of that row, tagged with the writer's transaction ID. The reader continues to read the old version from its snapshot because the new version's transaction ID is "in the future" from the reader's perspective. No lock contention, no blocking, no "readers wait for writers" scenario.

The garbage it creates is **dead row versions** — old versions of rows that are no longer visible to any active transaction. Every UPDATE and DELETE in PostgreSQL (or any MVCC engine) leaves behind a tombstone or stale tuple. The accumulation is continuous under write workloads, and if left uncollected it bloats the table, degrades index scans, and inflates cache pressure because the database has to page through dead tuples to find live ones. Cleanup is handled by **VACUUM** in PostgreSQL (or equivalent processes in Oracle/InnoDB), which scans dead tuples, marks their space as reusable, and updates the visibility map. The cost is real: VACUUM has its own I/O and CPU footprint, and a table that outruns its vacuum is the most common cause of unbounded bloat in production.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

It's a structural transition — extracting bounded contexts from a monolith into independently deployable services that communicate over a network. The main risks are:

- **Distributed transactions break ACID.** What was a single database transaction now spans multiple services. You need sagas, eventual consistency, or outbox patterns. Most teams underestimate how much their business logic relied on relational guarantees.
- **Network becomes the new failure mode.** Latency, timeouts, retries, cascading failures. A monolith that worked at 2ms inter-function calls now hits 50-100ms per service call. Circuit breakers and bulkheads become mandatory, not optional.
- **Data coupling is invisible until the split.** That "simple join" between two tables that shared the same database? Now they're behind separate services. You either duplicate data, accept stale reads, or introduce a shared schema — each with tradeoffs you didn't have before.
- **Testing complexity explodes.** Integration tests cross service boundaries. Contract tests replace unit tests. A change in one service can break six others, and you won't know until deployment.
- **Operational surface area multiplies.** One deployment pipeline becomes N. Monitoring, logging, tracing become distributed. You need OTEL, correlation IDs, and a team that understands observability — not just metrics.

The most common failure pattern: teams start splitting because the monolith is "too big" without first identifying clear bounded contexts or addressing data coupling. They end up with a distributed monolith — all the complexity of microservices with none of the autonomy, plus network failures they didn't have before.
