### Q03 [CHAT] — What is idempotency in the context of APIs? Why does it matter for retries? Answer from your training knowledge.

Idempotency means that making the same request multiple times produces the same effect as making it once. In REST APIs, the HTTP spec defines which methods are required to be idempotent by design — GET, PUT, DELETE — while POST is not.

For retries, it matters because network failures are not one-shot. When an API call times out, you have no way to tell whether the server processed the request before the response was lost. If the endpoint is idempotent, you can retry without worrying about creating duplicate orders, charging a card twice, or deleting resources that don't exist. If it's not idempotent (like a POST that creates a new resource on every call), you need idempotency keys or deduplication logic on the server side to make the retry safe.

Without idempotency, every retry is a gamble.

### Q05 [CHAT] — Explain the difference between compiled and interpreted languages. Where does Python fall? Answer from your training knowledge.

Compiled languages are translated entirely to machine code before execution — the source becomes a binary the CPU runs directly. Interpreted languages are executed line-by-line by an interpreter at runtime — no separate binary is produced before execution.

Python falls in the middle: it compiles source to bytecode (.pyc files) at import time, then a virtual machine interprets that bytecode at runtime. Neither pure compiled nor pure interpreted. That's why you get syntax errors at compile time but type errors at runtime, and why a simple script feels instant while a complex import chain pauses to compile first.

### Q08 [CHAT] — What is the difference between latency and throughput? Give an example where optimizing one hurts the other. Answer from your training knowledge.

Latency is the time a single unit of work takes from request to completion. Throughput is the number of units completed per unit time.

Classic example: a batch processing pipeline. Batching 1,000 requests together instead of handling them individually increases throughput because the overhead per request drops. But the first request in line now waits for 999 others to arrive and finish before it returns — latency for that request goes up by orders of magnitude. Optimizing one directly degrades the other.

### Q15 [CHAT] — What is the difference between a deadlock and a livelock? How do they differ? Answer from your training knowledge.

A deadlock is a state where two or more threads wait forever for a resource held by the other — no thread makes progress. A livelock is when threads are not blocked but keep reacting to each other's state changes, constantly retrying without making actual forward progress.

Three key differences:

1. **Blocking state:** In deadlock, threads are blocked and consume no CPU. In livelock, threads are active — they're running, checking, yielding, retrying — burning cycles without completing work.

2. **Detection difficulty:** Deadlock is easier to detect (blocked threads, timeout triggers). Livelock looks like activity. The system appears busy but nothing finishes — harder to distinguish from normal processing.

3. **Resolution:** Deadlock requires breaking one of the Coffman conditions — typically preemption or breaking circular wait. Livelock needs a change in the retry logic — random backoff, priority inversion, or a different coordination strategy so threads stop responding to each other's transient states.

Real-world example: Two processes each need two files. Each locks one and waits for the other — deadlock. If instead they detect the conflict, release their lock, and retry in lockstep — same timing each time — they never finish. That's livelock.
