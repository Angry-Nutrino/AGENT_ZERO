### Q01 [CHAT] — Explain the difference between horizontal and vertical scaling. What are the tradeoffs of each? Answer from your training knowledge.

**Horizontal scaling** — adding more machines to distribute load. **Vertical scaling** — adding more resources (CPU, RAM, disk) to a single machine.

**Horizontal tradeoffs:**
- +: Elasticity, fault tolerance (one box dies, others take over), theoretically infinite scale, commodity hardware
- −: Distributed systems complexity (consistency, coordination, network latency), operational overhead, state management becomes painful, requires application-level awareness (sharding, partitioning)

**Vertical tradeoffs:**
- +: Simpler architecture — no distributed state, no network partitioning, easier to reason about, lower operational overhead, familiar mental model
- −: Hard ceiling — eventually you run out of slots on the motherboard, downtime for upgrades, single point of failure, diminishing returns (each additional unit of resource costs more than the last), and at some point the hardware simply doesn't exist yet

**Decision rule:** Start vertical until you hit either a hard ceiling or the cost curve inverts (smaller commodity machines + orchestration becomes cheaper than one giant box). Then go horizontal — but only if your application is architected for it from the start. Retrofitting horizontal scaling onto a vertically-built system is where most of the pain lives.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

Each reader gets a snapshot of committed rows at the moment its transaction began, via transaction IDs and visibility rules — writers create new row versions (copy-on-write) that the reader can't see yet, so neither blocks the other. The garbage is dead row versions: expired versions no longer visible to any active transaction (bloat), plus committed versions that a writer created but no reader needs. PostgreSQL reclaims these via `VACUUM` — otherwise the table grows unbounded with invisible tuples.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a single monolithic application into a set of independently deployable services that communicate over a network, each responsible for a bounded business capability.

The main risks, in order of how often they collapse a migration:

1. **Premature decomposition** — carving out services along technical layers (a "database service," a "business logic service") rather than bounded contexts, which produces a distributed ball of mud with all the cost and none of the benefit.

2. **Distributed transactions** — a single monolithic transaction over two tables becomes a saga or two-phase commit over two services. Data consistency guarantees degrade, rollback logic multiplies in complexity, and idempotency bugs surface months later in production.

3. **Network as a new failure domain** — a method call that took microseconds and never failed is now a network hop with latency variance, timeout semantics, partial failure modes, and cascading retry storms that can take down an entire fleet.

4. **Data coupling** — the monolith's database had joins, foreign keys, and ACID. After the split, services own separate data stores, and what was a simple query now requires orchestration, materialized views, or eventual consistency that the business may not tolerate.

5. **Testing complexity** — integration tests that spun up one process now need service stubs, contract tests, and chaos engineering tooling. CI pipelines that ran in ten minutes now take forty because dependencies must be provisioned. Teams without this infrastructure ship broken contracts to production.

6. **Operational surface area** — one deployable becomes ten. Monitoring dashboards, log aggregation, secret management, and deployment pipelines each multiply. If you don't have container orchestration, service mesh, and observability stack before the split, you're building the airplane while flying it.

7. **Team coordination overhead** — what was a single code review becomes cross-team API contracts, version negotiation, and shared breaking-window coordination. Conway's law inverted: the architecture forces communication patterns the organization didn't ask for.

The pattern that survives is **Strangler Fig**: isolate one bounded context behind an interface, route traffic incrementally, validate in production, and only then remove the old code. Anything that decomposes the entire monolith in one cut fails — not because the architecture is wrong, but because the migration itself introduces too many simultaneous unknowns.
