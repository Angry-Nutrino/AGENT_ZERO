### Q01 [CHAT] — Explain the difference between a cache hit and a cache miss. What is cache locality and why does it matter for performance? Answer from your training knowledge.

**Cache hit:** The data requested is already in the cache. Access is fast — single-digit nanoseconds for L1, ~10–40 ns for L2.

**Cache miss:** The data isn't in the cache. The CPU stalls while fetching from main memory (DRAM) — ~100–200 ns penalty, or 10–100x slower than a hit. Worse, a miss to disk (page fault) costs milliseconds.

**Cache locality** is the observation that programs tend to access data that is spatially or temporally close to previously accessed data.

- **Temporal locality:** If you accessed an address now, you'll likely access it again soon. (Loop counters, frequently called functions.)
- **Spatial locality:** If you accessed address X, you'll likely access X+1, X+2 next. (Array traversal, struct fields allocated together.)

**Why it matters:** Modern CPUs are dramatically faster than memory buses. Without cache locality, the CPU spends most of its time waiting on RAM, dropping effective throughput to 5–15% of theoretical peak. Exploiting locality — compact structs, sequential access patterns, aligned allocations, hot/cold splitting — is the difference between a database that does 10K QPS and one that does 1M QPS on the same hardware.

### Q04 [CHAT] — What is the difference between a REST API and a GraphQL API? When would you choose each one? Answer from your training knowledge.

REST and GraphQL are fundamentally different approaches to API design.

**REST (Representational State Transfer)** operates on resources identified by URLs. Each endpoint returns a fixed structure. The server defines the response shape. Operations map to HTTP verbs — GET, POST, PUT, DELETE. Stateless by design, cacheable at the HTTP level.

**GraphQL** exposes a single endpoint. The client specifies the exact shape of the response. Queries mirror the data graph. Mutations handle writes. Subscriptions enable real-time updates. The server provides a schema, not a fixed set of endpoints.

**When to choose REST:**
- Simple CRUD applications where endpoints map cleanly to resources
- Systems that benefit from HTTP caching — CDNs, reverse proxies, browser cache
- File uploads or binary data transfer
- When you want predictable API behavior with minimal client complexity
- Teams that don't need the overhead of a query language and schema management
- Public APIs consumed by a wide variety of clients you don't control

**When to choose GraphQL:**
- Complex data relationships where clients need nested, related data in one request — dashboards, mobile apps, data-heavy UIs
- Multiple frontend clients (web, mobile, IoT) with different data needs from the same backend
- Rapid frontend iteration where changing the API shape weekly isn't viable
- When over-fetching and under-fetching (REST's classic problems) are costing noticeable bandwidth or latency
- Teams that need strong typing and self-documenting APIs via the schema

**The tradeoff:** REST is simpler, more mature, and easier to cache. GraphQL shifts complexity from the client to the server — resolver performance, N+1 queries, and authorization granularity all become the backend's problem. GraphQL is a solution to specific data-fetching problems, not a replacement for REST everywhere.

### Q10 [CHAT] — What is eventual consistency in distributed systems, and give an example of where it is acceptable? Answer from your training knowledge.

Eventual consistency guarantees that if no new updates are made to a data item, eventually all reads will return the last updated value. There is no immediate guarantee — replicas may return stale data for an unbounded window until convergence completes.

Acceptable in DNS. A domain record update can take hours to propagate across the world's nameservers. A user in Tokyo hitting an old IP while the record propagates is a minor inconvenience, not a catastrophe. The system is still usable and the eventual state is what matters. No transaction, no financial liability, no safety-critical timing constraint.
