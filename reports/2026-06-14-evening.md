### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from three distinct sources. First, the memtable flush — every write hits memory and is then written to disk as an immutable SSTable regardless of whether the data is hot or cold. Second, compaction — the system continuously merges overlapping SSTables across levels to maintain read performance and bound the number of files that must be checked per lookup. A single write may be rewritten many times as it moves down the tree through successive compaction rounds. Third, the write-ahead log — every write goes to a WAL on disk before it touches the memtable, adding a fourth write factor.

In practice, level-based compaction in a typical LSM (LevelDB/RocksDB default) produces write amplification of roughly 10-15×. Each byte the application writes results in 10-15 bytes written to disk. A database handling 100 MB/s of application writes will sustain roughly 1-1.5 GB/s of actual disk I/O. On consumer SSDs with ~500 MB/s sustained write throughput, that caps your write workload at roughly 30-50 MB/s before you hit the drive's performance ceiling. On NAND flash with limited program-erase cycles, the practical cost is accelerated wear — 10× write amplification means a drive rated for 300 TBW will become write-bound after 30 TB of application writes instead of 300 TB.

The trade-off LSM-trees accept for this is straightforward: high write throughput at the cost of write multiplication and, in exchange, far better read performance than B-trees on write-heavy workloads because incoming writes never randomly page into existing data blocks. LevelDB's default compaction strategy optimizes for this by keeping the number of SSTables per level bounded. Tiered compaction (Cassandra, HBase) reduces amplification further at the cost of more space amplification and slightly worse reads. Choosing between them is a decision about whether your bottleneck is write endurance or read latency against your working set.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives each read a snapshot of the database as of that transaction's start timestamp. The read operates on those committed versions without acquiring a lock, so a concurrent write transaction can proceed unblocked. The write creates a new version of the row (or pages, or index entries) that isn't visible to that snapshot. The writer and reader never contend on the same resource because they're logically operating on different data.

The garbage is **dead row versions** — old tuples in storage that are no longer visible to any active transaction. These accumulate as write transactions overwrite or delete rows while long-running reads hold snapshots that still need the old version. The cleanup is **VACUUM** (PostgreSQL) or an equivalent background process (InnoDB's purge thread, SQL Server's ghost cleanup) that recycles the storage and updates visibility maps. Two properties determine whether the garbage builds up: transaction ID wraparound (forcing a freeze) and the oldest active snapshot's age — if that snapshot never closes, nothing below it can be reclaimed.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services that communicate over a network, each owning its own data and business capability.

The main risks, in order of severity:

**1. Distributed transactions and data consistency** — The monolith's ACID transactions across bounded contexts break. You now need sagas, eventual consistency, or two-phase commit (which you should avoid). Most teams underestimate how much their business logic relies on a single database transaction that just works.

**2. Network becomes the new failure mode** — Every service call that was a local function call now goes over the network. Latency spikes, partial failures, cascading timeouts, retry storms. You need circuit breakers, timeouts, bulkheads, and idempotency — infrastructure the monolith never needed.

**3. Premature decomposition** — Splitting along technical layers (frontend/backend/database) instead of business domains. You end up with distributed tiers, not services. The result is a distributed monolith — all the complexity of microservices with none of the benefit, because a change still touches everything.

**4. Testing complexity** — Integration tests now require orchestrating multiple service instances, managing their state, and handling asynchronous boundaries. Unit tests alone won't catch the behavioral gaps. Most teams keep running monolith-style integration tests and miss the cross-service failures that only surface in production.

**5. Observability debt** — In a monolith, one log file, one stack trace, one health endpoint. After migration, you need distributed tracing, centralized logging, metrics aggregation, and structured logging from day one — not as an afterthought.

**6. Organizational coupling that mirrors the architecture** — Conways Law is not optional. If your teams are organized by technical layer (a DB team, a backend team, a frontend team), you will build a distributed monolith regardless of your service boundaries. Service boundaries must follow team boundaries, not the other way around.

**7. Deployment complexity explosion** — One deploy pipeline becomes N pipelines. Coordinated deploys, version compatibility across services, rolling back a single service when the issue is cross-service interface drift — all harder than the monolith's single artifact rollback.

**8. Data ownership and query patterns** — Reporting queries that once JOINed across the entire database now need API composition, CQRS, or a separate read-model service. Every cross-service query becomes a synchronous chain of N+1 calls unless you deliberately design for it.

The pattern that fails most consistently: spinning up Kubernetes and service mesh first, then trying to fit the monolith decomposition into whatever that infrastructure forces. Service boundaries and data ownership decisions come before infrastructure. Always.
