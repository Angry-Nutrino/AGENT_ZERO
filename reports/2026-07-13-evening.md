### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from three distinct sources, each tied to the architecture's design choices.

**Where it comes from:**

1. **Repeated writes to the same data.** Every mutation (insert, update, delete) is first appended to the in-memory memtable. When the memtable is flushed to disk as an immutable SSTable, the data is written once. Then, during *compaction* — the process that merges overlapping SSTables into larger, sorted runs — the same logical data is read from several SSTables, merged, and written back as a new SSTable. Each compaction level can rewrite data multiple times. Tiered compaction (LSM's default approach in many engines) rewrites data many more times than leveled compaction.

2. **Minor, major, and merge cascades.** A write goes through a pipeline: (a) memtable flush writes it once, (b) minor compaction merges level 0 → level 1, (c) major compaction merges across levels as data trickles downward. A single key inserted at level 0 may be rewritten at every level boundary it crosses. In a tree with L levels, worst case is O(L * write_size) bytes written per logical byte ingested.

3. **Block overhead and padding.** SSTable blocks are padded to block boundaries, index blocks are rebuilt during compaction, bloom filters are regenerated — all additional bytes written that the user never sees in their data payload.

**What it costs in practice:**

- **Write throughput ceiling.** On NVMe SSDs rated for ~3 GB/s sequential writes, write amplification of 10× means your *usable* write throughput is 300 MB/s — the rest is compaction overhead burning bandwidth. Your disk's physical write endurance is consumed at that amplified rate; a 600 TBW consumer SSD handling 50 GB/day of *logical* writes at 10× amplification lasts ~100 days instead of ~3 years.

- **Read amplification trade-off.** High write amplification is tolerated in LSM-trees precisely because compaction keeps data sorted and well-partitioned, so reads remain efficient (O(log N) SSTable lookups). This is the fundamental LSM bargain: you burn write resources to maintain read performance at scale. Compare with B-trees, which have near-zero write amplification (each page written exactly once) but suffer write-heavy random I/O on updates because they modify pages in place.

- **Real-world numbers.** LevelDB's default leveled compaction achieves roughly 10–15× write amplification under steady state. RocksDB with tiered compaction can go as low as 3–5× on the write path but pays for it in higher space amplification (more stale data on disk). Cassandra's size-tiered compaction is notorious for 20–30× during heavy compaction loads.

The practical cost is a CAP-like tradeoff: you can tune compaction style to minimize write amplification (tiered → lower WA, higher space amp) or minimize space amplification (leveled → higher WA, compact storage), but you cannot eliminate both simultaneously. The disk endurance of the underlying hardware sets the absolute floor on what your workload can sustain.

Martin Kleppmann covers this exact tradeoff in chapter 3 of *Designing Data-Intensive Applications*, including the formula for total bytes written as a function of compaction strategy — worth revisiting if you want the math.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC gives every read transaction a snapshot of the database as of a specific point in time — usually the transaction's start timestamp or its assigned transaction ID. When a writer modifies a row, it doesn't overwrite the existing version; it creates a new version marked with the writer's transaction ID and the visibility rules that govern which transactions can see it. The reader simply reads from its snapshot, so it never waits for the writer to commit. The writer likewise never blocks a reader — it just appends the new version.

What accumulates is **dead tuple versions**: rows that are no longer visible to any active or future transaction because a newer version superseded them or the transaction that created them aborted. These dead tuples waste storage in the table (and its indexes) and degrade scan performance because the engine has to skip over them. Cleaning them up is the job of a **VACUUM** (PostgreSQL) or **purge/garbage collection** (MySQL InnoDB's purge thread, Oracle's undo retention) — a background process that reclaims the space once it can prove no transaction still needs that version for snapshot consistency. The trade-off is that readers never block writers, but the system pays in storage bloat and GC overhead until the old versions are actually safe to remove.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services, each owning its own data and communicating over a network.

Main risks when splitting a monolith:

**Distributed system complexity** — Network calls replace in-process function calls. Latency, partial failure, and network partitions become first-class concerns. You lose the guarantee that a transaction either fully succeeds or fully rolls back.

**Data consistency** — The monolith's single database is replaced by per-service databases. Distributed transactions (2PC) are fragile and slow. Eventual consistency and saga patterns introduce reconciliation logic that didn't exist before.

**Coupling that hides as modularity** — Teams split by team structure rather than bounded context, leaving hidden shared schemas, synchronized deployments, and cross-service transactions that violate the independence principle. The system behaves like a distributed monolith — worst of both worlds.

**Observability gap** — A single log file and application dashboard becomes scattered traces across twenty services. Without distributed tracing, metrics per service, and structured logging with correlation IDs, debugging a failed request becomes a scavenger hunt.

**Network overhead** — Serialization, deserialization, and network latency for every cross-service call. Chatty service interactions (one service making five calls to complete a request) amplify this into significant perf degradation.

**Organizational coordination** — Service boundaries that don't match team boundaries create constant cross-team negotiation. Conway's law in reverse: you're fighting your own org chart.

Two unstated ones that kill projects silently: the cost of maintaining the monolith *and* the services in parallel during migration (you don't get to stop the old system), and the assumption that your monolith was well-structured enough to extract cleanly in the first place. Most aren't.
