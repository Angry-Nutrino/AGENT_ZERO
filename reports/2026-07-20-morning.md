### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Start with the database's assumption about the future.

**Pessimistic** assumes collision is likely. You lock the row (or page, or table) *before* you touch it — `SELECT ... FOR UPDATE`, write locks, read locks, mutexes in application code. Other transactions wait. Throughput drops under contention, but you never lose a write or have to retry. Right choice when: contention is high, writes are expensive (financial transactions, inventory decrements where overselling costs real money), or retries are dangerous (the operation is not idempotent).

**Optimistic** assumes collision is rare. You read a version number or timestamp, perform the update, and the database rejects the write if the version changed between read and commit — typically via a `WHERE version = :old_version` check that affects zero rows, or a Snapshot Isolation conflict in PostgreSQL/InnoDB. No locks held during the transaction. Higher throughput under low contention, but the writer must handle the `0 rows affected` error and retry. Right choice when: contention is low, reads dominate writes, the data is mostly immutable (append-log patterns), or the cost of a retry is negligible (counters, cached aggregates, user profile edits).

The trap is mixing them blindly. Pessimistic with MVCC underneath (PostgreSQL's `SELECT ... FOR UPDATE` inside a snapshot) can create deadlocks that don't surface until production under load. Optimistic under high contention turns a brief read into a retry storm that cascades. Know your collision profile before choosing.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Processes have isolated memory spaces — each gets its own heap, stack, and file descriptor table. Threads share the heap, code segment, and open file handles within a single process; only each thread's stack, registers, and program counter are private. Context-switching between threads is cheaper (no TLB flush, no page table switch) but a thread crash can take down the whole process.

In Python, the GIL makes this less clean. For CPU-bound work — number crunching, image processing, anything that keeps Python bytecode running — multiprocessing is the only real option because each process gets its own GIL. Threading still works for I/O-bound tasks: network requests, file reads, database queries, where the GIL is released during blocking syscalls. The overhead trade-off is initialization cost — spawning a process is heavier than starting a thread, but you get true parallelism.

The pattern I'd recommend: `concurrent.futures` for both. `ProcessPoolExecutor` for CPU-bound, `ThreadPoolExecutor` for I/O-bound. The interface is identical, so you can swap without restructuring code — and that's the practical answer about 90% of the time.

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Average latency hides the problem. P99 tail latency tells you what the slowest 1% of requests actually experience — and because a single user request fans out across dozens of microservices, they hit that tail at every hop. One slow call in the chain makes the whole response slow for that user. That's why tail latency is the bottleneck: you can optimize the mean until it glows, and 1% of users still have a terrible experience. Average is a lie; the tail is truth.

One technique: **hedged requests**. Send the same request to two replicas, take whichever responds first, cancel the other. Instead of waiting for the slowest 1%, you race two servers and the fast one always wins — your effective tail becomes the minimum of two independent draws from the latency distribution, which collapses the long tail dramatically. The cost is 2× load on the backend, so you use it selectively: only for requests already past a small timeout, or for the critical path of a user-facing call.
