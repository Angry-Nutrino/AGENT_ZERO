### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental tension between their design — accept writes fast, sort them later — and the reality that data must eventually land in a single, sorted, on-disk structure.

**Where it comes from — three compounding layers:**

1. **Compaction churn.** Every level merge reads a set of SSTables from level *N*, merges them with overlapping SSTables from level *N+1*, and writes out new SSTables to level *N+1*. That's every byte read and written *again* each time it moves down a level. With size-tiered compaction (LevelDB/Cassandra default), each level is ~10× larger than the previous, so a single record may be rewritten dozens of times over its lifetime.

2. **Memtable flush.** The in-memory sorted structure (memtable) is written to disk as an SSTable when full. That's one write — but as that SSTable participates in the first compaction, it's read back and rewritten immediately. Fresh data gets hit twice before it settles.

3. **Write-ahead log.** The WAL writes every mutation to disk *before* the memtable accepts it. This is sequential and cheap, but it's still an additional write of the same data that will be compacted later. Adds ~1× write amplification at minimum.

**The practical costs:**

- **Disk endurance.** On SSDs with finite write cycles (NAND flash), an LSM-tree's write amplification of 10–30× means a drive rated for 100 TBW fails after 3–10 TB of *logical* writes. This is the primary reason Cassandra and LevelDB users destroy consumer SSDs in production. RocksDB's leveled compaction with compression at higher levels mitigates this at the cost of CPU.

- **CPU spent in compaction.** Compaction is a multi-threaded blocking merge sort, repeated constantly. At steady state, a busy write workload can spend 40–60% of CPU cores on compaction threads, not serving queries. This is hidden from latency metrics — the queries just slow down because compaction steals IOPS and CPU.

- **Stall risk.** When compaction falls behind — write rate exceeds compaction throughput — the write path stalls. RocksDB reports this as "write-stall" events in its statistics. The database stops accepting writes until compaction catches up. The practical cost is unpredictable p99 latency spikes: a system doing 10K writes/sec suddenly drops to 0 for seconds at a time.

- **Read amplification as a derivative cost.** Compaction produces overlapping SSTables at higher levels (level 0 in most designs), requiring more files to probe on point reads. This forces larger bloom filters or more IOPS per read. Trade-off: you can compact aggressively to reduce read amplification (higher write-amp) or compact lazily to save disk writes (higher read-amp). Tuning is the permanent negotiation between these two.

- **Space amplification.** Old SSTables are deleted only after the new merged output is written and synced. During compaction, both the old and new files co-exist on disk. A compaction-happy workload can temporarily use 2× the logical data size in physical storage.

The real-world takeaway: LSM-trees trade write throughput (excellent for ingestion) against write amplification (terrible for flash endurance) plus read amplification (acceptable with bloom filters). B-trees have the opposite profile — higher raw write cost per operation but lower amplification — which is why you see B-tree engines on flash with a FTL layer and LSM engines on spinning rust or in workloads that batch and retire data (logs, time-series).

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works by giving each transaction a snapshot of the database at a point in time — typically the transaction's start timestamp or the most recently committed version before that timestamp. When a writer modifies a row, it doesn't overwrite the existing data. It creates a new version of that row tagged with the writer's transaction ID, while the old version remains visible to any reader whose snapshot predates the write. The reader simply continues reading the old version from its snapshot, never seeing the in-progress write. The writer never blocks, and the reader never waits.

The garbage it creates is dead row versions — old versions that are no longer visible to *any* active or future transaction because all transactions that could have seen them have committed or aborted. This accumulates in the table's page storage as bloat, degrading scan performance and cache efficiency until a garbage collection process — usually called vacuum in PostgreSQL, or a background version cleanup in Oracle/InnoDB — reclaims the space. If GC falls behind, you get transaction ID wraparound risk and unbounded table growth.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

Microservices migration is the process of decomposing a monolithic application into a set of independently deployable services, each owning its own data and communicating over a network. The migration typically proceeds incrementally — strangler fig pattern, extracting bounded contexts one at a time — rather than a full rewrite.

The main risks:

**Distributed systems complexity** — what was a local function call becomes a network call. You inherit partial failure, latency variance, and the need for retry logic, circuit breakers, and timeouts. The system is now subject to the fallacies of distributed computing.

**Data consistency** — the monolith's ACID transactions across modules must be replaced with eventual consistency, sagas, or two-phase commit (which carries its own trade-offs). This is where most teams get hurt: they split the code but keep a shared database, and end up with distributed coupling without the benefits of either model.

**Testing blind spots** — integration tests that ran in-process now require orchestrating multiple services, each with its own database and network state. Contract testing becomes necessary but is rarely done early enough.

**Observability debt** — a monolith logs to a single file. A distributed system requires structured logging with trace IDs, metrics aggregation, and distributed tracing. Teams often ship the architecture without the instrumentation and operate blind when something breaks.

**Organizational friction** — Conway's law works against you. If your teams aren't aligned to the service boundaries, you end up with coordination overhead that exceeds the monolith's build times. The architecture forces organizational change whether you planned for it or not.

The single biggest mistake: splitting for the sake of splitting, without a concrete driver (scale, team velocity, deployment frequency) that justifies the cost. Microservices extract a tax on every interaction — only worth it when the bottleneck is no longer solvable inside the monolith.
