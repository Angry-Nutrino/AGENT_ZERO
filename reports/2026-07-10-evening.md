### Q05 [CHAT] — Explain write amplification in LSM-tree storage engines: where it comes from, and what it costs in practice. Answer from your training knowledge.

Write amplification in LSM-trees comes from the fundamental design choice: writes arrive as sequential appends (memtable → SSTable), but the system must continuously compact those immutable files to maintain read efficiency and reclaim space.

Three sources, in order of impact:

**Compaction.** Minor compactions flush the in-memory memtable to an L0 SSTable. Then major compactions merge overlapping SSTables across levels — reading N input files, merging into one sorted output, writing it back. Every byte in an SSTable gets rewritten multiple times as it descends through levels. A level-based compaction strategy (LevelDB-style) with size ratio `r` and Lmax levels means each byte is written once per level it passes through. With r=10 and 7 levels, a byte can be written ~7–14 times before reaching the max level.

**Size-tiered vs leveled tradeoff.** Size-tiered (Cassandra default) delays compaction until enough SSTables accumulate at a tier — writes spend less time being compacted early, but read amplification spikes because query must check more files. Leveled compaction (RocksDB, LevelDB) compacts aggressively and continuously, trading higher write amplification for bounded read amplification. There is no free lunch here; you choose which side of the curve you optimize for.

**The hidden costs.** Write amplification doesn't just consume disk bandwidth engineering. The practical costs are threefold. First, it steals IOPS that could serve user writes — on SSDs with finite write endurance, every extra write cycle physically wears the NAND cells. A 10x write amplification on a consumer SSD rated for 150 TBW means you consume that budget 10x faster than the application layer expects. Second, compaction increases latency tail variance — a flushing memtable or a major compaction can saturate the disk queue, delaying incoming writes by tens to hundreds of milliseconds. Third, it forces overprovisioning: you provision IOPS capacity for the *amplified* write load, not the application write rate, inflating infrastructure cost.

The practical rule of thumb: LevelDB-style systems see 10–30x write amplification under steady state. RocksDB's tiered + leveled hybrid can bring that down to ~4–6x on write-optimized workloads, but at the cost of more complex tuning and higher background CPU. B-tree-based systems (InnoDB, WiredTiger) typically run 1–3x amplification from their B-tree page splits and checkpoint writes — dramatically lower, but they pay it on random-write workloads where LSM-trees excel at ingest throughput. The tradeoff is the entire reason Kleppmann's "LSM-Trees vs B-Trees" section exists.

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works by giving each reader a snapshot of the database at a point in time — typically the transaction ID at which the read started. Writes don't overwrite existing rows; they create new versions tagged with the writing transaction's ID. The reader's snapshot determines which versions are visible: it only sees versions committed before its snapshot began, ignoring any versions created later or written by uncommitted transactions. Since the writer creates a new version rather than locking the old one, both operations proceed in parallel.

The garbage it creates is **dead tuple versions** — old row versions that no active snapshot can ever see again. When all transactions that could have observed a given version have completed, that version becomes dead space in the table. In PostgreSQL this is called bloat: the table file accumulates dead tuples that must be reclaimed by `VACUUM`. Without cleanup, bloat grows unbounded — degrading index efficiency, blowing out buffer cache, and eventually forcing the database to scan pages full of data it can never return. Autovacuum is standard, but on write-heavy workloads it can fall behind, and until it catches up, every read pays the cost of skipping dead tuples.

If a given `os.replace` fails and exhausts its retries, there is no data loss because the atomic‑persist sequence never touches the live `memory.json` file until `os.replace` succeeds (the temp file is written first, and the live file is only overwritten atomically). ### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services that communicate over a network, each owning its own data and business capability.

The main risks:

**Network boundaries become trust boundaries** — what was an in-process function call is now a network hop. Latency, partial failure, and serialization overhead are no longer exceptional cases; they're the steady state. You don't just split code — you split failure modes.

**Data decomposition is the hard part** — the monolith's shared database has implicit joins, cross-schema transactions, and integrity constraints that don't survive the split. You either accept eventual consistency, implement the saga pattern, or introduce an orchestration layer — each with its own operational cost and failure surfaces.

**The service boundary is almost always wrong on the first attempt** — you cut along what looks like a clean seam (users vs orders vs payments) and discover that business transactions span three services, or that what you thought was a bounded context shares a hot path that now takes 40ms instead of 400μs. Refactoring service boundaries mid-flight is more expensive than refactoring module boundaries inside a monolith.

**Observability debt compounds** — a single request now traces through N services, each with its own logs, metrics, and exception handling. Without distributed tracing, you're debugging a distributed system with monolith tools. You discover gaps not when you deploy — but when you're trying to explain a 4-second p99 to a customer.

**Transactional integrity becomes a distributed systems problem** — the monolith relied on ACID; the microservices architecture relies on patterns (saga, outbox, two-phase commit with all its caveats). Teams that skip this migration and assume eventual consistency is "good enough" discover the hard way that inconsistent state propagates faster than compensating transactions can correct it.

**Team topology either accelerates or destroys the architecture** — Conway's law in reverse: if you decompose the monolith into services but keep the same team structure, you get the operational complexity of microservices with none of the independent deployability benefit. The architecture is downstream of the org chart, not upstream of it.

The honest assessment: don't migrate for technical reasons unless the monolith is demonstrably blocking deployment frequency or team throughput. Migrate because the cost of *not* migrating exceeds the cost of managing distributed systems — and that's a higher bar than most teams calculate.
