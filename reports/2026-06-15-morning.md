### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Optimistic concurrency control assumes conflicts are rare — you read data, do your work, and at the commit point you check whether the underlying data changed since your read. If it did, you abort and retry. Pessimistic concurrency control assumes conflicts are likely — you lock the resource at read time and hold the lock until the transaction commits, so no one else can touch it.

Optimistic is the right choice when read-write ratio is high, contention is low (same records rarely accessed by multiple writers), and the cost of an occasional retry is acceptable — think analytics dashboards, catalog reads, or your personal todo list. Pessimistic wins when contention is high, retry cost is prohibitive, or you need deterministic ordering — think inventory deduction during Black Friday, bank ledger transfers, or seat booking on a single flight.

There's a middle ground: optimistic with backoff strategies works well up to about 20% conflict rate. Above that, the retry overhead exceeds the locking overhead, and you should switch to pessimistic. The decision also depends on lock granularity — row-level pessimistic locks with short hold times can outperform optimistic retries even at moderate contention, because the wait is cheaper than the re-execution. Your system's latency budget and your database's deadlock detection mechanism matter more than textbook theory.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Processes run in isolated memory spaces — each has its own heap, stack, address space, and file descriptor table. Context switching between processes is expensive because it requires a full TLB flush and address space switch. Threads share the heap, code, and file descriptors within the same process — each gets its own stack and program counter. Context switching between threads is cheap, but in CPython the GIL serializes CPU-bound Python code even across threads.

**Use multiprocessing when** the work is CPU-bound — compute, number crunching, image processing. Each process gets its own GIL, so you get true parallelism across cores. Downside: IPC overhead, higher memory footprint, harder to share state.

**Use threading when** the work is I/O-bound — network calls, file reads, database queries. Threads block on I/O and release the GIL while waiting, so you can overlap many operations without paying process overhead. Shared memory makes coordination simpler (with appropriate locks).

**Hybrid pattern** that works well: thread pool for concurrent I/O, process pool for the compute result each thread collects. That's what you'd use for something like an agent orchestrator that talks to an LLM (I/O) then does token processing or embedding (compute).

### Q15 [CHAT] — Explain tail latency (p99/p999): why it dominates user experience in distributed services more than average latency, and one architectural technique to tame it. Answer from your training knowledge.

Tail latency is the long tail of slow requests — the 99th or 99.9th percentile. The average hides it: you can have 20ms p50 and 3s p999 in the same distribution, and the average looks fine.

It dominates user experience because of *fan-out* and *synchronous composition*. In a distributed service, a single user request touches 20–100+ nodes. If each node has a 1% chance of being a p99 outlier, the chance *any* of those 20 nodes is slow approaches 1 - (0.99)^20 ≈ 18%. By 100 nodes it's ~63%. The user waits on the *slowest* component in their critical path, not the average. Average latency is a server-side metric; tail latency is what the user actually experiences.

The canonical architectural technique is **hedged requests** (Google's approach, described by Dean & Barroso): issue the same request to *two* replicas, wait for whichever finishes first, cancel the other. This transforms the p999 of a single replica into the p001 of the *minimum* of two independent draws — dramatically cutting the tail. The cost is ~2x load on the backend, so you apply it selectively: only to requests already past a latency threshold (a "tied" request), or only on the critical path. Variant: **backup requests** with a small delay — send the primary, wait 10ms, if no response, send a backup. Either way, you're exploiting the independence of server slowdowns to probabilistically dodge the slow ones.
