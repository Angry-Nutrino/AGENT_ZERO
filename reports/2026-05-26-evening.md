### Q12 [CHAT] — Explain what the ResourceLedger does in CLARA's concurrent task architecture. What two race conditions does it prevent?

ResourceLedger is the read/write tracking layer in `conflict.py` — a dict mapping `task_id` to `{"reads": set(), "writes": set()}`. Every tool call that touches the filesystem reports back through `resource_callback`, which populates the sets with file paths. That's the source of truth for whether two concurrent tasks are stepping on each other.

It prevents two race conditions:

1. **Read-after-write staleness** — Task A writes to a file while Task B, in-flight and unaware, reads the same file. B gets pre-or- during-write content. ResourceLedger flags the write set of A against the read set of B at dispatch time so the arbiter can pause or reorder.

2. **Write-after-write corruption** — Two tasks both write to the same file. Last writer wins silently, first writer's output is lost, no signal. ResourceLedger catches overlapping write sets before the second task starts executing.

Layer 2 (`[ACTIVE TASKS]` block in context) is a soft advisory — the LLM can ignore it. ResourceLedger is the hard enforcement path that feeds into `ConflictDetector.check()` for decisioning.
