### Q01 [CHAT] — Explain the difference between optimistic and pessimistic concurrency control, and when each is the right choice. Answer from your training knowledge.

Two fundamentally different bets on whether contention will happen.

**Pessimistic locking** assumes conflict is likely and prevents it upfront — you lock a row, document, or partition before touching it. The other writers wait until the lock releases. Right choice when contention is high (same few records hammered by many concurrent writes) or when collisions are expensive enough that you need a guarantee at the write moment rather than a retry. Classic OLTP — banking, inventory, seat reservations.

**Optimistic concurrency** assumes conflict is rare and checks only at commit time. You read a version number or timestamp, do your work locally, then attempt to write with a `WHERE version = X` condition. If the version changed, someone else committed first — you retry from scratch. Right choice when contention is low (most transactions touch different data), when reads dominate writes, or when latency matters more than predictable write latency. Think social media feeds, analytics backfills, read-heavy APIs.

The dividing line: *do you pay the cost of coordination at every operation (pessimistic) or only when a rare collision actually happens (optimistic)?*

You're building a system ingesting billions of rows per month. That volume immediately tells you something: unless those billions hit the exact same partition simultaneously, you want optimistic — the coordination cost of pessimistic locks across that throughput would be a bottleneck you'd never unstick. But if you're writing a stream of deduped events to a specific user's timeline partition where two tasks could attempt the same write? That's where you pin a single record-level lock and move on. 

Know your hot spots. Everything else is math.

### Q10 [CHAT] — What is the difference between a process and a thread, and when would you use multiprocessing vs threading in Python? Answer from your training knowledge.

Processes have isolated virtual address spaces — each gets its own heap, stack, registers, page tables, file descriptor table, signal handlers. Threads share the address space of their parent process — same heap, same code/data segments, same open file descriptors. What threads *don't* share: each gets its own stack, program counter, register set, and errno value.

Context-switching between threads within the same process is lighter — no TLB flush required, no page table swap. Between processes, the kernel has to switch virtual memory mappings entirely, which is where the real cost lands. On x86, Meltdown mitigations made that flush even more expensive than it used to be.

**Python specifically:**

The GIL makes pure-Python CPU-bound threading useless — only one thread holds the GIL at a time, so parallelizing compute with threads gives you contention overhead with zero throughput gain. Multiprocessing side-steps this entirely: each child process gets its own interpreter, its own GIL, and full CPU core utilization.

Use threading when:
- The work is I/O-bound — HTTP requests, database queries, file reads, anything that blocks on the kernel. The GIL is released during `time.sleep()`, `select()`, `read()`, `write()`, and async-aware library calls, so threads *can* overlap waiting with computation. LuaSocket-style cooperative scheduling without the yield.
- You need shared state without serialization overhead — a shared `dict` with a `Lock` is cheaper than `multiprocessing.Manager` or serializing data via `pickle` across process boundaries.
- The number of concurrent operations is bounded and in the hundreds, not thousands (the thread switching overhead eventually bites).

Use multiprocessing when:
- The workload is CPU-bound — matrix multiplication, data transformation, rendering. Each process uses a full core independently.
- You need fault isolation — a segfault in one process doesn't take down the others. This matters in production ingestion pipelines where a malformed input in one stream shouldn't corrupt the whole system.
- You have large numeric arrays and can leverage shared memory via `multiprocessing.shared_memory` (Python 3.8+) to avoid copy overhead — `numpy` arrays in shared memory segments, zero-copy reads across workers.

The hybrid pattern that dominates real systems: multiprocessing for parallel compute, threading (or `concurrent.futures.ThreadPoolExecutor`) within each process for I/O-bound sub-tasks. Your ingestion pipeline, for example — one process per data source, threads within each process to handle the individual HTTP calls, connection pool shared via thread-local state.

### Q15 [CHAT] — Explain how Python's asyncio event loop runs many coroutines on a single thread, and what happens to the whole loop if one coroutine performs a long blocking CPU-bound computation. Answer from your training knowledge.

It's cooperative multitasking. The event loop runs in a single thread, maintaining a queue of scheduled callbacks. A coroutine only yields control when it hits an `await` — typically on an I/O operation (network, file, sleep) that the loop can service while other coroutines run. The loop picks the next ready coroutine from the queue, advances it to its next `await`, and repeats. This works because I/O-bound coroutines spend most of their time waiting, not computing.

If one coroutine does a long CPU-bound computation *without* yielding — no `await`, no `asyncio.sleep(0)`, no `run_in_executor` — it blocks the entire loop. No other coroutine gets to run, no callbacks fire, no new connections are accepted, until that computation finishes. The loop becomes a synchronous single-threaded program until control returns.

Fix is `loop.run_in_executor(None, blocking_fn, args)` — offloads the CPU work to a thread pool so the event loop stays responsive.
