### Q01 [CHAT] — Explain what idempotency means for an API request, and why it matters when a client retries a call. Answer from your training knowledge.

Idempotency means that making the same request multiple times produces the same effect as making it once. A PUT that updates a resource to a specific state is idempotent — the fifth attempt leaves the server in the same state as the first. A POST that creates a new order is not — three identical POSTs create three orders unless the client supplies an idempotency key that the server deduplicates against.

It matters for retries because networks drop packets, servers crash mid-write, and clients time out waiting for responses the server already processed. Without idempotency, the standard retry pattern — resend on timeout or 5xx — becomes a guaranteed source of double charges, duplicate records, and corrupted state. With it, the client can retry safely because the server can detect the duplicate and return the original response instead of executing the operation again.

The canonical patterns are: natural idempotency via PUT/DELETE semantics where the operation is its own identity check, or explicit idempotency keys on POST endpoints where the client generates a unique key per intent and the server rejects subsequent requests carrying the same key.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

A primary key uniquely identifies each row within its own table — every table has exactly one. A foreign key is a column (or set of columns) in one table that references the primary key of another table, enforcing referential integrity across the two. The primary key guarantees uniqueness and non-null within its table; the foreign key can have duplicates and nulls, and its values must exist in the referenced primary key column (or be null).

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

Readers get a consistent snapshot of committed data as of their transaction's start time, with visibility determined by comparing each row's creation/deletion transaction IDs against that snapshot. Writers create new row versions via copy-on-write instead of in-place updates, so neither blocks the other.

The garbage is **bloat** — old row versions that are no longer visible to any active transaction. These accumulate in table and index pages and must be reclaimed by a garbage collector (Postgres calls it VACUUM, MySQL uses purge threads) that identifies versions whose visibility transaction ID is older than the oldest still-running transaction and recycles their storage.

The tension is that the collector can never advance past the oldest open transaction — a long-running idle transaction pinning a snapshot prevents cleanup, causing table bloat to grow unbounded.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

A microservices migration is the process of decomposing a monolithic application into independently deployable services, each owning its own data and communicating over a network boundary.

The main risks:

**Distributed transactions** — The monolith's ACID guarantees vanish. You now have eventual consistency across service boundaries, and compensating transactions or sagas become necessary. Most teams discover this six weeks in when a payment succeeds but the inventory reservation doesn't.

**Network as a new primitive** — Latency, timeouts, partial failure, retry storms, cascading failures. A monolith's function call that took 1ms becomes an RPC that takes 50ms, if it doesn't fail silently. Circuit breakers, bulkheads, and timeouts are no longer optional — they're the entire reliability model.

**Data coupling** — Joins across services are gone. Every query that touched five tables in the monolith requires either an API composition layer, CQRS with read replicas, or event-driven denormalization. Most teams underestimate how many of these queries exist until they've already cut the boundary.

**Operational blast radius** — One service's memory leak takes down the entire cluster if resource limits aren't set. One bad deployment propagates if service discovery doesn't isolate it. Monitoring goes from "is the app up?" to "are 47 services healthy, and if not, which one is the root cause and which are just symptomatic?"

**Team alignment fallacy** — Conway's law cuts both ways. Splitting by technical layer instead of business capability guarantees you get distributed monolith with extra latency. Splitting before the team structure is ready guarantees coordination overhead that eats the speed gain.

**Premature extraction** — The most common failure pattern. Teams extract a service boundary that maps to what *could* change, not what *has* changed. The outcome: a split that adds complexity without reducing deployment risk or improving iteration speed. Strangler Fig pattern exists for a reason — extract only what's actively causing pain, and only when the boundaries are empirically clear.
