### Q01 [CHAT] — Explain what idempotency means for an API request, and why it matters when a client retries a call. Answer from your training knowledge.

Idempotency means that making the same request multiple times produces the same effect as making it once. In REST terms: GET, PUT, DELETE are idempotent — retrying them safely produces the same server state. POST is not idempotent — each call creates a new resource.

It matters for retries because networks fail. Clients time out without knowing whether the server processed the request or not. If the operation is idempotent, the client can retry without risk. If it isn't, retries cause duplicate charges, duplicate orders, or double-created resources — which means the server now needs deduplication logic, idempotency keys, or exactly-once semantics to recover from something that should have been safe to retry. Kleppmann covers this well in the chapter on reliability.

### Q05 [CHAT] — Explain the difference between a primary key and a foreign key in relational databases. Answer from your training knowledge.

A primary key uniquely identifies each row in a table — it's unique, non-null, and there can be only one per table. A foreign key is a column (or set of columns) in one table that references the primary key of another table, enforcing referential integrity across the two. In short: primary key says "this is who I am," foreign key says "this is who I'm related to."

### Q08 [CHAT] — Explain how MVCC (multi-version concurrency control) lets database readers avoid blocking writers, and what kind of garbage it creates that must later be cleaned up. Answer from your training knowledge.

MVCC works by giving each reader a snapshot of committed data at the moment its transaction begins. Instead of locking rows, the database keeps multiple versions of each row — when a writer updates a row, it creates a new version tagged with a new transaction ID. Readers simply read the version that was current at their snapshot point. The writer's new version is invisible to concurrent readers until the writer commits, at which point it becomes the latest visible version for future transactions. Neither waits on the other because readers never request exclusive access and writers never modify in-place data that readers might still be referencing.

The garbage it produces is **bloat** — old row versions that are no longer visible to any active transaction. Every update and delete leaves behind a dead row version because the database can't safely reclaim the space until it's certain no running snapshot can still see it. Over time these accumulate, inflating table size, degrading cache efficiency, and slowing sequential scans. The cleanup process — VACUUM in PostgreSQL, history eviction in MySQL InnoDB, compaction in distributed MVCC stores — traverses the heap, marks dead rows as reusable, and optionally defragments the space. If VACUUM doesn't keep pace with write volume, bloat grows unbounded until you're paying storage and query latency for data that no longer logically exists.

### Q15 [CHAT] — What is a microservices migration, and what are the main risks when splitting a monolith into independent services? Answer from your training knowledge.

You're asking for a concept from my training knowledge, not from your codebase. I know this. Straighten it out fast.

**What it is:** A microservices migration is the process of decomposing a monolithic application into independently deployable, loosely coupled services that communicate over a network — each owning its data, its lifecycle, its failure profile. It's a structural and operational transformation, not just a code refactor. The goal is organizational scaling: teams own services end-to-end, deploy independently, choose appropriate tech stacks per domain. The cost is every distributed systems problem you've ever skipped in a monolith — now unavoidable.

**Main risks when splitting a monolith:**

1. **Network = new failure mode.** Latency, timeouts, partial failures, retry storms — things that simply didn't happen in-process become constant. You need circuit breakers, bulkheads, retry policies, idempotency on every cross-service call. Most teams discover this one month in, not on day one.

2. **Data ownership bleed.** The hardest part is splitting a shared database. Teams that keep sharing tables or even read-replicas haven't migrated — they've created a distributed monolith. True decoupling requires defining service boundaries, extracting bounded contexts, owning data end-to-end per service. Reconciliation, eventual consistency, saga patterns — these aren't simplifying the system, they're making consistency explicit where it was implicit.

3. **Distributed transactions via saga is a trap.** The naive move is "make it eventually consistent and move on." But partial failures in saga workflows are extremely difficult to debug, idempotency guarantees are rarely complete, and compensating transactions don't always restore state cleanly. Most teams underestimate this by approximately 3x-5x in engineering time.

4. **Observability debt swaps.** In a monolith you have a single log stream, a single process to profile. In microservices you need distributed tracing, structured logging aggregation, per-service metrics pipelines, centralized alerting that understands request flows, not just individual service health. Most teams build none of this upfront and spend months retrofitting it while incidents pile up.

5. **Deployment complexity explosion.** One deploy pipeline becomes N pipelines. Each with its own rollback path, its own dependency versioning, its own canary/release strategy. Orchestrating an N-service release — coordinating schema migrations across services, feature flags that span multiple deployments, backward compatibility windows — this is a first-class engineering problem that doesn't exist in a monolith.

6. **Team/organization boundary mismatch.** Conway's Law isn't optional. If teams don't align with service boundaries, you get either (a) coordination hell — every change touches multiple teams — or (b) a monolith dressed as services, where one team "owns" the boundary and everyone else works around it. The migration reveals organizational problems faster than technical ones.

7. **Premature extraction.** The most common failure pattern: splitting a service that doesn't have a clear bounded context just to "start modernizing." You end up with services that call each other five times to serve one request, or that share caches, or that have circular dependencies. The rule: extract only when the boundary is clear *and* you have a forcing function (team size, scaling bottleneck, independent deploy needed). Everything else should stay in the monolith until it hurts enough to move.

The correct migration strategy is the Strangler Fig pattern: extract capabilities one at a time, maintain backward compatibility at the monolith boundary, and don't cut over until the new service runs in production alongside the monolith for long enough to prove its failure profile. Most teams rush the cut-over. That's where the real damage happens.
